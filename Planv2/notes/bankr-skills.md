# Bankr skills research: working notes

Sources: the ten files in `Planv1/research/bankr-skills/` (three reports `01-codebase-report.md`, `02-platform-mapping.md`, `03-spike-plan.md`, plus `notes/00-brief.md`, `notes/00-phase0.md`, `notes/00-inventory.tsv`, `notes/A-format.md`, `notes/B1-tools-a-l.md`, `notes/B2-tools-m-z.md`, `notes/C-catalog-security.md`), read in full. Citations use `file.md > Section heading`; notes files are cited as `notes/X.md > Section heading`. The source files label their own statements Verified or Inferred; where a source says Inferred, I keep that word. "Inference" marks my own reasoning. The decision register quoted in the task brief is called "the register". Nothing in Planv1 was changed; this note is the only file written.

## 1. Coverage and verdict

The research is a read-only study of the `BankrBot/skills` clone at commit `d7b28f4caea71b446655ef991346f4860b95656a` (last commit 2026-09-22, first commit 2026-01-26, 623 commits on `main`, 103 unique contributor names, 142 PR merges all by two maintainers, no root LICENSE); it counted 152 skill markdown files (145 root `SKILL.md`, one lowercase `BOTCOIN/skill.md`, 5 nested under `opensea/`, one uncatalogued duplicate under `skills/`), 146 `catalog.json` entries (115 `install.type: bankr`, 29 `external`, 2 non-conforming), about 121 skills with real content, 29 external-install stubs of 11 lines, and 2 four-line placeholders (`01-codebase-report.md > 1. Versions, license, contributors, summary`). No repository script was run, nothing was installed, and no URL taken from a skill was fetched; the Hermes material came from the official Hermes docs and agentskills.io through a paraphrasing fetch tool and is flagged for re-checking against source at our pinned version (`01-codebase-report.md > 3.6 Compared with Hermes Agent conventions`, `notes/A-format.md > 6. Comparison with Hermes Agent and agentskills.io`). The verdict: Bankr's catalog is a flat, PR-curated folder-per-skill format with "no manifest of permissions, no version pinning, no publisher signing, and no CI"; about 55 skills move value and "every one of them would bypass our Executor if used as written"; the easiest material to port is the research playbooks (the Aeon suite), the protocol knowledge bundles, and the few skills whose scripts emit unsigned transactions (`01-codebase-report.md > 1. Versions, license, contributors, summary` Summary paragraph). What to borrow is therefore the SKILL.md progressive-disclosure shape, the writing patterns of the best skills, the Bankr signing-gate model as an Executor policy reference, the x402 pinning guardrails as tool-server config, and the security findings as audit rules; what to reject is scripts, keys, remote fetches, free-form prompt delegation, and mutable `main`-tracking installs, which Report 2 turns into four design principles: text plus declarations never code or credentials; the manifest is the single source of truth; versions are content-addressed and immutable; all effects go through platform tools and typed intents (`02-platform-mapping.md > Design principles`).

## 2. The skill.json spec, verbatim structure

### 2.1 Manifest fields

All rows from `02-platform-mapping.md > 2.1 Skill package spec v1 > Manifest fields (skill.json)`. The design is the research's proposal and is labelled Inferred by definition in that report's header.

| Field | Type | Required | Meaning | Notes |
|---|---|---|---|---|
| `schema_version` | int | Required | Spec version | Value `1` |
| `id` | string | Required | Slug; equals the folder name | Unique per publisher namespace, globally unique for listed skills, immutable across versions; lowercase a-z0-9 and single hyphens, 3 to 64 chars (folder structure comment) |
| `name` | string | Required | Display name | Max 48 chars |
| `version` | semver string | Required | `MAJOR.MINOR.PATCH` | Immutable once published: the platform computes `content_hash` over the canonical package and rejects any upload that reuses a version with a different hash |
| `type` | enum | Required | `protocol`, `strategy`, or `research` | |
| `publisher` | object | Required | `{ id, address, key_id }` | Package is signed by `key_id`, which must be registered to `address` in the PublisherRegistry; protocol skills require a verified publisher |
| `description.model` | string | Required | What the model sees in the skill index | Max 160 chars; the first 57 chars must stand alone because Hermes truncates the index (web source; Spike); written as "Does X. Use when Y."; copied into generated frontmatter `description` |
| `description.marketplace` | string | Required | Human-facing listing text | Max 600 chars; never shown to the model |
| `triggers` | string[] | Optional | "Use when" phrases | 1 to 8 phrases, max 120 chars each; rendered into a "When to use" section at the top of SKILL.md; replaces Bankr's long trigger-laden descriptions (median 386 chars) |
| `not_for` | string[] | Optional | Negative scope | Rendered into "When not to use"; Bankr examples `0xwork`, `defi-native` |
| `required_tools` | string[] | Required (may be empty) | Platform tool IDs the skill calls, with a major version | Example `data.dex_quote@1`, `chain.read_contract@1`; build fails if the agent's tier lacks any; mapped to Hermes `metadata.hermes.requires_tools` so Hermes hides the skill when a tool is absent (web source; Spike) |
| `intents` | string[] | Required (may be empty) | Typed intents the skill may propose | Example `intent.propose_swap@1`; any intent the model emits that is not listed is rejected by policy for calls attributed to this skill (see 2.8 risk 4) |
| `data_sources` | string[] | Required (may be empty) | Registered data source IDs reached through data tools | Examples `defillama.yields`, `dune.query:4123456`, `x.search`; used for metering, disclosure and audit egress comparison |
| `required_tier` | enum | Optional | `base`, `medium`, `pro` | Default `base`; enforced by BuildRegistry |
| `slot_cost` | int | Required | Slots consumed in a build | 1 to 3, default 1; proposal: 1 for research and simple protocol skills, 2 for strategy skills, 3 only for multi-intent strategy skills; enforced by BuildRegistry against tier slot counts |
| `synergy_tags` | string[] | Optional | Marketplace and build-suggestion tags | Max 8, from a controlled vocabulary (for example `monad`, `usdc`, `wmon`, `dex`, `lp`, `lending`, `risk`, `research`, `allocation`); never used for permissions |
| `compatible_templates` | object[] | Required for `strategy`; optional otherwise | Platform strategy templates this skill tunes | `[{ id, version, params }]` where `params` is a JSON file of parameter defaults and bounds that must fit inside the template's own bounds |
| `chains` | string[] | Required | CAIP-2 chain IDs | `eip155:143` used for Monad mainnet as a placeholder to confirm; launch allowlist is Monad only |
| `assets` | string[] | Optional | Token allowlist the skill reasons about, as CAIP-19 IDs | Policy uses it as an extra allowlist for this skill's intents |
| `privacy` | enum | Required | `public` or `private` | `private` requires `type: strategy`, triggers encryption at rest, and disables showing the text in the marketplace |
| `dependencies` | object[] | Optional | Other skills by `{ id, version }` | Informational in v1 (rendered as `metadata.hermes.related_skills`); the build warns if one is missing; only one machine-readable dependency exists in all of Bankr (`BOTCOIN/skill.md`) |
| `disclosures` | object | Optional | `{ fees, referrals, conflicts }` | Required if the skill routes value to any address other than the owner's agent (Bankr examples `megapot` referrer, `based-mining` treasury) |
| `license` | SPDX string | Optional | For public skills | Default `LicenseRef-Platform-Standard` |
| `min_platform` | semver | Optional | Minimum platform runtime version | |

Computed by the platform, never set by publishers, stored in the registry and onchain as hashes: `content_hash` (sha256 over the canonical, sorted package bytes), `manifest_hash`, `signature`, `audit_attestation`, `published_at` (`02-platform-mapping.md > 2.1 Skill package spec v1 > Manifest fields (skill.json)`).

### 2.2 Folder structure and limits

From `02-platform-mapping.md > 2.1 Skill package spec v1 > Folder structure`:

- `<slug>/` where slug equals `manifest.id`.
- `skill.json` REQUIRED: the canonical manifest, authored by the publisher.
- `SKILL.md` REQUIRED: body written by the publisher; the frontmatter is GENERATED by the platform from `skill.json` at build time and any publisher frontmatter is discarded.
- `references/` OPTIONAL: Markdown only, one level deep, max 40 files, 100 KB each.
- `data/` OPTIONAL: static reference data as `.json`, `.csv`, `.yaml`; max 20 files, 256 KB each; schema-checked; no URLs that the model is told to call.
- `examples/` OPTIONAL: worked examples in `.md` (input, reasoning, tool calls, output).
- `evals/evals.yaml` REQUIRED for strategy skills, optional otherwise: prompts plus assertions used by the audit pipeline and version upgrades.
- `CHANGELOG.md` REQUIRED from version 1.1.0 onward.
- Not allowed anywhere: `scripts/`, `assets/`, `bin/`, executables, archives, binaries, dotfiles, symlinks, `package.json`, `requirements.txt`, `.env*`, `AGENTS.md`, `CLAUDE.md`, `.claude/`, `.hermes/`, HTML, images, or any file type not listed. Marketplace art lives outside the package.
- Size limits: SKILL.md at most 500 lines and 40,000 characters; whole package at most 2 MB uncompressed; these sit under Hermes' 100,000-character cap (web source; Spike) and follow the agentskills.io 500-line guidance.
- Why no scripts: Bankr's best strategy skill (`aero-stock-lp`) keeps its gates and calldata in deterministic scripts; in our model that determinism belongs in platform-owned strategy templates and Executor policy, and a skill references a template by ID and supplies parameters through `compatible_templates`, which keeps "skills do not write trading code at launch" true.

### 2.3 Hermes compatibility rules

From `02-platform-mapping.md > 2.1 Skill package spec v1 > Hermes compatibility` (all Hermes facts are web-sourced and marked Spike there; the underlying evidence is `notes/A-format.md > 6.1 What Hermes reads` and `notes/A-format.md > 6.2 How Hermes selects and loads skills`):

- Hermes reads `name`, `description`, `version`, `platforms`, and `metadata.hermes.{tags, related_skills, requires_tools, requires_toolsets, fallback_for_*, config, blueprint}`; it loads skills in three levels (index, then `skill_view`, then a reference file) from `skills.external_dirs`.
- What we generate: SKILL.md frontmatter from `skill.json`, discarding publisher frontmatter: `name` (equals folder and `id`), `description` (always double-quoted, from `description.model`), `version`, and `metadata.hermes.tags`, `metadata.hermes.requires_tools`, `metadata.hermes.related_skills`. The report's example shows `requires_tools: [price_feed, dex_quote, portfolio, volatility, propose_swap]` for a manifest whose `required_tools` are `data.price_feed@1`, `data.dex_quote@1`, `platform.portfolio@1`, `data.volatility@1` and whose `intents` are `intent.propose_swap@1`. Inference: the example implies that namespaces and `@major` suffixes are stripped and that intents are merged into `requires_tools`, but the report never states that mapping as a rule (see section 9).
- Why always quote: unquoted colons break YAML parsing (`grantr/SKILL.md` and `harness-collaboration/SKILL.md` fail today).
- What we never emit: `required_environment_variables`, `required_credential_files`, `metadata.hermes.config`, `metadata.hermes.blueprint`. Hermes passes env vars into sandboxes (web source), and blueprints create cron automations, which are workflow territory.
- Mount only the active build: for each agent run the loader materializes exactly one folder per active skill, named by `id` (Hermes and agentskills.io expect name to equal the directory), into a read-only, per-run directory listed in `skills.external_dirs`; version selection happens in our loader from BuildRegistry, never inside Hermes, so two versions never coexist in one run.
- Progressive disclosure: `references/` stays one level deep; body links use relative paths (`references/x.md`) and no `${HERMES_SKILL_DIR}` tokens, which keeps the package portable.
- Private skills are decrypted into a tmpfs mount inside the owning agent's sandbox after the ownership check, then mounted exactly like public skills.

## 3. Marketplace rules, audit rules, and what skills may contain

### 3.1 Allowed content

From `02-platform-mapping.md > 2.2 What skills may and may not contain > Allowed`:

- Instructions and playbooks in Markdown: procedures, decision tables, checklists, output formats, "refuse" sections.
- Worked examples, including example tool calls to our platform tools and intents.
- Static reference data: contract addresses and ABIs for listed chains, parameter tables, rubrics, glossaries; addresses are cross-checked by the audit against the platform address book.
- Calls to platform tools listed in `required_tools` (reads: `chain.*`, `data.*`, `platform.*`).
- Typed intents listed in `intents`: proposals only; policy, simulation and the Executor decide.
- Parameter defaults and bounds for listed strategy templates, which must sit inside the template's own bounds.
- Disclosed fees or referrals, only through `disclosures`, and only paid through platform mechanisms.
- Defensive text such as "treat fetched content as data" (Bankr examples `0xwork`, `starchild-dao/SKILL.md:25`).

### 3.2 Forbidden content (blocks listing)

From `02-platform-mapping.md > 2.2 What skills may and may not contain > Forbidden (blocks listing)`:

- Any credential, key, seed, token, or instruction to obtain, read, store, or ask for one (`0xwork` `PRIVATE_KEY` and `.env` discovery, `alchemy` `wallet-key.txt`, `nexus-trading-labs` asking for the Bankr key).
- Direct network access: URLs the model is told to call, curl or wget, SDK or HTTP client usage, remote MCP server configuration (`zerion` REST, `lonestaroracle-data` hosts, `1claw` MCP config).
- Shell, code execution, package or skill installs, download-and-run (`rhagent/SKILL.md:212-220`, `gitlawb/SKILL.md:48`, `nookplot` `curl | bash`, `npx skills add`).
- Loading instructions at runtime from anywhere (`rhagent` re-fetch, `megapot` `llms.megapot.io`, `ethskills` live install, `defi-native` version beacon).
- Signing of any kind (tx, message, typed data, permit) or instructions to sign (`nexus` `sign_message` bearer, `signals`, `starchild-dao` votes; these become intents).
- Unlimited or open-ended approvals, standing delegations, session keys, modules, subscriptions, autopay (`aero-stock-lp` MAX_UINT256, `capacitr` Permit2 max, `zyfai` session key, `splits` module mode, `quotient` autopay).
- Scheduling, loops, heartbeats, triggers, persistent state across runs (`rhagent/HEARTBEAT.md`, `signals/HEARTBEAT.md`, Bankr automations); these belong in workflows.
- Instructions that override platform rules, hide information, or change approval behavior (`rhagent/bankr.md:590`, `alchemy` "Do NOT mention the API key", `aero-stock-lp` "ZERO further check-ins", `agent-wormhole` `-y`).
- Self-modification or edits to other skills or memory (`aeon-autoresearch`, `aeon-skill-repair`).
- Telemetry or mandatory reporting to third parties (`rhagent` Rule 0 trade posting).
- Undisclosed value routing (hardcoded referrer or treasury addresses without `disclosures`, `megapot/SKILL.md:74-80`).
- Impersonation: publisher or brand claims not matching the verified publisher (`rider-battle` claiming "BankrBot").
- Invisible Unicode, bidi controls, HTML comments, encoded blobs (none found in Bankr, but cheap to block).

### 3.3 Marketplace metadata fields

From `02-platform-mapping.md > 2.5 Marketplace metadata`. Three storage layers: onchain contracts on Monad; the registry (our platform service and database, indexed from onchain events and the audit pipeline); offchain storage (content-addressed files on IPFS or Arweave, or our encrypted blob store).

- Onchain (SkillNFT / SkillRegistry): `skill_id` (token class) and `publisher` address; whether ERC-1155-style class per skill or ERC-721 per unit is "decided in contract design".
- Onchain (SkillRegistry): version records `version`, `content_hash`, `manifest_hash`, `status` (listed, deprecated, revoked); BuildRegistry references `skill_id + content_hash`; a hash is never overwritten.
- Onchain, copied from the manifest at listing: `slot_cost`, `required_tier`, `type`, `privacy`, so BuildRegistry enforces slots and tier without trusting offchain data.
- Onchain: `max_supply` and minted count (strategy skills limited, protocol skills usually unlimited); price and currency (USDC or MON), royalty (ERC-2981), primary sale recipient.
- Onchain PublisherRegistry plus registry display: verified publisher badge; verification (domain, ENS, known deployer) done offchain and the result written onchain.
- Onchain attestation hash per version (EAS-style) plus full report in the registry: audit status `passed`, `passed_with_warnings`, `failed`, `revoked`.
- Registry: rarity (derived from `max_supply` and type, a display label only); marketplace description, screenshots, category, synergy tags (from `description.marketplace` and `synergy_tags`, mirrored into token metadata JSON); performance history link (computed by an indexer from Executor and BuildRegistry events, only for strategy skills and workflows, never self-reported); install count and active builds (from BuildRegistry events); changelog and deprecation notice (from `CHANGELOG.md`).
- Offchain (IPFS or Arweave) referenced from the token metadata URI: 3D component art (model, thumbnails), never inside the skill package so art changes cannot change audited content.
- Offchain encrypted store plus a key service gated on an ownership check: the encrypted package blob and key wrapping, private skills only.

### 3.4 Audit pipeline

Stages, from `02-platform-mapping.md > 2.6 Audit rules`: (1) format validation, (2) static rules, (3) LLM review, (4) dynamic sandbox test, (5) human review for strategy skills and first-time publishers. Findings are Block (cannot be listed) or Warn (listed with a warning shown, or must be fixed before a verified badge).

Format rules, all Block (`02-platform-mapping.md > 2.6 Audit rules > Format rules (all Block)`):

- F1: `skill.json` validates against schema v1; `id` equals folder; semver valid; version not already published with a different hash.
- F2: only allowed paths and file types; no symlinks, executables, archives, binaries, dotfiles.
- F3: size limits (SKILL.md 500 lines and 40k chars; references 100 KB; package 2 MB).
- F4: `description.model` max 160 chars; first 57 chars non-empty and not cut mid-word.
- F5: every tool in `required_tools` and intent in `intents` exists in the platform registry at that major version and is allowed for `required_tier`.
- F6: every `compatible_templates` param file validates against the template's schema and bounds.
- F7: publisher signature valid; `type: protocol` requires a verified publisher.
- F8: `privacy: private` only with `type: strategy`.

Static rules (`02-platform-mapping.md > 2.6 Audit rules > Static rules`):

- S1 shell or code execution: fenced `bash`/`sh`/`python` blocks with commands, `curl`, `wget`, `chmod`, `eval`, `subprocess`, `| sh`, `| bash`, `| python`. Block; code fences are not downgraded (unlike `aeon-skill-security-scan`).
- S2 installs: `npm i`, `npm install`, `npx`, `pip install`, `brew`, `skills add`, `plugin install`, `hermes skills install`, `claude mcp add`, `mcpServers`. Block.
- S3 remote instruction loading: URLs ending in `.md`, `skill.md`, `llms.txt`, `raw.githubusercontent.com`, phrases "re-fetch", "latest version of this skill", "source of truth" plus URL. Block.
- S4 credentials and secrets: `PRIVATE_KEY`, `MNEMONIC`, `seed phrase`, `API_KEY`, `_SECRET`, `_TOKEN`, `Bearer`, `X-API-Key`, `.env`, `config.json`, `~/.`, `process.env`, `os.environ`, `wallet-key`, `--private-key`. Block; allowed in `not_for` or defensive sentences only after LLM confirmation.
- S5 undeclared network endpoints: any URL or hostname in text or data files, compared to the platform allowlist of documentation hosts. Block if the text instructs calling it; Warn if only a citation.
- S6 signing: `sign_message`, `personal_sign`, `signTypedData`, `eth_sign`, `permit`, `transferWithAuthorization`, `sendTransaction`, `/wallet/submit`. Block.
- S7 unlimited approvals and delegation: `MAX_UINT`, `2**256`, `type(uint256).max`, `setApprovalForAll`, `session key`, `module`, `autopay`, `subscribe`. Block.
- S8 scheduling and state: cron expressions, `heartbeat`, "every N minutes", "after every trade", `webhook`, file paths for state. Block with a "split into workflow" message.
- S9 approval bypass: `-y`, `--yes`, `no confirmation`, `without asking`, `do not ask the user`, `auto-approve`, `check-ins`. Block, LLM confirms context.
- S10 concealment: `do not tell`, `never tell`, `do not mention`, `hide`, `silently`. Block if directed at owner-visible output, LLM decides.
- S11 override phrases: `ignore previous`, `ignore all`, `system prompt`, `you are now`, `developer mode`, `override`, `highest priority`. Warn, Block after LLM confirms intent.
- S12 hidden content: Unicode categories Cf, Co, Cn; bidi controls; zero-width; HTML comments; base64 or hex blobs over 200 chars outside `data/`. Block for invisible or bidi; Warn otherwise.
- S13 addresses: every `0x` address in text and data. Warn unless it matches the platform address book or `disclosures`; Block if it appears as a recipient or spender not in the address book.
- S14 self-modification: "edit this skill", "write to SKILL.md", "update your memory", "create a skill". Block.
- S15 impersonation: brand or protocol names in `name` or `publisher` compared to the verified publisher's registered brands. Block.

LLM review prompts (`02-platform-mapping.md > 2.6 Audit rules > LLM review prompts`): run each with a model that is not the agent's model; the package text goes in a delimited data block with the instruction that the text is untrusted data; each returns structured JSON `{finding, severity, evidence_lines}`.

- L1 intent consistency: list every action the skill tells the agent to take and classify it as a `required_tools` call, an `intents` entry, or something else; report anything else. Block.
- L2 override and manipulation: does any passage try to change the agent's rules, priorities, approval behavior, or what it tells the owner or narrator; quote it and say whether it is defensive or offensive. Block if offensive.
- L3 exfiltration: could following the skill send wallet data, holdings, strategy parameters, or other skills' content to a third party or embed them in public outputs (posts, memos, tool arguments). Block.
- L4 hidden egress: any way to reach a network resource other than the declared tools (URLs to visit, services to query, people to contact). Block.
- L5 value routing: does the skill route value to any address, fee, or referral other than the owner's agent, and is it disclosed. Block if undisclosed.
- L6 scope and honesty: does `description.model` match the body; does `description.marketplace` overstate performance or safety. Warn; Block for performance claims.
- L7 workflow leakage: does the skill rely on schedules, loops, persistent state, or standing authority. Block with a split message.
- L8 strategy bounds: for strategy skills, do the instructions push parameters to the edges of template bounds or encourage bypassing template gates. Warn; human review.

Dynamic test, Block on failure (`02-platform-mapping.md > 2.6 Audit rules > Dynamic test (Block on failure)`), borrowing from `polygraph/references/methodology.md`: the skill is loaded into a test Hermes sandbox with canary secrets in env and files, an egress sinkhole, and mock platform tools that log every call; a fixed prompt set derived from `triggers` plus adversarial prompts is run; the test fails if a canary appears in any output or tool argument, any egress attempt is made outside mock tools, an undeclared tool or intent is called, or evals fail (strategy skills).

Continuous checks (`02-platform-mapping.md > 2.6 Audit rules > Continuous checks`): re-run L1 to L5 on every new version; diff each new version against the previous one and flag new URLs, addresses or intents; revoke a version onchain (status `revoked`) if a later finding confirms abuse, after which BuildRegistry refuses it and the loader unmounts it at the next run.

## 4. Skills versus workflows, and converting external skills

### 4.1 General mapping rules

From `02-platform-mapping.md > 2.3 Converting external skills > General mapping`:

- External REST or MCP read (portfolio, prices, quotes, market data) becomes a data tool on our data tools server, called with our platform key, metered per agent and tier; the skill keeps only the knowledge of when and how to use it.
- x402-paid endpoint: our data server pays (key or x402 from a platform wallet) and meters the agent; the agent never sees a 402; Bankr's pinning rules (payee, asset, cap) become server config.
- Chain write (swap, approve, deposit, stake, claim) becomes a typed intent with fixed fields, policy checks (allowlists, caps, exact approvals), simulation, then the Executor.
- Calldata built by a third-party API becomes a quote tool returning a `quote_id` bound to exact parameters (the Suwappu pattern, `suwappu-dex/SKILL.md:55-63`), then an intent referencing the `quote_id`; the Executor validates target and selector against the allowlist and never submits API calldata blindly.
- Deterministic scripts (gates, math, calldata) become a platform strategy template (audited code we own) with typed parameters.
- Scheduling, triggers, loops, approval grants become a workflow NFT.
- Keys, installs, remote fetches, telemetry, self-updates are dropped.
- Knowledge, rubrics, checklists, refusal lists are kept in SKILL.md and `references/`.

### 4.2 Worked example 1: `zerion` becomes `wallet-intel`

From `02-platform-mapping.md > 2.3 Converting external skills > Worked example 1: zerion`. Source facts: reads cover portfolio, positions, PnL, transactions, NFTs, gas, and swap offers (`zerion/SKILL.md:19-37`); access is by API key or x402 at $0.01 per call and the x402 client takes `PRIVATE_KEY` (`zerion/references/x402-reference.md:110-115`); execution is delegated to Bankr prompts including webhook copy-trade and stop-loss loops with no confirmation (`zerion/SKILL.md:437-491`); it is 569 lines, mostly endpoint reference. Treatment:

- The `GET /v1/wallets/{addr}/portfolio`, `/positions`, `/pnl`, `/transactions` endpoints become data tools `data.wallet_portfolio@1`, `data.wallet_positions@1`, `data.wallet_pnl@1`, `data.wallet_transactions@1`; the platform holds the Zerion key and meters.

### 4.4 The skill-versus-workflow boundary

Rule (`02-platform-mapping.md > 2.4 Skills versus workflows`): a skill answers "what does the agent know, and what can it propose in response to one request"; a workflow answers "when does the agent act without a fresh request, and under what standing authority". Tests:

- Needs a trigger other than the agent choosing to use it (time, event, price, webhook): workflow.
- Keeps state across runs (ledger, positions under management, watchlist diff, storyline): workflow.
- Relies on a standing approval, budget over time, delegation, or autopay: workflow (approval mode).
- Is a loop, a waiting period (cooldowns, unlock windows), or multiple runs: workflow.
- Is knowledge, a rubric, a checklist, a read method, or a bounded intent template for one request: skill.
- Contains both: ship the knowledge and intent templates as a skill and the routine as a workflow that declares the skill as a dependency.
- Mechanical audit check: cron expressions, "heartbeat", "every N minutes", "after every trade", "webhook", "autopay", "session key", "module", "subscribe" in a skill trigger a split-or-reject finding.

Bankr splits given in the same section: `aeon-deep-research`, `aeon-token-pick`, `bankr-token-scam-analysis` are skill only; `aeon-defi-monitor`, `aeon-unlock-monitor`, `aeon-monitor-polymarket` are both (method as skill; schedule, watchlist and alert as workflow); `aeon-distribute-tokens` is both (planning and idempotency method as skill; payout schedule, recipient allowlist and owner approval as a workflow of `propose_transfer` intents); `aero-stock-lp` is both; `harness-collaboration` is both and a design reference because its proposal, one-use authorization and ledger map almost 1:1 onto our intent plus workflow approval model (`harness-collaboration/SKILL.md:55-248`); `bankr-twitter-agent` is a non-financial workflow whose approval queue is a model for workflow approval modes; Bankr automations (limit, stop, DCA, TWAP) are workflow primitives to rebuild natively; `zerion` copy-trade examples are workflow only; `zyfai` session-key rebalancing and `megapot` subscriptions are not supported at launch; `symbiosis` and `trails` single bridge or swap recipes are skill only (one request, several transactions bundled into one intent). The same rule is derived independently in `notes/B1-tools-a-l.md > 5. Multistep flow skills: skill, workflow, or both` ("if a flow has a schedule, a watchlist, a waiting period or a loop, that part is a workflow") and `notes/B2-tools-m-z.md > 5. Multistep flow skills: skill, workflow, or both` (four-point general rule).
