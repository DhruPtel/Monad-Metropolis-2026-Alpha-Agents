## 1. Coverage and verdict

The research examined `morpho-org/vault-v2` at commit `9ee4dbdc` (merge of PR #1010, commit date 2026-09-25, `git describe` `2026-08-13-85-g9ee4dbdc`, GPL-2.0-or-later, Solidity 0.8.28 with `via_ir` and `evm_version = cancun`, so it uses transient storage). It covered `src/VaultV2.sol` (945 lines), `VaultV2Factory`, the two shipped adapters (`MorphoMarketV1AdapterV2`, `MorphoVaultV1Adapter`) and their factories, the gate contracts, the adapter registries, `BluePublicAllocator`, the libraries, 373 test functions, 39 Certora specs, and 15 audit PDFs (01-codebase-report.md > 1. Versions, licenses, and Monad deployment status; 01-codebase-report.md > 7.2 Audits; notes/00-brief-and-phase0.md > Phase 0 findings). MetaMorpho V1 submodules were empty, so V1 comparisons are general knowledge; Foundry was not installed, so every test and spec was read, not run (01-codebase-report.md > 1). Seven Morpho contracts have bytecode on Monad (chain 143), including `VaultV2Factory` at `0x8B2F922162FBb60A6a072cC784A2E4168fB0bb0c`, but whether that bytecode matches this commit was not verified (01-codebase-report.md > 1). The verdict is to build our own StrategyVault (the research's "Option C") that borrows Morpho's security architecture rather than its code path: constrained roles where managers can steer but not take, timelocks that exceed the depositor exit time, permanent abdication of dangerous setters, a risk-only emergency role, once-per-transaction valuation, virtual shares, and an exit that needs no role holder. Using Vault V2 directly (Option A) and forking it (Option B) were both rejected: the accounting is built for lending yield (upside clamped by `maxRate`, no high-water mark, adapter-trusted valuation, a flash-loan in-kind exit, a single immutable asset), and a fork would change the accrual and exit core, losing the audits and Certora coverage while inheriting GPL obligations (02-platform-mapping.md > 2.2 Build approach; notes/D-adapters-security.md > 2.5 Why the V2 model is a poor fit for spot trading). This matches the decision register's "own contract, not a fork". Option A is recorded as a sensible later product: a separate USDC lending vault using Morpho V2 unmodified (02-platform-mapping.md > 2.2).

## 2. Facts the final plan must carry

### 2.1 Roles and timelocks (Morpho, all Verified unless stated)

- Four configured roles: owner, curator, allocators (set), sentinels (set). Non-role actors: anyone, fee recipients, adapters, gates, adapter registry, per-adapter `skimRecipient`. There is no "guardian" role in Morpho; "guardian" is the research's name for our sentinel equivalent (notes/A-roles-timelocks.md > 1. Summary; 02-platform-mapping.md > 2.3 Role design).
- Owner (one address, set in constructor, then `setOwner`, one step, no accept, no zero-address check): `setOwner`, `setCurator`, `setIsSentinel`, `setName`, `setSymbol`. All instant. The owner never touches assets (NatSpec line 173). Certora `OwnerSafety.spec` only proves owner liveness (01-codebase-report.md > 4.1 Roles; notes/A-roles-timelocks.md > 2.4, > 4.3).
- Curator (one address, set instantly by owner): `submit(data)`, `revoke(data)`, `decreaseAbsoluteCap`, `decreaseRelativeCap`. Everything else it wants goes through `submit` (01-codebase-report.md > 4.1).
- Allocators (added or removed by timelocked `setIsAllocator`): `allocate`, `deallocate`, `setLiquidityAdapterAndData`, `setMaxRate` (up to 200% APR). None of these are timelocked (01-codebase-report.md > 4.1; notes/A-roles-timelocks.md > 2.2).
- Sentinels (added or removed instantly by owner): exactly `revoke`, `decreaseAbsoluteCap`, `decreaseRelativeCap`, `deallocate`. Cannot submit, allocate, set liquidity adapter, set maxRate, change roles, or undo anything. Weakness: the owner can remove a sentinel instantly, so the sentinel is only as independent as the owner (01-codebase-report.md > 4.4 Emergency role; notes/A-roles-timelocks.md > 5).
- Anyone: execute any matured timelocked call (`timelocked()` has no caller check; `test/SettersTest.sol:208` calls `setIsAllocator` from the test contract), `accrueInterest`, `forceDeallocate`, deposit and withdraw subject to gates (01-codebase-report.md > 4.1; notes/A-roles-timelocks.md > 2.2).
- Timelock mechanics: `submit` (curator only) stores `executableAt[data] = block.timestamp + timelock[selector]`, keyed by the exact calldata bytes; one pending entry per identical call; nothing about `data` is validated at submit time; pending entries never expire; execution is calling the function with identical calldata (01-codebase-report.md > 4.2 How timelocks work; notes/A-roles-timelocks.md > 3.1, > 3.2).
- `revoke` by curator or any sentinel. The owner cannot revoke directly but can make itself a sentinel instantly and then revoke. Certora `SentinelLiveness.sentinelCanRevoke` (notes/A-roles-timelocks.md > 3.3).
- `decreaseTimelock(sel, d)` waits `timelock[sel]` (the target's own timelock), so a long timelock cannot be shortcut; `increaseTimelock(sel, d)` waits `timelock[increaseTimelock]`; both reject the `decreaseTimelock` selector. Pending entries submitted before an increase keep their original `executableAt`, so a sentinel should revoke them. Certora `EarliestTime.spec` proves the earliest execution time never moves backward (01-codebase-report.md > 4.2; notes/A-roles-timelocks.md > 3.4).
- `abdicate(sel)` is timelocked and permanent; there is no un-abdicate; it applies only to timelocked functions. Certora `AbdicatedFunctions.spec` (notes/A-roles-timelocks.md > 3.5).
- Raising a timelock to a huge value makes `submit` overflow and revert, which disables the selector forever (notes/A-roles-timelocks.md > 3.1).
- All timelocks start at zero (NatSpec 187-189). Until raised, the curator can submit and execute in one transaction via `multicall` (01-codebase-report.md > 4.2; notes/A-roles-timelocks.md > 1).
- Timelocked: `setIsAllocator`, the four gate setters, `setAdapterRegistry`, `addAdapter`, `removeAdapter`, `increaseTimelock`, `decreaseTimelock`, `abdicate`, `setPerformanceFee`, `setManagementFee`, both fee recipients, `increaseAbsoluteCap`, `increaseRelativeCap`, `setForceDeallocatePenalty`. Instant: all owner functions, `submit`, `revoke`, cap decreases, all allocator functions, all user functions (01-codebase-report.md > 4.2; notes/A-roles-timelocks.md > 3.6).
- Roles outside the vault: `MorphoVaultV1Adapter.setSkimRecipient` is callable by the vault owner instantly and `skim` sweeps any token except the underlying shares; `MorphoMarketV1AdapterV2` has its own submit/revoke/abdicate timelock driven by the parent vault's curator; gate contracts have their own `roleSetter` and `whitelister` roles that are not timelocked (01-codebase-report.md > 4.1; notes/A-roles-timelocks.md > 2.3).
- Multicall is delegatecall to self only, preserves `msg.sender`, bubbles reverts, not payable. Certora `Immutability.spec` proves every DELEGATECALL targets the vault (notes/D-adapters-security.md > 5 Known pitfalls; notes/A-roles-timelocks.md > 2.2).
- Every path by which assets leave the vault: `withdraw`/`redeem` to receiver, `allocate` to an adapter (also from `enter` when a liquidity adapter is set), `forceDeallocate` (penalty withdrawn to the vault itself), fees (minted shares, not assets), adapter internals, adapter `skim`. The vault never grants token approvals (the only `approve` is the share token's), has no `sweep`, `rescue`, or generic `execute` (01-codebase-report.md > 4.3; notes/A-roles-timelocks.md > 4.1, > 4.2).
- Allocator griefing without timelock: pointing `setLiquidityAdapterAndData` at a non-adapter makes deposits and liquidity-dependent exits revert; `setMaxRate(0)` freezes share price growth; `forceDeallocate` still works as an escape (notes/A-roles-timelocks.md > 4.3).

### 2.2 Accounting (Morpho, all Verified unless stated)

- State: `uint256 public transient firstTotalAssets`, `uint128 _totalAssets`, `uint64 lastUpdate`, `uint64 maxRate` (lines 224-227) (notes/B-accounting.md > 2.1 State).
- `accrueInterestView`: if `firstTotalAssets != 0` return the stored value (once per transaction); `realAssets = asset.balanceOf(vault) + sum of adapters' realAssets()`; `maxTotalAssets = _totalAssets + _totalAssets * elapsed * maxRate / WAD`; `newTotalAssets = min(realAssets, maxTotalAssets)`; `interest = newTotalAssets - _totalAssets` floored at 0 (01-codebase-report.md > 5.1 Total assets; notes/B-accounting.md > 2.2).
- There is no oracle in the vault. Adapters value lending positions with deterministic interest math (`expectedSupplyAssets` in `MorphoMarketV1AdapterV2.sol:251-283`; `previewRedeem` in the V1 adapter). The adapter is fully trusted for both funds and share price (01-codebase-report.md > 5.1; notes/B-accounting.md > 2.3).
- Gains are recognized only up to `maxRate` (per second, WAD, `MAX_MAX_RATE` = 200% APR in `ConstantsLib.sol`, about 0.55% per day). Default is 0, so a new vault recognizes no gains until an allocator sets it. Excess gains stay as an unrecognized buffer that later accruals release; exiting holders do not get their share of it and entering holders buy at a discount (Blackthorn M-5 "delayed yield can be stolen"). Losses are recognized in full and immediately through the same `min`. There is no separate `realizeLoss` in this version (01-codebase-report.md > 5.1; notes/B-accounting.md > 4; notes/D-adapters-security.md > 2.5 item 1).
- Once per transaction: `firstTotalAssets` freezes valuation after the first accrual. This blocks flash-loan share shorting and relative-cap bypass. Cost: a loss created inside a transaction is invisible until the next one (Blackthorn H-1, won't fix; ChainSecurity CS-001, risk accepted). When total assets are 0, `firstTotalAssets` stays 0 so accrual can re-run in the same transaction (01-codebase-report.md > 5.1; notes/B-accounting.md > 2.4).
- Every price-dependent state-changing entry point accrues first: `deposit`, `mint`, `withdraw`, `redeem`, `allocateInternal`, `setMaxRate`, the four fee setters; `forceDeallocate` reaches it through `withdraw`. `deallocate` does not accrue (notes/B-accounting.md > 2.4; notes/D-adapters-security.md > 1.2).
- Per-id `allocation` is not `realAssets`: it only updates on allocate and deallocate, so it lags interest and losses (notes/B-accounting.md > 2.3).
- Virtual shares: `virtualShares = 10 ** max(0, 18 - assetDecimals)` (1e12 for USDC), plus 1 virtual asset; share decimals = `max(18, assetDecimals)`; an empty USDC vault mints 1e18 shares per USDC (notes/B-accounting.md > 3.1).
- Conversion table with `S = totalSupply + pendingFeeShares`, `A = newTotalAssets`, `V = virtualShares`: `previewDeposit = assets * (S + V) / (A + 1)` rounded down; `previewMint = shares * (A + 1) / (S + V)` rounded up; `previewWithdraw = assets * (S + V) / (A + 1)` rounded up; `previewRedeem = shares * (A + 1) / (S + V)` rounded down; `convertToShares`/`convertToAssets` equal `previewDeposit`/`previewRedeem`. `MathLib` has no 512-bit intermediate, hence the liveness requirement that totals stay below about 1e35 (notes/B-accounting.md > 3.1).
- Certora: `ExchangeRate.spec` proves rounding is tight on all four operations and `sharePriceIsIncreasing` except for management fees and loss realization; `RoundTrip.spec` proves no round trip creates value; `PreviewFunctions.spec` proves previews equal executed results and do not revert when the action succeeds; `Invariants.spec` bounds `0 < virtualShares <= 1e18` (notes/B-accounting.md > 3.1; notes/D-adapters-security.md > 4).
- First-depositor inflation: three layers (virtual shares and asset; donations not recognized in the same block because `elapsed = 0`; donations never recognized while `_totalAssets == 0`). Morpho still advises seeding (NatSpec 40-46, Zellic 3.1) because adapter rounding dust can deflate a nearly empty vault (01-codebase-report.md > 5.2; notes/B-accounting.md > 3.2).
- Donations of the base asset count via `balanceOf` but are clamped by `maxRate`; share donations to the V1 adapter with zero allocation are ignored; `MorphoMarketV1AdapterV2` tracks its own `supplyShares` so donated Blue shares are "lost forever" (notes/B-accounting.md > 3.3; notes/D-adapters-security.md > 1.4).
- Fees: `performanceFee` (max 50%, `MAX_PERFORMANCE_FEE = 0.5e18`) on "distributed interest" per accrual; `managementFee` (max 5% per year, per second) on `newTotalAssets` including during losses, so it can lower share price. Both are minted as shares: `feeShares = feeAssets * (totalSupply + V) / (newTotalAssets - perfFee - mgmtFee + 1)`. Setters are timelocked, enforce `fee != 0 => recipient != 0`, and accrue before changing so fees never apply retroactively. If the recipient fails `canReceiveShares`, that period's fee is skipped, not deferred (`lastUpdate` still advances). Fees round down (01-codebase-report.md > 5.3; notes/B-accounting.md > 5.1, > 5.2).
- No high-water mark. The base is the previous `_totalAssets`, which is written down on a loss, so recovering a loss is charged again. `_totalAssets` is flow-adjusted (deposits and withdrawals move it 1:1), so it is a last-value mark, not a peak mark. Morpho's audited "FeeWrapper" is a parent VaultV2 over a child VaultV2 for fees; that code is not in the repo (01-codebase-report.md > 5.3; notes/B-accounting.md > 5.3).
- `totalSupply` storage is stale between accruals; previews add pending fee shares (notes/B-accounting.md > 5.2; notes/C-deposits-withdrawals.md > 2.1).

### 2.3 Deposits and withdrawals (Morpho, all Verified unless stated)

- ERC-4626 surface: `deposit(assets, onBehalf)`, `mint(shares, onBehalf)`, `withdraw(assets, receiver, onBehalf)`, `redeem(shares, receiver, onBehalf)`, plus `forceDeallocate(adapter, data, assets, onBehalf)`. The parameter is named `onBehalf` instead of `owner`; ABI positions match ERC-4626. Also ERC-2612 `permit` (01-codebase-report.md > 6.1; notes/C-deposits-withdrawals.md > 2.1).
- Deposit flow: accrue, preview, then `enter`: `canReceiveShares(onBehalf)`, `canSendAssets(msg.sender)`, `safeTransferFrom`, `createShares`, `_totalAssets += assets`; if a liquidity adapter is set, `allocateInternal` runs and re-checks caps, so a full cap makes deposits revert, and a relative cap below WAD can make big deposits revert because it is computed against the pre-deposit `firstTotalAssets` (Blackthorn M-3) (notes/C-deposits-withdrawals.md > 2.2).
- Exit flow: `canSendShares(onBehalf)`, `canReceiveAssets(receiver)` (the vault itself always passes), pay from idle first, then pull only the shortfall from the single `liquidityAdapter`; if still insufficient the call reverts. No partial fill, no queue, no other fallback. Allowance is spent when `msg.sender != onBehalf`, `type(uint256).max` is infinite (01-codebase-report.md > 6.2; notes/C-deposits-withdrawals.md > 2.3, > 2.4).
- `maxDeposit`, `maxMint`, `maxWithdraw`, `maxRedeem` are `pure` and return 0 because gate calls might revert. ERC-4626 permits underestimation, so this is compliant but useless to integrators (01-codebase-report.md > 6.1; notes/C-deposits-withdrawals.md > 2.5).
- Withdrawal slippage: `withdraw`/`redeem` have no slippage parameter (Blackthorn M-1, resolved by a NatSpec comment that a check must be performed on top) (notes/D-adapters-security.md > 3.2).
- `forceDeallocate`: anyone can call; `deallocateInternal` requires every returned id to have `allocation > 0`; the penalty (`forceDeallocatePenalty[adapter]`, per adapter, timelocked, max 2%, default 0) is charged as `withdraw(penaltyAssets, address(this), onBehalf)` so `onBehalf`'s shares are burned while assets stay in the vault, a donation to remaining holders released subject to `maxRate`; `mulDivUp` on the penalty (Spearbit M 5.2.1 fix); a caller other than `onBehalf` needs share allowance covering the penalty; with a 0% penalty anyone can force-deallocate anyone's adapters for gas only (Spearbit M 5.2.4, acknowledged); the receive-assets gate never blocks it because the receiver is the vault; the adapter sees `selector = forceDeallocate.selector` and the real `sender`; `data` is caller-supplied so the adapter must validate it; optimal amount when illiquid is `min(marketLiquidity, A / (1 + penalty))` (01-codebase-report.md > 6.3; notes/C-deposits-withdrawals.md > 3.1).
- In-kind redemption through a flash loan (`MorphoMarketV1IntegrationIkrTest.sol:63-94`): flash-loan liquidity, supply it to the same market, `forceDeallocate` that amount, `withdraw` it, repay. The user ends up holding the market position directly; no role holder is needed. Certora `canForceDeallocateZero` is a liveness proof for the zero-amount path only (01-codebase-report.md > 6.3; notes/C-deposits-withdrawals.md > 3.2).
- Caps: `mapping(bytes32 id => Caps)` with `absoluteCap` (uint128), `relativeCap` (WAD, max 1e18), `allocation`. Ids are `keccak256(idData)` returned by adapters and can be shared across positions. Increases are timelocked; decreases are instant for curator or sentinel. Defaults are zero, so a curator must raise both before an id can be used; `absoluteCap == 0` blocks any allocation to that id (ChainSecurity CS-016 fix) (01-codebase-report.md > 6.4; notes/C-deposits-withdrawals.md > 4.1).
- Cap enforcement only in `allocateInternal`: `absoluteCap > 0`, `allocation <= absoluteCap`, `relativeCap == WAD or allocation <= firstTotalAssets * relativeCap / WAD` (rounded down). Using `firstTotalAssets` defeats deposit-allocate-withdraw flash loans (`testRelativeCapManipulationProtection`). Caps are never checked on `deallocate`, `withdraw`, `redeem`, or `forceDeallocate`; interest, donations, losses, and withdrawals can push allocation over a relative cap ("relative caps are soft"); `forceDeallocate(..., 0, ...)` is the permissionless way to refresh allocations (notes/C-deposits-withdrawals.md > 4.2, > 4.3).
- Gates (four, addresses timelocked, contracts are `view` and receive only the account): `receiveSharesGate` checked on deposit `onBehalf`, transfer `to`, and fee recipients inside `accrueInterestView`, so a reverting gate bricks every call that accrues including withdrawals; `sendSharesGate` on exit `onBehalf` and transfer `from`, can block exits; `receiveAssetsGate` on exit `receiver`, can block exits, vault always allowed; `sendAssetsGate` on deposit `msg.sender`, deposits only, "cannot block users' funds". A gate contract's internal state is not timelocked (`WhitelistReceiveSharesGate.setIsWhitelisted` is instant); a gate behind a proxy can change logic; gas griefing has the same effect. Certora `Gates.spec` proves blocked accounts never gain or lose shares (01-codebase-report.md > 6.5; notes/C-deposits-withdrawals.md > 5.1 to > 5.3).
- `BluePublicAllocator`: a contract holding the allocator role that lets anyone `reallocate` or `allocateFromIdle` within its own per-vault caps for a penalty paid in the asset directly to the vault; the pattern is "public, pay a penalty, bounded by owner flags" (notes/C-deposits-withdrawals.md > 3.4; notes/D-adapters-security.md > 1.5).

### 2.4 Adapters and security (Morpho, all Verified unless stated)

- `IAdapter`: `allocate(data, assets, selector, sender)` and `deallocate(data, assets, selector, sender)`, both returning `(bytes32[] ids, int256 change)`, plus `realAssets()`. The vault passes `msg.sig` and its own `msg.sender`, so an adapter can tell which entry point and who triggered it. The same `change` is applied to every returned id, so one adapter cannot move value between two ids in one call (notes/D-adapters-security.md > 1.1, > 2.5 item 6).
- Loose adapter spec (NatSpec 70-92): only the vault calls allocate/deallocate; enter and exit markets only inside those calls; return correct non-repeating ids; approve the vault to pull after deallocate; deallocation must always be possible; ignore markets with zero allocation; never re-enter the vault; returned changes must sum to the current position; entry and exit losses must be negligible relative to gas. Liveness: `realAssets` must never revert and deallocate must not revert when the market is liquid (notes/D-adapters-security.md > 1.1; 01-codebase-report.md > 7.1).
- Token flow: on allocate the vault pushes `asset` to the adapter before calling it; on deallocate the vault calls the adapter and then pulls with `safeTransferFrom`, so both shipped adapters grant the vault unlimited approval in their constructors and unlimited approval to their yield source (notes/D-adapters-security.md > 1.2).
- `addAdapter`, `removeAdapter`, `setAdapterRegistry` are timelocked; `removeAdapter` does not check the adapter is empty (Blackthorn M-2, NatSpec advice to keep an exclusive zero-cap id); the "all adapters are in the registry" invariant holds only if the registry is add-only; `RegistryList` is an owner-controlled append-only list; with `adapterRegistry == 0` any adapter can be added (notes/D-adapters-security.md > 1.3, > 7 Q6).
- Both shipped adapters compute `change = freshValue - vault.allocation(id)` from their own accounting and never trust donatable balances; the Blue adapter requires `mintedShares >= assets` to reject manipulated share prices and has `burnShares` (timelocked) to write off a broken market (notes/D-adapters-security.md > 1.4).
- Audits: 15 reports. Critical, High, and Medium findings and their status: Spearbit 2025-05 H 5.1.1 donation side effects (fixed, clamped by maxRate), M 5.2.1 penalty rounding (fixed), M 5.2.3 exchange-rate skew (fixed with decimal offset), M 5.2.4 zero penalty lets anyone deallocate (acknowledged), M 5.2.5 and 5.2.6 loss dodging (superseded by automatic loss realization); Zellic M 3.1 first-deposit via interest truncation (acknowledged, seed the vault); Cantina competition 3 Mediums all in removed code (VICs, `realizeLoss`); Blackthorn 2025-09 H-1 frozen totalAssets lets users dodge bad debt (won't fix), M-1 no withdrawal slippage (comment), M-2 allocate to adapter being removed (comment), M-3 relative cap blocks deposits (comment), M-4 lossy adapter as liquidity adapter lets an attacker loop losses onto others (acknowledged), M-5 delayed yield stolen (acknowledged); ChainSecurity CS-016 Critical fake loss via donated position plus `forceDeallocate(0)` (fixed with zero-cap and zero-allocation checks), CS-001 users escape losses (risk accepted), CS-019, CS-020, CS-002 fixed; Market V1 Adapter V2 reviews no C/H/M (Certora L-02 sandwiching scheduled `burnShares`, acknowledged); fee wrapper none; arbitrary ERC4626 via V1 adapter 4 Mediums all acknowledged and unfixed (no inflation check on allocate, no slippage protection, no balance-delta check, no atomic approvals); gates 1 Low; BluePublicAllocator Blackthorn H-1 exposure exceeds caps under oracle compromise (won't fix), M-1 penalty manipulation (resolved), M-2 bad debt shift (acknowledged), M-3 instant risk-raising settings (acknowledged), M-4 liquidity griefing (acknowledged) (01-codebase-report.md > 7.2; notes/D-adapters-security.md > 3.1, > 3.2).
- Lesson for our Executor: the BPA findings are the class of risk an allocator contract adds; non-timelocked policy knobs let whoever controls it route funds where depositors did not review. Executor policy changes should be timelocked relative to depositors, or only reduce risk instantly (notes/D-adapters-security.md > 3.2, Inferred).
- Certora: 39 specs covering core invariants (`totalSupplyIsSumOfBalances`, `balanceOf(0) == 0`, fee and cap bounds, adapters-in-registry), `TotalAssetsChange` (exact changes per entry point), `TotalAssetsIsUpToDate`, allocation hierarchy, exchange rate and rounding, previews, round trips, entrypoint equivalence, ids and changes, relative caps, earliest time, abdication, immutability, exact revert conditions, liveness (owner, sentinel, forceDeallocate zero, remove market), gates, token balance changes, skim, `Reentrancy.spec` (only external calls go to the trusted set) and `ReentrancyView.spec`. Modeling assumptions: bounded loops, adapter calls summarized, fee-on-transfer and reentrant tokens unsupported, multicall removed and covered by induction (notes/D-adapters-security.md > 4; 01-codebase-report.md > 7.2).
- Pitfalls table: no reentrancy guard (trusted closed call set); rounding always in the vault's favor; inflation handled by decimal offset plus seeding; fee-on-transfer and rebasing tokens unsupported (positive rebases act as donations); donations clamped; oracle dependence none; flash-loan manipulation blocked by `firstTotalAssets`; front-running of predictable losses accepted (CS-001, H-1); allocator can drain idle but `forceDeallocate` remains; gate griefing; zero-penalty griefing; bad adapter protected only by timelock and registry; permit malleability not checked (nonce prevents replay); gas DoS from adapter loops; timelock bypass blocked by exact-calldata keys and target-selector timelock (notes/D-adapters-security.md > 5; 01-codebase-report.md > 7.3).
- Tests: 373 test functions, fuzzed unit and integration tests, no stateful `invariant_` tests. `test/mocks/AdapterMock.sol` (72 lines) is a reference adapter that records `selector` and `sender` and returns `assets + interest - loss` (notes/D-adapters-security.md > 6.1; 01-codebase-report.md > 7.4).
- Invariants worth copying: `totalSupply == sum(balances)` and `balanceOf(0) == 0`; rounding direction on all four operations and no profitable round trip; previews equal results; `totalAssets` changes by exactly the deposited or withdrawn amount and otherwise only through accrual or trades; donations never raise share price in the same transaction; allocation never exceeds caps after a risk-increasing action and zero-cap ids never gain exposure; the emergency role can always reduce risk; timelocked calls never execute early and abdication is permanent; the only external calls go to an allowlisted set; new for us, a depositor can always exit with the platform, Executor, oracle, and DEX offline, `realAssets` never reverts, tracked balances equal actual balances minus donations, per-trade loss bounded by the slippage limit (01-codebase-report.md > 7.4; notes/D-adapters-security.md > 6.2).

## 3. Platform mapping: what the research recommends we borrow and what to avoid

### 3.1 Build approach and license

- Recommended: purpose-built StrategyVault on an MIT base (OpenZeppelin `ERC4626` with `_decimalsOffset() = 12`), re-implementing Morpho's ideas (timelock keyed by calldata, abdication, sentinel, soft caps, once-per-transaction valuation) in our own code. If any Morpho source is copied verbatim, that file must be GPL-2.0-or-later; confirm with counsel (02-platform-mapping.md > 2.2 Build approach; 03-spike-plan.md > 2 Q10).
- Rejected Option A reasons, each of which is a design constraint for us: `maxRate` clamps gains while losses hit instantly; no HWM; no lockup, leader stake, or proportional close; swap adapters make every allocate and deallocate a lossy trade (NatSpec 87-89, Blackthorn M-4); `forceDeallocate` becomes a permissionless forced market sale; an oracle-priced `realAssets()` that reverts blocks every withdrawal (02-platform-mapping.md > 2.2; notes/D-adapters-security.md > 2.5).
- Rejected Option B (Executor as the adapter): mixes policy engine and custody, puts depositor funds in the Executor, conflicts with the brief's model that assets stay in the vault (notes/D-adapters-security.md > 2.3).
- Reuse Morpho's invariant list and Certora rule shapes as the test plan (02-platform-mapping.md > 2.2; notes/D-adapters-security.md > 6.2).

### 3.2 Patterns that transfer directly

- Timelock framework: `submit(data)` / execute-by-anyone / `revoke` / `abdicate`, exact-calldata keys, `decreaseTimelock` gated by the target's own timelock, `increaseTimelock` requiring `d >= current` (notes/A-roles-timelocks.md > 6.2; 02-platform-mapping.md > 2.7).
- Timelocks set in the constructor and never zero, unlike Morpho (02-platform-mapping.md > 2.3).
- Virtual shares 1e12 for USDC plus 1 virtual asset; Morpho's rounding table exactly (deposit and redeem down, mint and withdraw up); lazily computed `totalAssets()` view equal to post-accrual state; previews exact (notes/B-accounting.md > 6.4; 02-platform-mapping.md > 2.4.1).
- Once-per-transaction NAV cached in transient storage like `firstTotalAssets` (02-platform-mapping.md > 2.4.1; notes/B-accounting.md > 6.3 item 8).
- Accrue or settle before any fee or parameter change; fee changes timelocked and capped; rounding against the fee recipient; fee share minting formula `feeAssets * (supply + V) / (assets - fees + 1)` (02-platform-mapping.md > 2.4.5; notes/B-accounting.md > 6.4).
- Risk-only emergency role; caps-to-zero as reduce-only mode; "check after the state change" style from `allocateInternal` (notes/A-roles-timelocks.md > 6.2; 02-platform-mapping.md > 2.1).
- Limits checked on the risk-increasing action only, never on exits, with the denominator frozen at the first touch in the transaction; after an exit pushes the portfolio out of bounds, the Executor is reduce-only until restored (notes/C-deposits-withdrawals.md > 4.4; 02-platform-mapping.md > 2.5.2 step 7).
- Penalty-stays-in-vault accounting for any forced or inconvenient exit path (notes/C-deposits-withdrawals.md > 3.3).
- Deposit-side gating only ("cannot block users' funds"); no exit-side gates at all, so nothing needs abdicating there (notes/C-deposits-withdrawals.md > 5.4; 02-platform-mapping.md > 2.3).
- Multicall as delegatecall to self only (notes/D-adapters-security.md > 5).
- Rich events (`EventsLib.sol` style): every swap with tokens, amounts, oracle prices, NAV before and after; deposit, withdrawal, lock, fee, handover (02-platform-mapping.md > 2.1).
- Add-only registries for tokens, pools, and oracles; abdicate what is final (02-platform-mapping.md > 2.3, > 2.8 Risk 8).
- Adapter-style internal accounting lesson: never trust balances that can be donated; compute change from the contract's own records (notes/D-adapters-security.md > 1.4). Note the research is inconsistent on whether our vault should read live `balanceOf` (02-platform-mapping.md > 2.4.1) or track internal balances (notes/D-adapters-security.md > 5); see section 4.

### 3.3 Patterns to avoid

- `maxRate` smoothing: spot prices move both ways; upside smoothing creates a backlog new depositors capture. Mark to market symmetrically and handle fairness with directional pricing. A rate-style cap remains useful only for fee crystallization and for rejecting absurd NAV jumps (02-platform-mapping.md > 2.4.1; notes/B-accounting.md > 6.3 item 7).
- The adapter abstraction for spot tokens: `forceDeallocate` with caller-chosen `data` becomes a permissionless forced sale and sandwich target; allocation tracking in base units drifts with price (notes/B-accounting.md > 6.1; notes/C-deposits-withdrawals.md > 3.3; notes/D-adapters-security.md > 2.5 item 7).
- Any swap adapter as liquidity adapter (Blackthorn M-4 loss looping) (notes/D-adapters-security.md > 2.5 item 2).
- Exit-side gates and fee accrual coupled to `canReceiveShares` (notes/C-deposits-withdrawals.md > 5.4).
- A valuation that reverts on oracle failure (NatSpec 124 rule that a reverting `realAssets` bricks every exit) (notes/D-adapters-security.md > 2.5 item 3; 02-platform-mapping.md > 2.4.2).
- The agent's ERC-6551 account as vault owner: the buyer could instantly replace the curator and remove the platform sentinel, defeating handover (notes/A-roles-timelocks.md > 6.4).
- Pending actions that survive a role change and never expire (notes/A-roles-timelocks.md > 6.4; 02-platform-mapping.md > 2.3).
- No reentrancy guard: Morpho relies on a closed trusted call set; we call DEX routers, pools, and oracles, so add a guard and allow only hookless pools (01-codebase-report.md > 7.3; notes/D-adapters-security.md > 5).
- Unlimited approvals to yield sources (Spearbit arbitrary-ERC4626 M 5.1.4): use exact approvals reset after each swap and balance-delta checks (notes/D-adapters-security.md > 1.2; 02-platform-mapping.md > 2.1).

### 3.4 Role design proposed for StrategyVault (02-platform-mapping.md > 2.3, Inferred)

- Constants: `MAX_LOCKUP = 7 days`, `NOTICE = 2 days`, `RISK_TIMELOCK = MAX_LOCKUP + NOTICE = 9 days`, `HANDOVER_PERIOD = 3 days`; unpause and reduce-only-off through an admin timelock ("short, e.g. 1 day").
- Depositor: `deposit`, `mint` while deposits are open, not in handover, oracle fresh; `redeem`/`withdraw` (USDC path); `redeemInKind` always. Cannot transfer shares at launch.
- Manager: resolved live from `AgentNFT.ownerOf(agentId)` when `ownershipEpoch == acceptedEpoch`, never stored. Can open or close deposits, toggle `alwaysProportional`, lower the lockup instantly, propose a lockup increase (waits new duration plus `NOTICE`), propose fee changes later (`RISK_TIMELOCK`), own the leader stake, trade only through the Executor. Cannot call `executeSwap`, move assets, change Executor, tokens, pools, or oracles, withdraw the leader stake below 5%, or act during handover.
- Executor: immutable reference, replaceable only by timelock; `executeSwap(params)` with epoch arguments and nothing else; cannot transfer out, approve, deposit, withdraw, act when paused, with stale epochs, or with risk-increasing trades in reduce-only.
- Platform admin (timelocked multisig): propose replacing the Executor, adding a token, oracle, or pool (add-only), changing backstop bounds, appointing or removing the guardian; execute after `RISK_TIMELOCK`; abdicate selectors. Removing a token or pool from the trade allowlist is instant and never affects in-kind redemption of existing balances. Cannot move assets, add exit gates (none exist), shorten a timelock faster than that timelock, or pause withdrawals.
- Guardian (sentinel, separate platform security key): instant `pause()` (no trading, no deposits), `setReduceOnly(true)`, `revoke(pending)`, tighten backstops. Cannot unpause, trade, move assets, block any withdrawal path, or appoint itself. Appointing or removing the guardian waits `RISK_TIMELOCK`, which fixes Morpho's instant sentinel removal.
- Handover (new) owner: only `acceptManagement()` after `HANDOVER_PERIOD` from `AgentNFT.epochStartedAt(agentId)` while holding at least 5%.
- Anyone: execute matured timelocked actions, `poke()` NAV and peak tracking.
- Pending actions store the `ownershipEpoch` at submit time and fail execution if the epoch changed.
- Abdication at launch: abdicate "replace oracle adapter for USDC"; consider abdicating `addToken` once the launch set is final.

### 3.5 Accounting design proposed for StrategyVault (Inferred)

- `NAV = USDC.balanceOf(vault) + sum over allowlisted t of balanceOf_t(vault) * price_t / 10^dec_t`, with `price_t = feed_t/USD ÷ feed_USDC/USD` from Chainlink push feeds; LST price would be `LST/MON × MON/USD` (02-platform-mapping.md > 2.4.1).
- Token list fixed, at most 5, add-only through `RISK_TIMELOCK`; only allowlisted tokens count, so non-allowlisted donations are ignored; a donation of an allowlisted token is a gift (02-platform-mapping.md > 2.4.1).
- Directional NAV: `NAV_buy = NAV × (1 + s)` for deposits, `NAV_sell = NAV × (1 − s)` for the USDC withdrawal path; `s` roughly the feed deviation threshold times the non-USDC share, example 0.25%; the spread stays in the vault (02-platform-mapping.md > 2.4.2). Stronger variant from the accounting note: per-token haircut about the feed deviation threshold, `NAV_low` from `min(oracle, TWAP)` minus haircut for exits and `NAV_high` from `max(oracle, TWAP)` plus haircut for deposits (notes/B-accounting.md > 6.3 item 1).
- Deposit guards: every feed fresher than `MAX_STALENESS` (5 minutes) and within 2% of an allowlisted pool TWAP of at least 30 minutes; otherwise `deposit` reverts and `maxDeposit` returns 0. NAV never uses pool spot. If a pull oracle is ever used, require the price timestamp to be at or after the request time (02-platform-mapping.md > 2.4.2; notes/B-accounting.md > 6.3 items 3 and 6).
- If the spread and lockup prove insufficient against oracle lag, add asynchronous deposits (ERC-7540 style) settling at the next oracle round (02-platform-mapping.md > 2.4.2; notes/B-accounting.md > 6.3 item 5). A small entry or exit fee (0.1% to 0.3%) accruing to the vault is listed as an alternative (notes/B-accounting.md > 6.3 item 4).
- Reject absurd NAV jumps: if NAV moves more than X% since the last accrual, deposits pause (notes/B-accounting.md > 6.3 item 7).
- Leader 5% minimum: invariant `!handover && !windDown => leaderShares × 10000 >= 500 × totalSupply`, checked at the end of any `deposit`/`mint` and any leader `redeem`/`withdraw`/`redeemInKind`, never on other depositors' exits; `maxDeposit` returns `max(0, leaderShares × 20 − totalSupply)` in assets; the leader stake carries the same lockup; `closeVault()` starts wind-down (deposits close, reduce-only) and after `MAX_LOCKUP` the 5% check is lifted (02-platform-mapping.md > 2.4.3).
- Seeding: the leader's 5% seed is required before `depositsOpen` can be set (02-platform-mapping.md > 2.4.2).
- Share transfers disabled at launch (`transfer`/`transferFrom` revert); can be enabled later behind a timelock with rules that move locks and cost basis (02-platform-mapping.md > 2.4.4). The exits note offers a different rule if transfers exist: transfers spend only free shares and the receiver's lock is unaffected, never propagate `unlockAt` (notes/C-deposits-withdrawals.md > 7.3).
- Precision: 18-decimal tokens times prices into 6-decimal USDC; round NAV down for withdrawals and up for deposits (notes/B-accounting.md > 6.2).

### 3.6 Performance fee above a high-water mark (later, Inferred)

- Primary proposal: per-depositor HWM charged on withdrawal. Track `costBasisPerShare[account]` (weighted average entry price updated on each deposit). On exit of `n` shares at price `p` (`NAV_sell` per share for USDC exits; last good stored price for in-kind exits): `profit = max(0, p − basis) × n`; `feeShares = profit × 10% × (supply + V) / (NAV − profit × 10% + 1)`. Fee shares are moved from the exiter to the leader, not minted, so nobody else is diluted. Losses never reset the basis downward. Requires non-transferable shares (02-platform-mapping.md > 2.4.5).
- Alternative: global `hwmPricePerShare` (WAD, on `NAV_low` or mid, never `NAV_high`), crystallized at accrual or on a schedule (weekly and on handover): if `price > hwm`, `gain = (price − hwm) × (supply + V)`, `feeAssets = gain × 10%`, mint `feeShares` to the manager with Morpho's formula, set `hwm` to the post-fee price. Simpler, but a depositor entering during a drawdown rides the recovery fee-free. Add an explicit cap on fee shares per period and crystallize on a conservative NAV and TWAP (notes/B-accounting.md > 7; 02-platform-mapping.md > 2.4.5).
- Guardrails: fee changes timelocked (`RISK_TIMELOCK`) and capped (at most 20% suggested); fees settled before any parameter change; rounding against the recipient; HWM fees crystallize on `NAV_sell` only after the lockup with a per-period fee cap (02-platform-mapping.md > 2.4.2, > 2.4.5).
- On NFT sale, crystallize first so the old owner receives fees earned under their management; with per-depositor fees nothing is owed until exits, so the recipient simply switches with the epoch (02-platform-mapping.md > 2.6 step 5; notes/B-accounting.md > 7).
- Management fee is not in the product spec; Morpho's per-second pattern transfers if ever wanted (notes/B-accounting.md > 7).

### 3.7 Exit design proposed for StrategyVault (Inferred)

- Three exit functions: `redeem(shares, receiver, owner)` / `withdraw(...)` (ERC-4626) plus a safe overload `redeem(shares, receiver, owner, minAssetsOut, deadline)`, paying USDC, depending on a fresh oracle and allowlisted pools only when USDC is insufficient, blocked by lockup, stale oracle, or venue failure (revert only, funds untouched); `redeemInKind(shares, receiver, skipMask)` paying a pro-rata slice of every held token, depending on ERC-20 `transfer` only, blocked by lockup only; optional periphery `ExitZap` that calls `redeemInKind` and swaps in the user's context (02-platform-mapping.md > 2.5.1).
- USDC path: check free shares and deadline; NAV once per transaction with fresh oracle; `owed = shares × NAV_sell / supply` rounded down; `freeUsdc = USDC balance − floor` with `floor = 10% × (NAV − owed)`; if `owed <= freeUsdc` and not `alwaysProportional`, pay USDC and touch nothing; otherwise proportional close: `slice_t = balance_t × shares / supply`, sell each through its allowlisted pool with `minOut_t = slice_t × oraclePrice_t × (1 − maxExitSlippage)` where `maxExitSlippage` is 0.5% plus the pool fee, exact approval reset afterwards, pay USDC slice plus proceeds; require total `>= minAssetsOut` and `block.timestamp <= deadline`; any failing leg reverts the whole call; limits not checked on exit (02-platform-mapping.md > 2.5.2).
- Size guard: a slice larger than about 2% of the pool's liquidity reverts early with `UseInKind()`; with about 5,700 USDC in the v3 WETH pool any WETH slice above roughly 100 USDC would go in-kind, which is the stated reason to launch with USDC plus WMON only (02-platform-mapping.md > 2.5.2).
- `redeemInKind`: burns shares, transfers `floor(balance_t × shares / supply)` of each allowlisted token; makes no oracle, DEX, Executor, AgentNFT, or platform call, with one exception: when the lockup is active and the user claims a handover waiver, the vault reads the NFT epoch inside `try/catch` and a failed call counts as handover; cannot be paused; no setter exists that can disable it; `skipMask` lets the user skip a token whose transfer reverts and forfeits that slice to remaining holders; the user can pick another `receiver`; later fees settle at the last good price; gas bounded by at most 5 tokens; holds WMON not native MON so every leg is an ERC-20 transfer (02-platform-mapping.md > 2.5.3; notes/C-deposits-withdrawals.md > 6.1).
- The in-kind path must use the same `totalSupply` that includes any pending fee shares, so fee accrual must be computable without an oracle or settled at the last good checkpoint (notes/C-deposits-withdrawals.md > 6.1).
- A per-user claimable balance (pull pattern) is the alternative to `skipMask` for an untransferable token (notes/C-deposits-withdrawals.md > 8 Q2; 03-spike-plan.md > 2 Q8).
- `redeemInKind` is the spot-token equivalent of Morpho's in-kind redemption through `forceDeallocate`; it needs no flash loan because the user receives the tokens directly (02-platform-mapping.md > 2.5.3; notes/C-deposits-withdrawals.md > 6.3).

### 3.8 Lockup design proposed for StrategyVault (Inferred)

- State per account: `lockedShares`, `unlockAt`. Global: `lockupDuration` in `[1 day, 7 days]`, constants `MIN_LOCKUP = 1 days`, `MAX_LOCKUP = 7 days` (02-platform-mapping.md > 2.5.4; notes/C-deposits-withdrawals.md > 7.1).
- On deposit: if `now >= unlockAt` then `lockedShares = new`, `unlockAt = now + d`; else `lockedShares += new`, `unlockAt = max(unlockAt, now + d)`. Per-account bucket rather than per-deposit lots for O(1) gas; per-deposit lots would need a bounded ring buffer (02-platform-mapping.md > 2.5.4; notes/C-deposits-withdrawals.md > 7.1).
- Anti-griefing: a deposit `onBehalf` of an account with an active lock reverts; changes to `lockupDuration` never move existing `unlockAt` values; an increase waits new duration plus `NOTICE`, a decrease is instant (02-platform-mapping.md > 2.5.4).
- Free shares `= balance − (now < unlockAt ? lockedShares : 0)`; all exits spend only free shares (02-platform-mapping.md > 2.5.4).
- Lockups are waived in handover, wind-down, and guardian pause (02-platform-mapping.md > 2.5.1, > 2.5.3; notes/C-deposits-withdrawals.md > 7.2).
- ERC-4626: `maxRedeem(owner)` = free shares; `maxWithdraw(owner)` = `previewRedeem(free)` or 0 if the oracle is stale, never reverting; `preview*` ignore lockups; `maxDeposit`/`maxMint` return 0 when deposits are closed, in handover, paused, or the oracle is stale, otherwise the leader-stake headroom (02-platform-mapping.md > 2.5.4; notes/C-deposits-withdrawals.md > 7.4).
- Morpho has no lockup and gates cannot express one because they are `view` and receive only the account (notes/C-deposits-withdrawals.md > 7; notes/D-adapters-security.md > 2.5 item 4).

### 3.9 Handover design proposed for StrategyVault (Inferred)

- Detection: `AgentNFT` increments `ownershipEpoch[agentId]` and records `epochStartedAt[agentId]` on every transfer; the vault stores `acceptedEpoch`; handover is active when they differ, whether or not the transfer went through escrow (02-platform-mapping.md > 2.6).
- Handover mode: depositors can take every exit with lockups waived but cannot deposit; the old owner can exit their former stake freely (no longer bound by 5%) but cannot act as manager, and their pending actions fail the epoch check; the Executor may make reduce-only swaps only when the guardian or its circuit breaker requires, and no swap with a stale epoch; the new owner can only `stakeAsIncomingLeader()` (a deposit exempt from "deposits closed", locked like any other); the guardian keeps pause, reduce-only, revoke (02-platform-mapping.md > 2.6).
- Sequence: escrow settles and the NFT transfers; optional `vault.noteSale()` emits an event only; for `HANDOVER_PERIOD` depositors can leave with no lock; then the new owner calls `acceptManagement()`, which requires at least 5% of supply, sets `acceptedEpoch`, reopens trading, and leaves deposits closed until opened (02-platform-mapping.md > 2.6).
- Open design choice: the escrow could bundle the old leader's shares with the sale through a one-off `transferLeaderStake` callable only by the escrow during handover (02-platform-mapping.md > 2.6; 03-spike-plan.md > 2 Q7).
- Morpho lesson: roles are plain addresses and nothing follows the NFT; pending actions survive a sale, so handover must include revoking all pending entries; removing an allocator is timelocked, so revocation of an old owner's rights must happen at the Executor level (epochs), with sentinel cap-zeroing as the vault-level fast lever (notes/A-roles-timelocks.md > 6.4; notes/D-adapters-security.md > 7 Q8).

### 3.10 Interface sketch given by the research (02-platform-mapping.md > 2.7, Inferred)

- Exits (never pausable): `redeem(shares, receiver, owner, minAssetsOut, deadline) returns (assets)`; `redeemInKind(shares, receiver, skipMask) returns (tokens[], amounts[])`.
- Trading (Executor only): `struct SwapParams { tokenIn; tokenOut; amountIn; minAmountOut; bytes32 poolId; deadline; uint64 ownershipEpoch; uint64 configEpoch; }`; `executeSwap(SwapParams) returns (amountOut)`. The vault builds the router call itself with recipient = vault, exact approval reset to 0, balance-delta checks, an oracle floor (`value out >= value in × (1 − backstopSlippage)`), `trade size <= backstopTradeBps` of NAV, and in reduce-only mode requires `tokenOut == USDC`.
- Manager: `setDepositsOpen(bool)`, `setAlwaysProportional(bool)`, `decreaseLockup(uint32)` (instant, at least 1 day), `submitLockupIncrease(uint32)` (executes after new duration plus `NOTICE`), `closeVault()`, `acceptManagement()`, `stakeAsIncomingLeader(assets) returns (shares)`.
- Governance: `submit(bytes)`, `revoke(bytes)`, `setExecutor(address)` (timelocked), `addToken(token, priceFeed, pool)` (timelocked, add-only), `setBackstops(maxTradeBps, maxAssetBps, minUsdcBps, maxSlippageBps)` (timelocked if loosening), `abdicate(bytes4)`.
- Guardian: `pause()`, `setReduceOnly(bool)` (on instant, off via admin timelock), `tightenBackstops(...)`.
- Views: `navUsdc() returns (nav, fresh)`, `navBreakdown()`, `inHandover()`, `freeShares(account)`, `leaderShareBps()`, `drawdownBps()`, plus `peakNav7d()` named in 02-platform-mapping.md > 2.1.
- `IExecutor.swap(vault, SwapParams, sessionAuth)` enforces the full policy then calls `vault.executeSwap`. `IAgentNFT`: `ownerOf`, `ownershipEpoch`, `epochStartedAt`.
- Split of limits: the vault enforces depositor-protecting backstops (token, pool, and router allowlists; recipient is the vault; oracle floor on every swap; maximum trade size; concentration on risk-increasing trades; reduce-only and pause). The Executor enforces operating policy (trade count, deadlines, oracle-to-pool deviation, circuit breaker, epochs, per-agent configuration). Vault backstops set equal to or slightly looser than Executor limits (12% per trade, 45% per asset, 1% slippage) so a mismatch shows up as an Executor bug rather than a silent loss (02-platform-mapping.md > 2.7).
- Events on every swap carry tokens, amounts, oracle prices, and NAV before and after (02-platform-mapping.md > 2.1).

### 3.11 Ranked risks from the research (02-platform-mapping.md > 2.8, Inferred)

1. Oracle-priced entry and exit lets informed users extract value (Morpho's CS-001 and H-1 made daily). 2. Thin Monad DEX liquidity. 3. Executor or session key compromise. 4. New, unaudited vault code (small immutable contract, ported invariants, external audit, TVL cap, mandatory seed). 5. In-kind exit blocked by a token. 6. Handover edge cases. 7. MEV on Executor swaps and proportional exits (investigate Monad private order flow and Chainlink SVR feeds). 8. Governance abuse by platform admin. 9. LST depeg (deferred with the LST). 10. Fee gaming later. 11. Gas and cost model on Monad. 12. License.

## 6. Gaps and weak spots

- **Venue evidence does not cover either register option.** All liquidity measurements are Uniswap v3; v4 pools were not checked and Kuru is never mentioned. The spike addresses are v3 (02-platform-mapping.md > header; 03-spike-plan.md > 0). The hookless-pools-only guidance (01-codebase-report.md > 7.3) has no equivalent for an orderbook venue. Inference: the proportional-close and `executeSwap` designs assume AMM pool semantics (`poolId`, pool liquidity fraction for the size guard) and will need rework for Kuru.
- **PersonalAccount is not covered.** The register says the Executor executes trades for both PersonalAccount and StrategyVault; the research designs `IExecutor.swap(vault, ...)` for the vault only and never analyzes the personal account (notes/00-brief-and-phase0.md > Part 1; 02-platform-mapping.md > 2.7).
- **The time-scaled reference price band is not designed anywhere.** The research's band is a static 2% against a 30-minute TWAP plus a 5-minute staleness rule (02-platform-mapping.md > 2.4.2). The register's time-scaled band needs its own design and its own test.
- **Oracle parameters are unknown.** Heartbeat and deviation for MON/USD, ETH/USD, USDC/USD and SVR semantics are open (03-spike-plan.md > 2 Q2). Inference: the 5-minute staleness rule and the 0.25% spread example cannot be validated until M-33 runs, and both could be wrong in the direction that blocks the USDC path.
- **USDC/USD feed as a single point of failure.** NAV divides every price by the USDC/USD feed (02-platform-mapping.md > 2.4.1). Inference: this makes deposits and USDC exits depend on a feed for the base currency itself; the research never discusses USDC depeg handling.
- **Internal inconsistency on donations.** 02-platform-mapping.md > 2.4.1 reads live `balanceOf`; notes/D-adapters-security.md > 5 says track internal balances and never raw `balanceOf`; notes/B-accounting.md > 6.4 allows either. One rule must be chosen.
- **Internal inconsistency on fee shares in the in-kind path.** notes/C-deposits-withdrawals.md > 6.1 requires `redeemInKind` to use a supply that includes pending fee shares (Morpho's accrual model), while 02-platform-mapping.md > 2.4.5 proposes per-depositor fees crystallized on exit with no pending shares. Inference: the plan must pick one fee model before the exit math is frozen.
- **Handover waiver depends on `AgentNFT` liveness.** A failed `AgentNFT` call inside `redeemInKind` counts as handover and waives every active lock (02-platform-mapping.md > 2.5.3). Inference: if `AgentNFT` is upgradeable or can be made to revert, all lockups vanish at once; this is fail-safe for depositors but means the lockup guarantee to the manager is only as strong as `AgentNFT`. Also, any NFT transfer (including one the manager makes to their own second address) closes deposits and waives all locks, so handover mode is manager-triggerable at will (02-platform-mapping.md > 2.6).
- **Small USDC exits below the floor become swaps.** With `floor = 10% × (NAV − owed)`, once USDC sits at or under the floor every USDC-path exit, however small, runs the proportional close with one swap per token (02-platform-mapping.md > 2.5.2). Inference: this makes small exits expensive in gas and slippage; a minimum slice size or a rule that pays USDC while the post-exit USDC share does not fall below the pre-exit share is worth considering.
- **Spread example likely too small.** `s` of 0.25% is given as an example while the sizing rule is "feed deviation threshold times the non-USDC share" (02-platform-mapping.md > 2.4.2). Inference: with a 40% single-asset cap and up to 90% non-USDC, a 0.5% or 1% feed deviation implies `s` between 0.45% and 0.9%.
- **No formal verification for our contract.** Morpho ships 39 Certora specs (notes/D-adapters-security.md > 4); the research proposes Foundry invariants only (03-spike-plan.md > 1.11). Inference: decide whether any formal rule (at least the offline exit liveness) is required before external review.
- **Deployment and factory are not designed.** Morpho uses a CREATE2 factory with an `isVaultV2` registry (01-codebase-report.md > 3); the research never says how StrategyVaults are deployed per agent, how `agentId` is bound immutably, or where the platform-wide deposit cap is enforced (02-platform-mapping.md > 2.8 Risk 4).
- **Executor's own governance is thin.** The BPA lesson (timelock loosening, instant tightening) is stated (notes/D-adapters-security.md > 3.2) but the interface sketch only shows the vault's `setBackstops`; the Executor's config-epoch changes have no timelock in the sketch (02-platform-mapping.md > 2.7).
- **Monad gas model unverified.** "Monad is reported to charge by gas limit rather than gas used" is flagged as needing verification and is not reproducible on anvil (02-platform-mapping.md > 2.5.3; 03-spike-plan.md > 2 Q5).
- **Monad mempool and MEV environment unknown.** Sandwich and oracle-update front-running exposure depend on it (03-spike-plan.md > 2 Q4; notes/B-accounting.md > 9 Q2).
- **Audit coverage of roles and timelocks in the notes.** Sub-agent A did not read the audit PDFs for its section (notes/A-roles-timelocks.md > 7 Q8); the audit findings on roles come only from notes/D-adapters-security.md.
- **Public RPC log limits.** `eth_getLogs` is limited to 100 blocks on the public RPC (03-spike-plan.md > 0), which affects the indexer needed for the transparency features (02-platform-mapping.md > 2.1) rather than the vault itself.
- **Unsound as written, small.** The guardian's `pause()` "stops deposits and executeSwap" while `setReduceOnly(true)` still allows the Executor to sell to USDC in handover only "when the guardian or the Executor's own circuit breaker requires it" (02-platform-mapping.md > 2.6, > 2.7). Inference: the interaction between pause (no swaps at all) and a 20% circuit-breaker pause that may want reduce-only selling is not specified; define whether pause forbids all swaps or permits reduce-only.

## 7. Open questions needing a human decision

1. **Is the leader minimum stake (5%) in scope?** Recommended: yes, keep 5%. Reason: the research uses it as the inflation seed, the deposit headroom rule, and the handover acceptance criterion (02-platform-mapping.md > 2.4.2, > 2.4.3, > 2.6).
2. **Share transfers: disable at launch, or keep the register's propagation rule?** Recommended: disable at launch; if enabled later, only free shares transfer and the receiver's lock is untouched. Reason: dust-transfer lock griefing and per-account cost basis (notes/C-deposits-withdrawals.md > 7.3; 02-platform-mapping.md > 2.4.4).
3. **Per-depositor or global high-water mark, and does the leader's own stake pay the fee?** Recommended: per-depositor, crystallized on exit, leader stake exempt. Reason: Hyperliquid parity with no dilution of other depositors, and the stake is the leader's own money (02-platform-mapping.md > 2.4.5; 03-spike-plan.md > 2 Q6; notes/B-accounting.md > 9 Q6).
4. **Does the escrow transfer the old leader's stake to the buyer, or must the buyer post a fresh 5%?** Recommended: fresh stake at launch, with the escrow-only `transferLeaderStake` path as a later addition. Reason: fewer escrow-to-vault couplings in the first audit (02-platform-mapping.md > 2.6; 03-spike-plan.md > 2 Q7).
5. **Untransferable token in `redeemInKind`: `skipMask` forfeit or per-user claimable balance?** Recommended: `skipMask` with documented forfeit semantics at launch. Reason: two launch tokens and minimal state (02-platform-mapping.md > 2.5.3; 03-spike-plan.md > 2 Q8).
6. **Are lockups waived in handover, guardian pause, and wind-down?** Recommended: all three. Reason: those are the moments depositors most need to leave and a waiver only adds exits (notes/C-deposits-withdrawals.md > 7.2; 03-spike-plan.md > 2 Q9).
7. **Should `alwaysProportional` exist, and should toggling it or changing lockups carry a notice period for existing depositors?** Recommended: include the flag as instant with an event; lockup increases already carry new duration plus `NOTICE` and apply to new deposits only. Reason: the flag changes only the withdrawer's own execution and never blocks `redeemInKind` (02-platform-mapping.md > 2.1; 03-spike-plan.md > 2 Q9).
8. **Venue: Uniswap v4 (hookless pools only) or Kuru?** Recommended: decide after M-32 plus a Kuru depth measurement, and keep venue code in a timelock-replaceable module. Reason: no research evidence covers either option and the reentrancy guidance depends on the venue (02-platform-mapping.md > header; notes/D-adapters-security.md > 7 Q7).
9. **Is any Morpho source copied, accepting GPL-2.0-or-later on that file?** Recommended: no copying; re-implement on an MIT base with legal review. Reason: avoids GPL obligations on the stack and derivative-work questions for the Executor (02-platform-mapping.md > 2.2; 03-spike-plan.md > 2 Q10).
10. **Oracle stack: Chainlink push feeds as primary, per-feed staleness, and USDC treated as 1 or via the USDC/USD feed?** Recommended: Chainlink primary, staleness per feed from measured heartbeat, USDC as 1 with a depeg guard that pauses deposits. Reason: a USDC/USD feed outage must not block the USDC path (Inference on top of 02-platform-mapping.md > 2.4.1 and 03-spike-plan.md > 2 Q2).
11. **Circuit breaker: which NAV for the 7-day peak and where does it live?** Recommended: `NAV_sell` tracked in the vault via `poke`, read by the Executor. Reason: the vault holds the authoritative NAV and the backstop must survive Executor compromise (Inference; 03-spike-plan.md > 2 Q13).
12. **Third-party exits: standard ERC-4626 allowance on all exits, including `redeemInKind`?** Recommended: yes, and no other burn path. Reason: the `ExitZap` periphery needs consent-based exits (02-platform-mapping.md > 2.5.1; notes/C-deposits-withdrawals.md > 8 Q9).
13. **Custody core boundary: swap call building inside the vault or in a venue module?** Recommended: venue module called by the core with exact approval and balance-delta verification. Reason: venue undecided and the register asks for a small custody core (Inference; 02-platform-mapping.md > 2.7).
14. **Executor policy loosening: timelocked at `RISK_TIMELOCK`?** Recommended: yes, with tightening instant. Reason: BPA H-1 and M-3 show instant loosening defeats vault timelocks (notes/D-adapters-security.md > 3.2).
15. **Timelock constants: `NOTICE` 2 days, `RISK_TIMELOCK` 9 days, `HANDOVER_PERIOD` 3 days, unpause 1 day?** Recommended: accept as proposed. Reason: they exceed the 7-day maximum lockup with a buffer, satisfying the register (02-platform-mapping.md > 2.3).
16. **Async deposits (ERC-7540 style) as a contingency if M-28 shows the spread and lockup are insufficient?** Recommended: defer, keep as the named fallback. Reason: the register has no withdrawal queue and the research lists async settlement only as a fallback (02-platform-mapping.md > 2.4.2; notes/B-accounting.md > 6.3 item 5).
17. **Where does the platform-wide deposit cap live?** Recommended: per-vault cap plus a platform total in a registry, tightenable instantly, loosened by timelock. Reason: the register says platform-wide and the research never places it (Inference; 02-platform-mapping.md > 2.8 Risk 4).
18. **Formal verification scope before external review?** Recommended: at least a Foundry invariant for offline exit liveness (M-13) and the Morpho-shaped invariants (M-34), with a formal rule for exit liveness if budget allows. Reason: Morpho's assurance rests on 39 Certora specs we will not inherit (notes/D-adapters-security.md > 4).
