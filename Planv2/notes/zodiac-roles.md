How to read this note. It consolidates the eight files under `Planv1/research/zodiac-roles/` (three reports, five notes) for the Planv2 build plan. Citations use the form `file.md > Section heading`; notes files are cited as `notes/X.md > Section`. "Verified" and "Inferred" inside a bullet are the source's own labels. A sentence starting with "Inference:" is my own reasoning and is not in any source. The decision register (own Executor with typed intents, no Zodiac Roles, no Merkle-verified calldata) is treated as binding. ## 1. Coverage and verdict

The research studied the repository `gnosisguild/zodiac-modifier-roles` at `main` commit `820e5bc9` (tag `zodiac-roles-sdk-v4.1.3`) and established that the deployed and audited code line is Roles v2.1.1 on branch `origin/v2` at `218a5164` (mastercopy `0xF2964CE6161ce0e75964Fe7927cE114cb0B283D5`), that `main` is an unaudited refactor that lacks the 2.1.1 fixes, and that an unreleased v3 on `origin/contracts-v3` is BUSL-1.1 and unaudited (`01-codebase-report.md > 1.1 Versions`; `notes/C-admin-deploy-sdk.md > 0. Headline finding`). It covered the contracts (call flow, scoping, condition operators, integrity rules, storage packing, allowances, unwrappers, execution options), the TypeScript SDK 4.1.3 and the app's diff and apply code, the four 2023 audit PDFs (G0 Group April and November, Omniscia May and November), the zodiac-core 3.0.1 dependency, and read-only RPC checks on Monad chain 143 that confirmed the Roles mastercopies, libraries, ModuleProxyFactory, singleton factory, Safe 1.4.1, MultiSend, Uniswap v3 SwapRouter02, USDC and WMON are deployed there with runtime bytecode matching the recorded artifacts (`01-codebase-report.md > 1.4 Monad deployment status`; `notes/C-admin-deploy-sdk.md > 3.3 Monad bytecode verification`). The overall verdict was to reject both Zodiac-based architectures (Option 1, Safe plus Roles; Option 2, Roles in front of our own accounts) and build a purpose-built Executor that accepts typed intents (Option 3) (`02-platform-mapping.md > Recommendation: Option 3`). The reasons given: Roles natively covers only 4 of the 13 launch limits, partially covers 2, and covers none of the 7 value, price or time based ones, so every percentage, oracle, deadline, breaker and epoch rule must be written by us in every option (`02-platform-mapping.md > 2.1 Limit coverage`); Roles' generality over arbitrary calldata is where its worst pitfalls live and typed intents remove that class; Roles has no hook to kill grants atomically with an NFT transfer; ERC-4626 vault invariants would be implemented twice; and the code on `main` diverges from what is deployed while the useful v3 parts are unaudited and BUSL (`02-platform-mapping.md > Recommendation: Option 3`). This matches the register, so the research now serves as a source of permission-model lessons, security findings and test cases rather than as an integration guide.

### Architecture and call flow

- Roles sits between members and an account (avatar). Checks run in this order: `moduleOnly`, role key non-zero, membership, unwrapper lookup, target clearance, execution options, function header, condition tree walk; any failure reverts `ConditionViolation(status, info)` (`01-codebase-report.md > 3.3 Call flow`; `notes/A-permission-model.md > 2.2`).
- Every entry point runs `_authorize` (view checks), then `_flushPrepare` (writes allowance debits to storage), then `exec`, then `_flushCommit` (emit on success, restore balances on failure). v2 has no reentrancy guard; writing the debit before the external call is the reentrancy defense; v3 adds `nonReentrant` with a transient-storage guard and persists consumption only after success (`notes/A-permission-model.md > 2.1 Entry points`; `notes/B-allowances-state.md > 1.6`; `notes/D-security-audits.md > 4. Reentrancy and ordering`).
- Owner is one OZ `OwnableUpgradeable` address with single-step `transferOwnership` and `renounceOwnership`, every setter `onlyOwner`, no built-in delay. The avatar is only read (for `EqualToAvatar`); the target is only called (`execTransactionFromModule[ReturnData]`) (`01-codebase-report.md > 3.2 Roles of each address`; `notes/C-admin-deploy-sdk.md > 1.1 Ownership`, `1.3 Built-in time delay?`, `1.5 setUp, avatar vs target`).
- The owner can grant anyone `allowTarget` with delegatecall, so the Roles owner is effectively a full controller of the target's funds (Inferred in source) (`notes/C-admin-deploy-sdk.md > 1.6 Who is really in control`).
- A Safe is not required. The target must implement only the two `execTransactionFromModule` functions and must itself restrict them to the Roles proxy, because that is the only gate (`01-codebase-report.md > 6.4 Avatar requirements`; `notes/C-admin-deploy-sdk.md > 4. Avatar or target requirements`).

### Permission model: roles, targets, functions, scoping

- A role is a `bytes32` key mapping to `{ members, targets, scopeConfig }`; `scopeConfig` is keyed by `_key(target, selector)` with no code-hash or implementation check (`notes/A-permission-model.md > 1. Actors and storage`; `notes/D-security-audits.md > 7. Target protocol upgrades`).
- Three target clearances: `None` (deny), `Target` (any selector and any params, only execution options checked), `Function` (only selectors with a stored header). A function is either wildcarded (`allowFunction`, no param checks) or scoped (`scopeFunction`, condition tree). Empty calldata is selector `0x00000000`; calldata of 1 to 3 bytes reverts (`01-codebase-report.md > 4.1 Scoping layers`; `notes/A-permission-model.md > 3. Scoping layers`).
- `revokeTarget` does not delete function headers, so a later `scopeTarget` silently restores old function scopes (Verified by `test/Clearance.spec.ts`) (`01-codebase-report.md > 4.1`; `notes/D-security-audits.md > 3. Permissive defaults`).
- `ExecutionOptions { None, Send, DelegateCall, Both }` is stored per target (for `Clearance.Target`) or per function header; there is no role-wide switch, so every grant must individually pass `None` (`01-codebase-report.md > 4.6 Execution options`; `notes/A-permission-model.md > 5. Execution options`).
- Membership is a boolean with no expiry and no epochs; `assignRoles` auto-enables the module and never disables it; `assignRoles(false)` leaves the module enabled with no memberships (`01-codebase-report.md > 5.3`; `notes/C-admin-deploy-sdk.md > 1.2 Owner-only functions`, `7. Notes toward our design`).

### Conditions and operators

- Trees are submitted flat in BFS order as `ConditionFlat { parent, paramType, operator, compValue }`; the root must be `Calldata`; parameter types are `None, Static, Dynamic, Tuple, Array, Calldata, AbiEncoded`; all array elements decode with the first child's type; a nested `Calldata` selector is skipped, not checked (the SDK compensates with `And(Calldata Matches, Dynamic Bitmask(selector))`) (`01-codebase-report.md > 4.2 Parameter types`; `notes/A-permission-model.md > 4.1 Data model`, `4.4 Decoding`).
- Operators: `Pass`, `And`, `Or`, `Nor`, `Matches` (child count must equal payload count, which pins array length), `ArraySome` (bug in 2.1.0 and `main`: only element 0 checked; fixed in 2.1.1), `ArrayEvery` (empty array passes), `ArraySubset` (at most 256 children), `EqualToAvatar` (rewritten at load time to `EqualTo(keccak256(abi.encode(avatar)))`), `EqualTo` (hash comparison; for dynamic values pins length and every byte including padding), `GreaterThan`, `LessThan`, signed variants, `Bitmask` (15-byte window at a byte shift), `Custom` (STATICCALL to `ICustomCondition.check`), `WithinAllowance`, `EtherWithinAllowance`, `CallWithinAllowance` (`01-codebase-report.md > 4.3 Operators`; `notes/A-permission-model.md > 4.2 Operators`, `4.3 Bug found`).
- No operator compares two fields to each other, reads `block.timestamp`, reads a balance or reads a price, other than through `Custom` (`01-codebase-report.md > 4.3`; `notes/B-allowances-state.md > 3.3 Time and deadlines`).
- `Custom` checkers are view-only STATICCALLs that receive `(to, value, data, operation, location, size, 12 bytes extra)`, cannot consume allowances in v2, must be stateless because they cannot know whether the transaction will execute, and any revert inside them reverts the whole authorization (`notes/B-allowances-state.md > 3.1 Custom conditions`; `notes/A-permission-model.md > 4.2`).
- There is no post-execution hook of any kind: after `exec`, only `_flushCommit` runs (`notes/B-allowances-state.md > 3.2 Post-execution hooks`).
- Integrity rules: exactly one root at index 0, BFS order, per-operator type and compValue rules, sibling type compatibility for logical and array nodes, `ArraySome`/`ArrayEvery` exactly one child, `ArraySubset` at most 256 children, allowance counters must be direct children of a `Calldata` node. v2 has no explicit node count or depth cap (practical limits: `uint8` parent index, 16-bit count, max contract code size); v3 adds explicit caps (`notes/A-permission-model.md > 4.5 Integrity rules and limits`).

### State layout and gas

- Condition trees are packed at 2 bytes per node plus 32 bytes per comparison value and deployed as contract bytecode through the singleton factory with salt 0 (`WriteOnce`, SSTORE2-like, runtime prefixed with STOP), so identical trees dedupe to one pointer across all Roles instances; `_load` re-derives the tree and type tree on every call, so gas scales with tree size (`01-codebase-report.md > 4.4 Storage and limits`; `notes/A-permission-model.md > 4.6 Storage`).
- Header word layout: `[2B count][1B options][1B isWildcarded][8B unused][20B pointer]` (`notes/A-permission-model.md > 4.6`).
- No gas measurements are committed anywhere in the repo. Cost drivers from code: three cold SLOADs, one cold `extcodecopy`, linear decode and tree walk, two SLOADs plus one SSTORE per allowance used, then the external call. Estimates (Inferred in source, Ethereum pricing): 25k to 40k overhead for a simple scoped call; 40k to 70k for a Uniswap-style tree with an allowance; the Option 3 Executor was estimated at roughly 60k to 110k overhead for four cold oracle reads, `slot0`, four to eight balance reads and one or two SSTOREs (`01-codebase-report.md > 6.6 Gas`; `notes/C-admin-deploy-sdk.md > 6. Gas`; `02-platform-mapping.md > Option 3`).
- Monad specifics asserted but unconfirmed (Inferred in source): gas charged on gas limit rather than gas used, cold state access repriced upward, anvil does not model this (`notes/C-admin-deploy-sdk.md > 6. Gas`; `03-spike-plan.md > Step 6`).

### Allowances: accrual, refill, consumption

- `Allowance { uint128 refill; uint128 maxRefill; uint64 period; uint128 balance; uint64 timestamp }` lives in one flat `allowances[bytes32]` mapping per instance, not namespaced by role, target or function; only the owner can set them; the public getter returns stored, not accrued, values (`notes/B-allowances-state.md > 1.1 Struct and storage`, `1.2 Who can set allowances`).
- Accrual is discrete and fixed-window: after each whole `period` since the anchor `timestamp`, `balance += refill`, capped at `maxRefill`; partial periods accrue nothing; the anchor advances by whole periods so windows stay aligned to the original anchor; `period = 0` means one-time; there is no rolling window (`01-codebase-report.md > 5.1 Mechanics`; `notes/B-allowances-state.md > 1.3 Accrual math`).
- `setAllowance` defaults: `maxRefill == 0` stores `type(uint128).max`, `timestamp == 0` stores `block.timestamp`; it overwrites the whole struct including balance; a future anchor means no accrual until `timestamp + period`; `refill * elapsedIntervals` is checked `uint128 * uint64` math and can overflow-revert for extreme values (v3 widens to `uint256`) (`notes/B-allowances-state.md > 1.2`, `1.3`).
- Units are unitless counters: raw token units for `WithinAllowance`, wei for `EtherWithinAllowance`, 1 per evaluation for `CallWithinAllowance`; one key cannot sensibly mix tokens of different decimals or prices (`notes/B-allowances-state.md > 1.4 Units`).
- Within one transaction all references to a key accumulate; `Or` keeps only the winning branch's consumption; `Nor` never propagates consumption; batches merge consumptions across inner calls so splitting a trade does not bypass a budget (`notes/B-allowances-state.md > 1.5`; `notes/A-permission-model.md > 8.3`).
- `setAllowance(key, 0, ...)` with `refill > 0` keeps refilling on schedule; zero is not revocation unless `refill` is also zero (`notes/D-security-audits.md > 3.`, `8. Revocation`).
- "20 trades per day" as a fixed window allows up to 40 trades across a window boundary; a strict rolling bound needs a smaller bucket (for example `maxRefill = 10, refill = 1, period = 9600`) at the cost of burst capacity (`notes/B-allowances-state.md > 2.1`; `02-platform-mapping.md > 2.1`).
- A per-trade cap is not an allowance: it is `LessThan` on the amount, per token, raw units; `WithinAllowance` is cumulative (`notes/B-allowances-state.md > 2.2 Max trade size`).
- v3 adds priced allowances through `IPricing` adapters (18-decimal price, consumed amount rounded up), `WithinRatio` (compares two plucked calldata values after pricing, in basis points, cannot see balances or NAV), custom conditions that can return consumptions, and `updateAllowance` that keeps balance and timestamp. No production pricing adapter is on the v3 head (`notes/B-allowances-state.md > 4.1` to `4.5`).

### Batches, unwrappers, multicall

- Unwrappers are registered per `(to, selector)` and are global to all roles; each inner transaction is checked exactly like a direct call and allowances accumulate across the batch; unwrapping is one level only; the outer delegatecall itself is trusted; `MultiSendUnwrapper` ignores its `to` argument, so registering it for anything but a genuine MultiSend is dangerous (`01-codebase-report.md > 4.7 Batches`; `notes/A-permission-model.md > 8.1`, `8.2`).
- A delegatecall to MultiSend with no unwrapper is an ordinary call and is denied by default; if the owner grants delegatecall on the MultiSend address, the whole batch executes unchecked in the avatar's context (`notes/A-permission-model.md > 8.4`).
- Router `multicall(bytes[])` counts as one call for `CallWithinAllowance` unless the tree descends into each element; whether that works was not tested (`notes/B-allowances-state.md > 2.1`; `03-spike-plan.md > 2. Open questions`, Q16).

### Recipient binding and Uniswap specifics

- `EqualToAvatar` on the `recipient` field is a full 32-byte word comparison against the modifier's `avatar` storage variable, resolved at load time, so `setAvatar` silently changes the meaning of every recipient condition across all roles (`notes/A-permission-model.md > 6.1 Mechanism`; `notes/C-admin-deploy-sdk.md > 1.5`).
- SwapRouter02 `exactInputSingle` (selector `0x04e45aaf`, present in the router bytecode on Monad) has no deadline field; deadlines exist only through `multicall(uint256 deadline, bytes[])`; `exactInput`'s packed `path` can be safely constrained only by `Or` of exact `EqualTo` paths because `Bitmask` cannot bind path length; Universal Router `execute` is constrainable in v2 only for one fixed command shape (`01-codebase-report.md > 4.5`, `5.3`; `notes/A-permission-model.md > 6.2`, `6.3`, `6.4`).
- Router side doors named in the research: recipient constants `address(1)` (msg.sender) and `address(2)` (router), `sweepToken`, `unwrapWETH9`, `refundETH`, `pull`, `multicall`; token functions `transfer`, `transferFrom`, `permit`, `increaseAllowance` (`notes/D-security-audits.md > 6. Safe-specific pitfalls`; `notes/A-permission-model.md > 6.2`).
- Exact-amount approvals cannot be bound to the swap amount across two calls in v2 or v3 because each call is evaluated independently; leftover router approvals are usable only by calls from the account itself (Inferred in source) but remain usable by the member through any permitted router function (`02-platform-mapping.md > 2.1`; `notes/A-permission-model.md > 6.5`; `notes/D-security-audits.md > 6.`).
- Uniswap V3 pool callbacks go to the router, not the account; calling a pool directly from the account would hit a fallback that does not implement the callback and revert (Inferred in source) (`notes/D-security-audits.md > 6.`).

### Administration, deployment, SDK

- Mastercopies are CREATE2 through the singleton factory with salt 0 and constructed inert with `(0x1, 0x1, 0x1)`; instances are EIP-1167 proxies from `ModuleProxyFactory.deployModule(masterCopy, setUp(owner, avatar, target), saltNonce)` initialized atomically, address deterministic from those inputs (`01-codebase-report.md > 6.3 Deployment`; `notes/C-admin-deploy-sdk.md > 3.1 Mechanism`).
- v2 has no batch setter; changes across separate transactions are not atomic, so a partially applied update is live immediately; the app applies revocations before grants (`notes/C-admin-deploy-sdk.md > 2.1 Onchain granularity`).
- SDK v4 removed the plan/diff/apply API; the replacement is the closed `@zodiac-os/sdk` (needs a Zodiac org and API key) and an inlined app copy that reads Gnosis Guild's Subsquid indexer, with no Monad indexing; only the chain-agnostic authoring parts (`c.*`, `processPermissions`, `flattenCondition`, `targetIntegrity`, `rolesAbi`, `encodeKey`) would have been usable (`01-codebase-report.md > 6.2`, `6.5`; `notes/C-admin-deploy-sdk.md > 2.2`, `2.3`, `5. SDK`).
- Licensing (`fetchLicense` against `app.zodiac.eco`) gates nothing on chain; it gates SDK CoW swap app-data fees (25 bps partner fee without an Enterprise plan) and the app's apply flow (`notes/C-admin-deploy-sdk.md > 5.1 Licensing`).
- No Uniswap preset or permission library exists in the repo; DeFi Kit is external with unknown Monad coverage (`01-codebase-report.md > 6.5`; `notes/C-admin-deploy-sdk.md > 5.2 Presets / Uniswap`).
- Layering a delay: owner = OZ `TimelockController` gives a real delay; owner = Safe plus a Zodiac Delay modifier is a real delay only if Safe owners cannot bypass it; the product needs an owner contract with an instant tightening path and a delayed loosening path (Inferred in source) (`notes/C-admin-deploy-sdk.md > 1.4 Layering a delay or timelock`).

### Audit findings

- G0 Group, April 2023 (all contracts): 4 Medium, 1 Minor: allowance conditions were undecidable during evaluation because the allowance was checked after the call so an `Or` branch could not backtrack (this is why consumption is now computed during the walk and flushed before exec); `setAllowance` should ensure `maxBalance >= balance`; the implicit 65,536 condition limit from header packing should be enforced in Integrity; the first node must be the only root; `_arraySubset` assumes at most 256 children. All fixed (`notes/D-security-audits.md > 1. Audit summaries > Audit01`).
- Omniscia, May 2023 (17 files): 2 Medium (XOR operator returned Ok only when exactly one child passed, removed; `Topology` assumed root at index 0 while Integrity allowed it elsewhere), 2 Minor (weak child-count and compValue validation), 27 Informational of which 13 acknowledged and not fixed, including an unchecked `uint32` cast in `WriteOnce` and no zero-address sanitization (`notes/D-security-audits.md > Audit02`).
- Omniscia, November 2023 (delta only, `AllowanceTracker` explicitly out of scope): 3 Medium: `AbiEncoded` inline handling differed between Packer and Topology; removing the `balance <= maxBalance` check made accrual reset high balances down, fixed by the `maxRefill` refactor with the side effect that periods elapsed while balance is at or above the cap are never credited later (`notes/D-security-audits.md > Audit03`).
- G0 Group, November 2023: 1 Minor (custom condition lacked the `operation` argument), fixed at `a19c0ebd` (`notes/D-security-audits.md > Audit04`).
- Three real bugs in the audited 2.1.0 code, missed by all four audits, fixed in 2.1.1: `ArraySome` checked only element 0 (fail-closed alone, fail-open under `Nor`); `Bitmask` on dynamic values counted ABI padding; zodiac-core `SignatureChecker` accepted an ERC-1271 signer that reverts with the magic value as revert data (`notes/D-security-audits.md > 0. Headline findings`; `notes/C-admin-deploy-sdk.md > 0.`).
- Not audited: the 2.1.1 fixes, `MorphoBundler3Unwrapper`, the MultiSendUnwrapper loop-bound change (#448), the whole `main` refactor (which also deleted the decoder's adversarial out-of-bounds tests), and all of v3 (`01-codebase-report.md > 7.1 Audits`; `notes/D-security-audits.md > Audit coverage vs today's code`).

### Known pitfalls beyond the above

- Signed (relayed) module transactions carry only a salt: no deadline, no nonce ordering; a signed-but-unsent transaction is valid until used, invalidated, or the signer loses membership; the default-role path is keyed by `msg.sender` so it does not work for relayed transactions; v3 keeps the no-deadline property (`notes/C-admin-deploy-sdk.md > 4.1 Signed (relayed) module transactions`; `notes/D-security-audits.md > 5.`; `notes/A-permission-model.md > 2.1`).
- Reentrancy edge case: if a reentrant inner call consumes the same allowance and succeeds while the outer call returns `success == false` without reverting, the outer `_flushCommit` erases the inner consumption; exploitation requires a module to reenter (`notes/D-security-audits.md > 4.`).
- Dirty high bits: `EqualTo` and `LessThan` fail closed, `GreaterThan` passes; matters only for targets that mask rather than revert on sub-256-bit types. The decoder has no canonicality checks; trailing calldata is ignored; parameters not described in the tree are never inspected; a wrong type tree checks the wrong bytes (`notes/D-security-audits.md > 2. Calldata encoding tricks`).
- Revocation is a plain storage write, effective for later transactions in the same block, and can be front-run on a public mempool (`notes/D-security-audits.md > 8. Revocation`).
- Allowing the avatar or the Roles modifier itself as a target lets a member re-enable modules or rewrite permissions; delegatecall to `SignTypedMessageLib` lets a member mint ERC-1271 approvals (Permit2, CoW orders) that move funds outside Roles' view (`notes/D-security-audits.md > 6.`).
- Worst case under a tight Uniswap scope with no oracle check: sandwich, attacker-seeded thin pool at an unpinned fee tier, or flash manipulation takes nearly all of each `amountIn`; with 10% trades and 20 per day the account can be drained within one day of trading; with an oracle-based min-out at 0.5% and the 0.05% fee tier, loss through churn is about 1.1% of the account per day, which the 10% breaker catches only after many days (Inferred arithmetic in source) (`notes/D-security-audits.md > 9. Worst case`; `01-codebase-report.md > 7.2 Issues and pitfalls`).
- Allowance griefing: a shared key can be exhausted by one role, blocking others; this is authorized use and cannot be prevented by Roles (`notes/D-security-audits.md > 9.`).
- What Roles cannot prevent in any configuration: loss from pool fees and permitted slippage, MEV within the allowed band, DoS of shared allowances, front-running of a revocation, the behaviour of an upgraded target, and oracle or custom-checker failure (`notes/D-security-audits.md > 9.`).

## 3. Lessons that transfer to our own Executor

Each bullet takes one register limit, states what the research found, and states the lesson for the Executor.

- **Max 10% of account value per trade.** Roles can only cap `amountIn` by a constant per token in raw units; a percentage of NAV needs balances and prices, which no operator reads (`notes/B-allowances-state.md > 2.2 Max trade size`, `5. Requirements for the percentage-based limits`). Lesson: the Executor computes NAV pre-trade from account balances and oracle prices and rejects when `value(amountIn)` exceeds 10% of NAV (`02-platform-mapping.md > Intent and checks`, step 6). Inference: expose the percentage as a view so the tools server reads it, as the register requires.

- **Max 40% in any non-USDC asset, at least 10% USDC.** These are post-trade holdings versus NAV; Roles has no post-execution hook, and a pre-trade projection is unsound because actual output above min-out can push the projection past the cap (`notes/B-allowances-state.md > 3.2`, `5.`, `7. Open questions` Q6). Lesson: check holdings after the swap in the same transaction (`02-platform-mapping.md > Intent and checks`, step 10), and always allow reduce-only trades toward USDC so that a price move cannot strand the account above the cap with no legal trade (`02-platform-mapping.md > 2.6 Risks`, row 5).

- **Max 0.5% slippage.** `amountOutMinimum` can only be compared to a constant in v2; v3 `WithinRatio` compares two calldata values after pricing but cannot see balances (`02-platform-mapping.md > 2.1`; `notes/B-allowances-state.md > 4.4 WithinRatio`). Lesson: require `minAmountOut >= amountIn * pIn / pOut * (1 - 0.5%)` with decimals normalized, and post-check that NAV fell by no more than `value(amountIn) * 0.5%` plus the pool fee (`02-platform-mapping.md > Intent and checks`, steps 7 and 10). Without a price-based min-out, a compromised key can lose close to 100% of each trade's `amountIn` (`notes/D-security-audits.md > 0. Headline findings`, item 4). Pin the fee tier or pool: an unpinned tier lets an attacker seed a thin pool at an absurd price (`notes/D-security-audits.md > 9.`). Inference: the register's 2% oracle-to-pool tolerance means the effective per-leg bound is not 0.5% but up to 0.5% plus the permitted 2% oracle gap when the oracle reads high relative to the pool; the research's 1.1% per day figure assumes an accurate oracle.

- **Rolling 20 trades per 24 hours.** Roles' `CallWithinAllowance` is a fixed anchored window that allows 40 trades around a boundary; the research's own design keeps a ring buffer of the last 20 trade timestamps and requires the oldest to be more than 24 hours old (`notes/B-allowances-state.md > 2.1`; `02-platform-mapping.md > Intent and checks`, step 8). Lesson: count per evaluation, not per transaction, so a batch of N intents counts N (`notes/A-permission-model.md > 8.3`); update counters only after a successful swap, or debit before the external call and restore on failure, and never leave a path where a reentrant consumption can be erased (`notes/B-allowances-state.md > 1.6`; `notes/D-security-audits.md > 4.`).

- **2-minute deadlines.** No Roles operator reads `block.timestamp`; the router's own `checkDeadline` enforces `block.timestamp <= deadline` but not that the deadline is short; SwapRouter02 `exactInputSingle` has no deadline field at all (`notes/B-allowances-state.md > 3.3 Time and deadlines`). Lesson: the Executor enforces `block.timestamp <= deadline <= block.timestamp + 120` on the intent itself (`02-platform-mapping.md > Intent and checks`, step 4). If intents are ever signed by the session key and relayed, the deadline must be inside the signed payload, because a salt-only signature stays valid until used (`notes/D-security-audits.md > 5.`; `notes/C-admin-deploy-sdk.md > 4.1`).

- **Oracle price under 5 minutes old and within 2% of pool price.** Custom checkers can read feeds, `slot0` and `block.timestamp`, but core Roles has no staleness logic; v3's `ChainlinkPricing` checks `updatedAt` age and `answer > 0` but has no `answeredInRound` or sequencer-uptime check; `ConsensusPricing` compares each source to the mean (so a 2% pairwise gap with two sources needs `maxDeviationBps = 100`) and uses a TWAP not spot; `UniswapPricing` works only on V3 pools with `observe()`, not Uniswap v4 singleton pools (`notes/B-allowances-state.md > 3.1`, `4.6`). Lesson: define "pool price" precisely (spot of the pool actually traded versus TWAP; pairwise versus mean), fail closed on a missing, stale, zero or reverting feed, and treat the oracle module as a trusted dependency that gets its own audit attention (`notes/D-security-audits.md > 3.`, row `Custom`; `02-platform-mapping.md > 2.6 Risks`, row 1).

- **Circuit breaker: 10% reduce-only, 20% pause, from 7-day peak.** Needs persistent NAV history; Roles custom checkers are stateless and view-only (`02-platform-mapping.md > 2.1`; `notes/B-allowances-state.md > 5.`). Lesson: the Executor keeps 7 daily max buckets and updates them after each trade; in reduce-only mode `tokenOut` must be USDC; the pause is lifted only by the owner (`02-platform-mapping.md > Launch policy`, `Intent and checks`, steps 2 and 11). Inference: for PersonalAccount, deposits and withdrawals change NAV without any trade, so the peak must be per-share or flow-adjusted; the research specifies "max-NAV-per-share" only in the vault context.

- **Recipient always the source account.** Roles binds recipient with `EqualToAvatar`, which is resolved at load time from a mutable `avatar` variable that `setAvatar` can flip for every condition at once (`notes/A-permission-model.md > 6.1`; `notes/C-admin-deploy-sdk.md > 1.5`). Lesson: the account passes `recipient = address(this)` itself and the Executor post-checks that the tokenOut delta landed in the account; no admin setter may exist that changes the binding (`02-platform-mapping.md > What we borrow from Roles`). Exclude the router recipient constants `address(1)` and `address(2)` and never expose `sweepToken`, `unwrapWETH9`, `refundETH`, `pull` or `multicall` (`notes/D-security-audits.md > 6.`).

- **Exact approvals only, reset to zero in one transaction.** Roles can pin `spender` and bound `amount` but cannot tie the approval to the swap amount or require a reset (`02-platform-mapping.md > 2.1`; `notes/A-permission-model.md > 6.5 Token allowlists`). Lesson: `forceApprove(router, amountIn)`, swap, `approve(router, 0)` in one call, then post-check `allowance(account, router) == 0` (`02-platform-mapping.md > Intent and checks`, steps 9 and 10; `03-spike-plan.md > Step 3`, assertion on allowance). Inference: the approval must be issued by the account that holds the tokens on the Executor's instruction; the register's phrase "the Executor approves" should be read that way, otherwise the Executor would have to custody funds, which contradicts "recipient always the source account".

- **Allowed assets and venue; no delegatecall, no arbitrary calls, no native value.** Roles does these natively with deny-by-default target and selector tables and `ExecutionOptions.None` on every grant (`02-platform-mapping.md > 2.1`). Lesson: a typed intent has no target, selector, operation or value field, so these limits become structural: the only reachable code paths are the registered adapters; use WMON rather than native MON so no call ever needs value (`notes/A-permission-model.md > 5.`; `02-platform-mapping.md > Option 3`). Keep the ProtocolRegistry deny-by-default and record something stronger than an address, since Roles' address-plus-selector keying keeps passing after a proxy upgrade (`notes/D-security-audits.md > 7.`).

- **Epochs, and old permissions never returning.** Roles has no epochs; the only emulation is a fresh role key per `(agent, ownerEpoch, configEpoch)` plus explicit revocation on every transfer, and stale function scopes revive when a target is re-scoped (`02-platform-mapping.md > 2.4 Epochs, transfers and tiers`; `notes/C-admin-deploy-sdk.md > 7.`). Lesson: bump `ownerEpoch` inside `AgentNFT._update` so every existing grant dies in the same transaction as the transfer with no keeper; require exact epoch equality on every call; because epochs are monotonic, a returning NFT never revives a grant; the owner-withdraw path must not depend on any of this (`02-platform-mapping.md > 2.4`, `2.5`). Test mint, burn, transfer, safeTransfer and escrow paths (`02-platform-mapping.md > 2.6 Risks`, row 6).

- **Session keys.** v2 membership is a boolean; v3 packs `start | end | usesLeft` with automatic revoke at zero uses, which the research calls directly useful for session-key expiry (`notes/B-allowances-state.md > 4.7`; `01-codebase-report.md > 5.4`). Lesson: a grant `{ sessionKey, ownerEpoch, configEpoch, validUntil, usesLeft }` written only by the current NFT owner, checked with `msg.sender == grant.sessionKey` (`02-platform-mapping.md > 2.3 Contracts`, `Intent and checks`, step 1). Prefer direct `msg.sender` over relayed signatures, because signed module transactions have no deadline (`notes/C-admin-deploy-sdk.md > 4.1`).

- **Rate-limit state and budgets.** Roles allowance keys are global and shared, so one role can grief another, and "set to zero" is not revocation (`notes/D-security-audits.md > 3.`, `9.`). Lesson: key counters by account so no agent can consume another's budget. The research also recommends a daily turnover budget on `amountIn` "set well below the per-day tolerable loss", since a count cap and a per-trade cap do not by themselves bound daily churn (`notes/D-security-audits.md > 9.`; `02-platform-mapping.md > What we borrow from Roles`, "Daily turnover budgets"). Inference: 20 trades at 10% of NAV permits about 200% of NAV in churn per day under the register as written.

- **Admin power.** The Roles owner is a full controller and there is no delay (`notes/C-admin-deploy-sdk.md > 1.6`). Lesson: loosening goes through a timelock with owner-visible events, tightening is instant, the platform guardian can only tighten (pause an agent, a venue, or all trading), and single-step ownership transfer is a foot-gun that locks admin forever on a typo (`02-platform-mapping.md > 2.4`, `2.6 Risks`, row 7; `notes/C-admin-deploy-sdk.md > 1.1`, `1.4`).

- **Batches.** Every inner call must face the same checks and share cumulative budgets; unwrap only one level; never grant the batching primitive itself (`notes/A-permission-model.md > 8. Batched calls and unwrappers`). Lesson: at launch avoid batching entirely (`notes/A-permission-model.md > 8.5`, recommendation); if batched intents are ever added, count and budget per intent, and reject the whole batch on the first failure.

- **How conditions are evaluated against calldata.** Roles decodes calldata with standard ABI offsets, has no canonicality checks, ignores trailing bytes, and inspects only the parameters the tree describes (`notes/D-security-audits.md > 2.`). Lesson: typed intents decoded by Solidity remove this class; the ArraySome, Bitmask padding and dirty-bits findings are all consequences of hand-decoding untyped bytes (Inference). Any future `bytes` field in an intent is where this class returns.

- **What cannot be expressed on chain and needs an oracle or off-chain check.** Percentages of NAV, slippage against a price, deadlines against `block.timestamp`, oracle freshness and deviation, and the circuit breaker all need price reads and state (`02-platform-mapping.md > 2.1`, summary line). Only the oracle dependency itself cannot be removed; the research's mitigation list is freshness plus pool deviation on every trade, fail closed on missing feeds, and a second source for vault deposits and withdrawals (`02-platform-mapping.md > 2.6 Risks`, row 1).

- **Content-addressed policy sets.** `WriteOnce` stores each distinct tree once and references it by CREATE2 pointer, and `EqualToAvatar` keeps blobs account-independent (`notes/A-permission-model.md > 4.6`; `notes/C-admin-deploy-sdk.md > 3.5`). Lesson: store policy sets by hash and map tiers and equipped skills to hashes so new parameter sets need no redeploy; new action types need a new audited adapter registered through the timelock (`02-platform-mapping.md > 2.4`, "Tiers and skills without redeploying").

Reasons the research gave against Zodiac, verbatim (`02-platform-mapping.md > Recommendation: Option 3`):

1. "Roles covers only the easy half of our limits (allowlists, recipient, no delegatecall). Those are trivial to hard-code when the account builds its own calldata. The hard half (percentages, oracle, slippage, deadline, circuit breaker, epochs, post-trade checks) must be written by us in every option."
2. "Roles' generality is a liability for us: its most serious pitfalls (wildcards, `allowTarget`, router side doors, delegatecall grants, stale scopes after `revokeTarget`, the owner being a full controller) only exist because it accepts arbitrary calldata. Typed intents remove that class of bugs."
3. "Epochs must invalidate grants atomically with NFT transfers, including transfers on outside marketplaces later. Roles has no hook for that; our own Executor reads epochs on every call."
4. "ERC-4626 vault safety needs vault-level invariants anyway. With Roles in front, we would implement them twice."
5. "Roles' code base on `main` diverges from what is deployed and audited, and the parts that would help (v3 pricing, memberships) are unaudited and BUSL."

Reasons the research recorded in Zodiac's favor: a battle-tested audited core, deployed and byte-verified on Monad with nothing left to deploy but proxies, native allowlists, recipient binding, no-delegatecall, and cheap per-account proxies sharing condition blobs (`02-platform-mapping.md > Option 1`, Security row; `notes/C-admin-deploy-sdk.md > 3.3`, `3.5`). The cost the research attached to Option 3: "moves all enforcement into unaudited new code", mitigated by keeping the Executor small and non-generic, porting Roles' adversarial tests, formal invariants (balance deltas, allowance zero, no value), two independent audits, a bug bounty, and low launch caps (`02-platform-mapping.md > 2.6 Risks`, row 3).

## 6. Gaps and weak spots

- **No oracle has been identified on Monad.** Every percentage, slippage, deviation and breaker rule depends on one, and the research left provider, heartbeat and deviation thresholds open (`03-spike-plan.md > 2. Open questions`, Q1; `notes/B-allowances-state.md > 7.`, Q2; `02-platform-mapping.md > 2.6 Risks`, row 1, "confirm feed availability on Monad before build").
- **The venue is undecided and only v3 SwapRouter02 was analyzed.** The research's verified addresses, `slot0` pool-price read, fee-tier pinning, side-door list and Uniswap V3 `observe()` TWAP all assume v3; Universal Router and v4 were judged impractical to scope and v4 singleton pools are unsupported by the pricing adapter; Kuru is not mentioned anywhere (`notes/A-permission-model.md > 6.4`; `notes/B-allowances-state.md > 4.6`, `7.`, Q1; `03-spike-plan.md > 2. Open questions`, Q2). Inference: an orderbook venue has no pool spot price in the `slot0` sense, so "within 2% of pool price" needs a new definition there.
- **Pool liquidity depth was never checked** for any pair or tier; fee-tier pinning and slippage realism depend on it (`01-codebase-report.md > 1.4`; `03-spike-plan.md > 2. Open questions`, Q2).
- **The daily loss bound is weaker than the limits suggest.** With oracle min-out the research bounds churn loss at about 1.1% of the account per day, and the 10% breaker reacts only after many days of that; with a 2% oracle-to-pool tolerance the per-leg bound is looser still (Inference) (`notes/D-security-audits.md > 9.`). The register has no turnover cap to close this.
- **Post-trade caps can strand the account** after a price move unless reduce-only trades are always allowed; the register does not say so (`02-platform-mapping.md > 2.6 Risks`, row 5).
- **Circuit-breaker peak for PersonalAccount is undefined** once owner deposits and withdrawals move NAV without trades (Inference; the research specifies per-share only for the vault, `02-platform-mapping.md > Launch policy`).
- **StrategyVault "owner review" after a 20% pause has no decided authority** (`03-spike-plan.md > 2. Open questions`, Q13), and vault share-price attacks (same-block trade and deposit, donation, inflation) are only listed as mitigations, not designed (`02-platform-mapping.md > 2.6 Risks`, row 4).
- **Whether PersonalAccount funds travel with the NFT** is undecided; the research's escrow flow depends on it (`03-spike-plan.md > 2. Open questions`, Q12; `02-platform-mapping.md > 2.4`).
- **Monad execution properties are all unconfirmed:** gas charged on limit and repriced cold access (`notes/C-admin-deploy-sdk.md > 6.`), mempool visibility and private transaction paths for revocation races and sandwiches (`03-spike-plan.md > 2. Open questions`, Q10), EIP-1153 support (Q11), contract code size limit (`notes/A-permission-model.md > 10.`, item 5).
- **Privy policy capabilities on chain 143 are untested** (`03-spike-plan.md > 2. Open questions`, Q14).
- **All enforcement now lives in unaudited new code.** The research is explicit that Option 3 "moves all enforcement into unaudited new code" and that the price, NAV, deadline, epoch and breaker logic needs a full audit in every option (`02-platform-mapping.md > 2.6 Risks`, row 3; `02-platform-mapping.md > Option 3`, Audit burden row).
- **The register's approval wording is ambiguous.** "The Executor approves the exact amount" cannot be literal if the account holds the tokens and is always the recipient; the research's design has the account approve on the Executor's instruction (`02-platform-mapping.md > Intent and checks`, step 9). Inference: the plan must say which contract calls `approve`.
- **No testnet (10143) addresses exist in the research** for USDC, WMON, any venue or any oracle; only mainnet 143 was verified (Inference from `01-codebase-report.md > 1.4` and `03-spike-plan.md > Step 6`).
- **Signed-intent path is unspecified.** The research shows that signed module transactions have no deadline (`notes/D-security-audits.md > 5.`); the register says session keys "must be designed" but does not say whether the key submits directly or signs for a relayer.

## 7. Open questions needing a human decision

1. **Which venue at launch: Uniswap v3 SwapRouter02 (verified on Monad), Uniswap v4, or Kuru?** Recommended: pick the venue that has a direct onchain spot price read and verifiable USDC/WMON depth, and treat v3 SwapRouter02 as the only option the research has de-risked. Reason: every verified address, the deviation check and the side-door analysis apply only to v3 (`01-codebase-report.md > 1.4`; `notes/A-permission-model.md > 6.4`).
2. **Which oracle provider for MON/USD (and USDC/USD) on Monad, and is it push or pull?** Recommended: a pull-style or sub-5-minute-heartbeat feed, with fail-closed behaviour and a `answer > 0`, `updatedAt` age and round check. Reason: the 5-minute freshness rule is unmeetable with a long-heartbeat push feed (`03-spike-plan.md > 2. Open questions`, Q1; `notes/B-allowances-state.md > 4.6`).
3. **Add a rolling daily turnover cap as a fraction of NAV?** Recommended: yes, value to be chosen by the team. Reason: 20 trades at 10% permits about 200% NAV churn per day and the research bounds churn loss only through a turnover budget (`notes/D-security-audits.md > 9.`).
4. **Exempt reduce-only trades from the 40% and 10% post-checks?** Recommended: yes, any trade with `tokenOut == USDC` passes those two checks. Reason: otherwise a price move can strand the account with no legal trade (`02-platform-mapping.md > 2.6 Risks`, row 5).
5. **Who lifts a 20% pause on a StrategyVault?** Recommended: the agent owner, with depositor `withdraw` and `redeem` open at all times and the guardian able only to pause. Reason: the research flags this as a product and legal decision for third-party funds (`03-spike-plan.md > 2. Open questions`, Q13).
6. **Do PersonalAccount funds travel with the NFT on sale?** Recommended: sweep to the seller before transfer by default, with the listing allowed to declare otherwise and escrow enforcing it. Reason: the research's safe default is that the listing declares it (`02-platform-mapping.md > 2.4`, "Agent sale through our escrow").
7. **Does the session key submit directly (`msg.sender`) or sign intents for a relayer?** Recommended: direct submission at launch. Reason: relayed signatures have no built-in deadline unless it is inside the signed payload (`notes/D-security-audits.md > 5.`; `notes/C-admin-deploy-sdk.md > 4.1`).
8. **Do rate-limit counters and the 7-day peak persist across epoch bumps?** Recommended: yes, keyed by account and never reset on transfer. Reason: otherwise a transfer refreshes the budget (Inference; global-key griefing in `notes/D-security-audits.md > 3.`).
9. **What exactly is "pool price"?** Recommended: spot price of the pool being traded, pairwise deviation of at most 2% from the oracle. Reason: consensus-to-mean and TWAP semantics differ materially (`notes/B-allowances-state.md > 4.6`).
10. **Is the 0.5% slippage bound measured against the oracle or against the pool quote?** Recommended: against the oracle, plus the post-trade NAV-loss bound. Reason: that is the only version that bounds a compromised key's loss (`notes/D-security-audits.md > 9.`; `02-platform-mapping.md > Intent and checks`, steps 7 and 10).
11. **Should loosening of PolicyRegistry or ProtocolRegistry go through a timelock, with the guardian able only to tighten?** Recommended: yes. Reason: the Roles research's central admin lesson is that an owner with instant loosening power is a full controller of funds (`notes/C-admin-deploy-sdk.md > 1.6`; `02-platform-mapping.md > 2.6 Risks`, row 7).
12. **Which contract calls `approve`: the account or the Executor?** Recommended: the account, on the Executor's instruction, with the Executor post-checking `allowance == 0`. Reason: the Executor must never custody funds (Inference from the register's "recipient always the source account"; design in `02-platform-mapping.md > Intent and checks`, step 9).
13. **Allow batched intents at launch?** Recommended: no. Reason: the research recommends avoiding batching entirely and every batch lesson is about cumulative counting and smuggling (`notes/A-permission-model.md > 8.5`).
14. **How is the circuit-breaker peak measured for PersonalAccount when owners deposit and withdraw?** Recommended: per-share or flow-adjusted NAV. Reason: raw NAV would trip the breaker on a withdrawal (Inference; per-share is specified only for the vault in `02-platform-mapping.md > Launch policy`).
15. **Should ProtocolRegistry pin a code hash or require immutable venues?** Recommended: yes, fail closed on mismatch. Reason: address-plus-selector keying keeps passing after a proxy upgrade (`notes/D-security-audits.md > 7.`).
16. **Which testnet (10143) addresses will be used for USDC, WMON, the venue and the oracle?** Recommended: verify by RPC the same way the research verified mainnet before any testnet run. Reason: none exist in the research (Inference from `01-codebase-report.md > 1.4`).
