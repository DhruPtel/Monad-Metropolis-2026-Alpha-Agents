# monad-agent-kit research: working notes

Sources read in full: `01-codebase-report.md`, `02-platform-mapping.md`, `03-spike-plan.md`, `notes/00-phase0-orientation.md`, `notes/A-mcp-structure.md`, `notes/B-tools-transactions.md`, `notes/C-data-reliability-security.md`, all under `Planv1/research/monad-agent-kit/`. Citations are written as `file.md > Section heading`. The labels "Verified" and "Inferred" are carried over exactly as the sources used them. "Inference" marks my own reasoning in this note. Nothing here was checked against the network, the kit repo, or the chain; only the seven files were read.

## 1. Coverage and verdict

The research examined `stakeme-team/monad-agent-kit` at commit `b0f0a09`, package version 0.1.0, by reading only: nothing was installed or run, `.env` and `.keystore/` were not opened, and the hosted server the kit points at could not be reached because a safe-browsing filter on the research network blocks the domain (`01-codebase-report.md > 1. Versions, license, maintenance, summary`; `notes/00-phase0-orientation.md > The most important structural finding`). The repo is about 1,700 lines of TypeScript (ESM, Node 20, run through `tsx` with no build step), depends on `viem` 2.47.18 and `@ai-sdk/mcp` 1.0.36 with `ai` 4.3.19, has one contributor, eight commits all on 2026-04-28, zero stars, no releases, no issues, and no `LICENSE` file although the README claims MIT; the same org publishes near-identical kits for other chains, so this looks like a template instance (`01-codebase-report.md > 1. Versions, license, maintenance, summary`). The decisive finding is that the repo is a client-side starter kit, not an MCP server: every chain tool lives on a closed-source hosted server at `api.monad.exploreme.pro/mcp`, and the repo's own code only generates and stores a wallet key, signs any unsigned transaction JSON it is given, tries and fails to stop Claude Code from reading `.env`, and auto-signs `prepare_*` results in the Vercel AI SDK flow (`01-codebase-report.md > 1. Versions, license, maintenance, summary`). The verdict: there is no server code to fork or trim, the hosted tool surface is the opposite of our intent model (prepare, sign and broadcast primitives with no policy), the client code is probably broken as shipped, and the license is ambiguous, so the research recommends writing our own server with the official MCP TypeScript SDK and viem on the platform side and borrowing only four patterns: keep prepare separate from sign with the signer in an isolated process, reach the server through one line of client config, script multistep flows as skills, and never rely on filtering what an agent may do inside a box that holds secrets (`02-platform-mapping.md > Headline`; `02-platform-mapping.md > 2.2 Build approach`; `01-codebase-report.md > 5.5 What is worth keeping as a pattern`). The decision register already adopts that recommendation, so the remaining value of this research is the tool design, the intent flow, the identity and metering design, the security lessons, and the spike plan.

## 2. Facts the final plan must carry

### MCP structure

- The kit registers no MCP tools and does not depend on `@modelcontextprotocol/sdk`. `getMCPTools()` returns `client.tools()`, so the remote server decides every name, description and input schema at runtime and the client has no local types (Verified). `01-codebase-report.md > 3.2 Tool registration and schemas`; `notes/A-mcp-structure.md > 2. Tool registration, schemas, descriptions`.
- Transport declarations disagree inside the kit: `.mcp.json` says Streamable HTTP, Codex uses stdio through an unpinned `npx mcp-remote`, and `src/mcp-client.ts` asks for legacy SSE. The MCP spec revision 2025-03-26 replaced HTTP+SSE with Streamable HTTP (one endpoint, POST returning JSON or an SSE-framed stream, optional GET for server-initiated messages, optional `Mcp-Session-Id` header); later revisions keep only Streamable HTTP and stdio. Streamable HTTP is the right transport for our server (Verified configs, Inferred spec). `01-codebase-report.md > 3.1 Transports`; `notes/A-mcp-structure.md > 1. How the MCP connection is built`.
- Sessions: `Mcp-Session-Id` is a server-issued correlation ID visible to the client, and the spec warns against treating it as authentication. Session state must be keyed to the authenticated principal, and a session ID presented with a different principal must be rejected (Inferred). `notes/A-mcp-structure.md > 4. Authentication, sessions, caller identity`.
- Error shape in the kit is unstructured: no client code reads `isError`; a signing failure is returned as a successful tool result with ad hoc `_signingError` and `_note` fields; `getEnv()` calls `process.exit(1)` inside a tool path; thrown tool errors are uncaught and probably abort the whole `generateText` call in `ai` 4.x (Verified, Inferred for the abort). `01-codebase-report.md > 3.3 Errors`; `notes/A-mcp-structure.md > 3. How errors reach the agent`.
- Recommended error shape for our server: `isError: true` plus typed `structuredContent` carrying a stable `code`, `message`, `retryable`, and for intents a policy detail, with the error schema included in `outputSchema` as a union (Inferred recommendation). `notes/A-mcp-structure.md > 3. How errors reach the agent`; `02-platform-mapping.md > 2.4 Tool design`.
- Authentication and identity: the kit has none. No config or client code sets a header, token or `authProvider`. The wallet address reaches the model through the system prompt or by reading `.env`, and goes back to the server as a model-supplied `from` argument. That is the pattern to avoid: identity supplied by the model as a parameter (Verified). `01-codebase-report.md > 3.4 Authentication, sessions, identity`; `notes/A-mcp-structure.md > 4. Authentication, sessions, caller identity`.
- The client library `@ai-sdk/mcp` accepts a `headers` map and supports OAuth 2.1 with PKCE through an `authProvider` (it depends on `pkce-challenge`); the kit uses neither (Verified dependency, Inferred meaning). `notes/A-mcp-structure.md > 4. Authentication, sessions, caller identity`.
- Per-client tool control: none in the kit. Every listed tool reaches the model; the dangerous `generate_disposable_test_wallet` is kept out by prose only. For our tiers the server must filter `tools/list` by the authenticated tier and also reject `tools/call` for tools outside the tier; the simplest way is one server instance per authenticated session, or a tier check in a shared handler wrapper (Verified kit, Inferred recommendation). `01-codebase-report.md > 3.5 Per-client tool control`; `notes/A-mcp-structure.md > 5. Enabling or disabling tools per client`.
- Official SDK pattern to use: `registerTool` with a zod `inputSchema`, an `outputSchema`, and a handler that returns both `content` text and `structuredContent`; identity is read from `extra.authInfo` (populated by `requireBearerAuth`), never from arguments. The SDK validates `structuredContent` against `outputSchema` and advertises both schemas in `tools/list`. Exact field names must be checked against the pinned SDK version (Inferred; the example is illustrative and not from the kit). `01-codebase-report.md > 3.2 Tool registration and schemas`; `notes/A-mcp-structure.md > 2. Tool registration, schemas, descriptions`.
- Two likely defects in the kit: the bridge only `JSON.parse`s strings while `@ai-sdk/mcp` returns a `CallToolResult` object, so the AI SDK demos probably cannot sign as shipped; and the lockfile pairs `ai` 4.3.19 (provider 1.x) with `@ai-sdk/mcp` 1.0.36 (provider 3.x), whose tool shapes differ (Inferred, would need a run). `01-codebase-report.md > 3.7 Two likely defects`; `notes/A-mcp-structure.md > 2. Tool registration, schemas, descriptions`.
- How Hermes reads MCP servers, per the research's earlier work: a YAML `mcp_servers` map with stdio entries (`command`, `args`, `env`) and HTTP entries (`url`, `headers`), per-server tool include and exclude lists, and a headless mode. Key names are Inferred and must be checked against the pinned Hermes version. `notes/A-mcp-structure.md > 6. How Hermes would connect`; `01-codebase-report.md > 3.6 How Hermes would connect`.

### Tools and transactions

- The five sources of the tool list disagree: README lists 15, `CLAUDE.md` 17, skills and examples add `get_transaction_receipt`, `PREPARE_TOOLS` in the bridge adds `prepare_erc721_transfer`, `prepare_erc1155_transfer`, `prepare_token_approval` and `prepare_contract_write`, and `docs/ARCHITECTURE.md` mentions faucet tools that exist in sibling kits, which points at a shared server codebase (Verified lists, Inferred existence on the server). `notes/B-tools-transactions.md > 1.1 Sources and discrepancies`; `01-codebase-report.md > 4.1 Tool inventory`.
- Read tools: `get_balance`, `get_token_balance`, `list_evm_blocks` (arg `limit`), `get_evm_block_by_height`, `read_evm_contract` (args `address`, `abi`, `functionName`), `get_evm_compiler_versions`, `list_erc20_tokens`, `get_erc20_token_by_address`, `get_erc721_token_by_address`, `explorer_search`, `get_account_by_address`, `wait_for_transaction`, `get_transaction_receipt`, plus the local `get_wallet_address` added by the bridge. `notes/B-tools-transactions.md > 1.2 Grouped list`.
- Prepare tools return unsigned transaction JSON: `prepare_native_transfer` (args `from`, `to`, `amount` in human units such as "0.001"), `prepare_erc20_transfer`, `prepare_transaction` (arbitrary `to` and `data`; no `to` means contract creation), and the four bridge-only names. Send and write tools: `broadcast_signed_raw_transaction` (arg `serializedTransaction`), `verify_evm_contract_standard_json`, and `generate_disposable_test_wallet`, which returns a private key into model context. `notes/B-tools-transactions.md > 1.2 Grouped list`; `01-codebase-report.md > 4.1 Tool inventory`.
- Transaction path: the server prepares; a local process signs (`sign-tx.ts`, the socket daemon, or the AI SDK bridge); the model passes the signed hex back to the server to broadcast and then polls `wait_for_transaction` and `get_transaction_receipt`. `01-codebase-report.md > 2. Architecture`; `01-codebase-report.md > 4.2 Transaction path, end to end`; `notes/B-tools-transactions.md > 2.2 Flow (a)`; `notes/B-tools-transactions.md > 2.3 Flow (b)`.
- What the signer does, triplicated in three files: copy `to`, `value`, `data`, `gas` or `gasLimit`, `gasPrice`, `maxFeePerGas`, `maxPriorityFeePerGas`, `nonce`, `chainId` into viem `account.signTransaction`, nothing else. No chain ID pin (a missing `chainId` on a legacy transaction likely yields a pre-EIP-155 signature valid on any chain, Inferred), no `from` check, no destination allowlist, no value cap, no calldata or selector inspection, a missing `to` is signed as a deployment, and `type`, `accessList`, `authorizationList` are dropped (Verified by absence). `notes/B-tools-transactions.md > 2.1 Common local parsing`; `notes/C-data-reliability-security.md > 4. Input validation and transaction integrity`.
- Nothing binds the signed transaction to what was prepared. In the Claude Code flow the model writes the JSON it pipes into the signer; in the AI SDK flow the bridge signs whatever the server returned without comparing it to the model's arguments. A compromised server, or an overridden `MONAD_MCP_URL`, could substitute `approve(attacker, max)` (Verified code, Inferred exploit). `notes/B-tools-transactions.md > 2.2 Flow (a)`; `notes/B-tools-transactions.md > 2.3 Flow (b)`; `notes/C-data-reliability-security.md > 4. Input validation and transaction integrity`.
- Signer daemon: auto mode is the default; `--manual` gives a y/n prompt that labels every call with a `to` as "TRANSFER" (approvals included) and shows only the first 20 hex characters of calldata. It supports only `sign_transaction` and `get_address`, with no `signMessage` or `signTypedData`, so Permit2 or EIP-712 flows are impossible through it (Verified). `notes/B-tools-transactions.md > 2.4 signer-daemon.ts auto vs manual`.
- Chain handling: the client has no `viem/chains` import, no chain ID constant, no RPC URL and no token addresses; the network is chosen only by the MCP URL. The chain IDs 143 (mainnet) and 10143 (testnet) do not appear anywhere in the repo; the research states them as Inferred. `notes/B-tools-transactions.md > 4. Tokens, decimals, chain config, network selection`; `01-codebase-report.md > 4.3 Protocols and chain handling`; `03-spike-plan.md > (intro)`.
- Decimals: never handled by the client. `prepare_native_transfer` takes a human amount, so the server converts (Inferred); for `prepare_erc20_transfer` it is unknown whether the server looks up decimals. `formatValue` assumes 18 decimals and uses `Number(wei) / 1e18`, which loses precision (Verified). `notes/B-tools-transactions.md > 4. Tokens, decimals, chain config, network selection`.
- Gas and nonce: copied from the server's JSON; no local estimation, no nonce tracking (two prepares before a broadcast would collide and a stale nonce is not detected), no deadlines (a signed transaction stays valid until its nonce is used), no retry, replacement or stuck-transaction handling (Verified absence). `notes/B-tools-transactions.md > 5. Gas, nonces, deadlines`; `01-codebase-report.md > 4.3 Protocols and chain handling`.
- Monad-specific behaviour the research states: Monad charges gas on the gas limit, so over-estimation costs real MON (Inferred concern, not verified), and Monad "differs in some RPC methods", which may stop Anvil from forking it correctly (marked verify). `notes/B-tools-transactions.md > Open questions` item 6; `03-spike-plan.md > Step 2`. The research contains no facts on priority fees, block time, finality, mempool behaviour, or any specific RPC endpoint; the grep results in `notes/B-tools-transactions.md > 5. Gas, nonces, deadlines` and `notes/C-data-reliability-security.md > 1. How the kit reads balances, prices, and protocol state` show the kit has none, and no other file supplies them.
- Protocol coverage: a repo-wide grep for `uniswap|kuru|swap|quote|stake|lend|router|oracle|deadline|decimals` finds nothing except the org name. No swaps, quotes, oracles, pool prices, staking, lending, wrap or unwrap, or portfolio valuation (Verified). `notes/B-tools-transactions.md > 3. Protocols and actions supported`; `01-codebase-report.md > 4.3 Protocols and chain handling`.
- Key exposure: in secure mode with the daemon in Docker (`network_mode: none`, keystore read-only) no code path returns the key, but anything gets signed; in simple mode (the default) the key sits in `.env`, readable by any process the agent starts, and in the AI SDK flow it is loaded into the agent's own process. Docker secure mode across containers probably does not work because the socket volume is not mounted by the `dev` service (Verified, Inferred for the volume). `notes/B-tools-transactions.md > 2.5 Can the private key reach the agent?`; `notes/B-tools-transactions.md > 2.6 Everything that can sign or send`; `notes/C-data-reliability-security.md > 6. Secrets handling and guard.sh`.
- If any kit-style signer were ever kept (for example for an operating wallet), the research's minimum is: chain ID pinned to Monad mainnet, `from` asserted, destination allowlist of the Executor only, a value cap, a selector allowlist, and rejection of contract creation. `notes/B-tools-transactions.md > 6. Adapt or remove`.

### Data reliability

- The repo reads no chain data itself; viem is used only for key generation and signing. Every read goes through the hosted server, which probably wraps STAKEME's explorer indexer plus a node RPC, so balances and token metadata may carry indexer lag. Freshness, block tag and RPC provider are undocumented (Verified absence, Inferred server internals). `notes/C-data-reliability-security.md > 1. How the kit reads balances, prices, and protocol state`; `01-codebase-report.md > 5.1 Data sources and external services`.
- External services contacted: the hosted MCP endpoint (anonymous, third party, sees every address, query, prepared and signed transaction), the npm registry (unpinned `npx mcp-remote` fetched at every cold start), the Anthropic and OpenAI APIs (AI SDK flow only), Docker Hub and Alpine mirrors at build time. No Monad RPC anywhere. `notes/C-data-reliability-security.md > 2. External services contacted`; `01-codebase-report.md > 5.1 Data sources and external services`.
- Reliability handling: none. A grep for `retry|timeout|setTimeout|backoff|rate.?limit|429` finds only a doc line about `mcp-remote` timeouts. Socket calls have no timeout or size limit; concurrent manual approvals can consume the wrong "y"; a missing env var exits the process; there are no staleness fields anywhere (Verified). `notes/C-data-reliability-security.md > 3. Reliability`; `01-codebase-report.md > 5.2 Reliability`.
- Requirements the research derives for us: timeouts on every upstream call, retries with backoff, idempotency keys so a retried intent cannot double-execute, freshness metadata (block, timestamp, oracle age) on every typed output, two RPC providers, and `STALE_DATA` and `UPSTREAM_UNAVAILABLE` errors carrying `retryable`. `notes/C-data-reliability-security.md > 3. Reliability`; `02-platform-mapping.md > 2.8 Risks, ranked` (risk 7).
- Price sources: none exist in the kit, and the research names no oracle provider, price API, indexer or RPC provider on Monad and no rate limits for any of them. Everything our read tools need (oracle age, pool price, the 2% deviation check, remaining limits) must be built against our own RPC and contracts. `notes/C-data-reliability-security.md > 1. How the kit reads balances, prices, and protocol state`; `03-spike-plan.md > Open questions` item 11; `notes/C-data-reliability-security.md > Open questions` item 7.
- Caching: platform-side placement allows one shared price and quote cache for all agents, which cuts paid calls; each metered call should record `cacheHit` so the price table can be tuned. `02-platform-mapping.md > 2.3 Where the server runs`; `02-platform-mapping.md > 2.6 Identity, tiers, and metering`.
- Lookalike tokens: there is no symbol-to-address registry, so a "USDC" returned by `list_erc20_tokens` or `explorer_search` is indistinguishable from the real one. Our allowlist must be by address, exposed as an enum in schemas, policy and the Executor (Verified absence). `notes/C-data-reliability-security.md > 4. Input validation and transaction integrity`; `01-codebase-report.md > 5.3 Input validation, injection, secrets`.

### Security

- Signer signs anything: severity High as a design requirement. Our signer must sign only Executor calls rebuilt from a validated intent, with the chain ID pinned. `01-codebase-report.md > 5.4 Security table` item 1; `notes/C-data-reliability-security.md > 7. Security table` item 5.
- Automatic signing of every `prepare_*` result: intent tools must never return a signable blob or calldata. `01-codebase-report.md > 5.4 Security table` item 2; `notes/C-data-reliability-security.md > 7. Security table` item 6.
- Generic call, approve, transfer and broadcast tools must not exist in our server; the Executor makes exact approvals internally. `01-codebase-report.md > 5.4 Security table` item 3; `notes/C-data-reliability-security.md > 7. Security table` item 8.
- Identity must come from the authenticated connection, never from a parameter or the system prompt. `01-codebase-report.md > 5.4 Security table` item 4.
- A third-party MCP server sees all activity, has no auth and no SLA: privacy, front-running and availability risk. Do not depend on it even for reads. `01-codebase-report.md > 5.4 Security table` item 6; `02-platform-mapping.md > 2.2 Build approach`.
- Prompt injection through chain strings: token names, symbols and URIs, contract names and verified source, `read_evm_contract` string returns, transaction input data and logs all reach the model unfiltered, and anyone can deploy a token whose name carries instructions. Mitigation: return enums and numbers, never free-text chain strings; cap length; strip control and bidi characters; use our own registry so the narrator never sees raw on-chain names; store `reason` as data and never render it as instructions. `notes/C-data-reliability-security.md > 5. Prompt injection through tool outputs`; `01-codebase-report.md > 5.4 Security table` item 8; `02-platform-mapping.md > 2.8 Risks, ranked` (risk 5).
- Server-substituted transaction goes undetected in the kit. For us: any external quote or router API that builds calldata must be decoded and checked against the intent before signing. `01-codebase-report.md > 5.4 Security table` item 9; `02-platform-mapping.md > 2.5 Intent flow`.
- Human approval UI lesson: the daemon shows "TRANSFER to 0xToken, value 0" for an `approve(attacker, max)` call. Any approval screen we build (tier upgrades, withdrawals) must decode calldata and show token, amount, spender and simulated balance changes. `notes/C-data-reliability-security.md > 6. Secrets handling and guard.sh`; `01-codebase-report.md > 5.4 Security table` item 11.
- The guard hook is a no-op: `'$TOOL_INPUT'` is single-quoted so the script always receives a literal string; Claude Code delivers hook input as JSON on stdin; the matcher covers only Bash, so Read and Grep are never checked; `security-test.ts` tests the script directly, so its 26/26 result is misleading. Even a working regex denylist is bypassable (`tac .env`, `cut`, globs, `/proc/self/environ`, allowlist prefix abuse) and has false positives (`cat .env.example`, any command containing "od" before ".env"). Lesson: keep secrets out of the sandbox entirely and test the real integration, not the script. `notes/C-data-reliability-security.md > 6. Secrets handling and guard.sh`; `01-codebase-report.md > 5.3 Input validation, injection, secrets`; `01-codebase-report.md > 5.4 Security table` item 13.
- Shell injection: the skills tell the model to run `echo '<json>' | make sign` with server-returned JSON; a single quote in any field breaks out of the quoting. We never pipe tool output through a shell. `notes/C-data-reliability-security.md > 4. Input validation and transaction integrity`; `01-codebase-report.md > 5.3 Input validation, injection, secrets`.
- Docker: the `dev` service receives `.env` as environment variables and the "network none" signer mounts the whole repo. This reinforces E2B header injection so that no credential is present in the sandbox environment. `notes/C-data-reliability-security.md > 7. Security table` item 20.
- Keystore and socket weaknesses (scrypt N=8192, 32 times weaker than geth's default; plaintext password file; unauthenticated socket in `/tmp`; chmod race; key passed on the CLI in `import`) are not applicable to our custody model. `notes/C-data-reliability-security.md > 6. Secrets handling and guard.sh`; `01-codebase-report.md > 5.4 Security table` items 15 and 17.
- Calldata versus intents: the kit hands raw unsigned transactions to the model, which our design deliberately avoids; tools return intent IDs and the Executor call is built server side from the stored intent. `notes/A-mcp-structure.md > 2. Tool registration, schemas, descriptions`; `notes/B-tools-transactions.md > 6. Adapt or remove`; `02-platform-mapping.md > 2.5 Intent flow`.
- Patterns worth keeping: prepare and sign separation with the key in a network-isolated process; one remote MCP endpoint reached with one line of config; read tool naming and granularity (`get_balance`, `get_token_balance`, `wait_for_transaction`, `get_transaction_receipt` folded into intent status); skill files that script multistep flows. `01-codebase-report.md > 5.5 What is worth keeping as a pattern`; `02-platform-mapping.md > 2.2 Build approach`.

## 3. Platform mapping: what the research recommends we build

### 3.1 Shape of the server

- Stack: `@modelcontextprotocol/sdk` (TypeScript) with Streamable HTTP, `outputSchema` and `structuredContent` on every tool; viem for reads and for building Executor calldata server side; zod schemas shared between the MCP tool schemas, the policy engine and the intent store; Postgres for intents, a limits cache and the metering ledger; a job queue for the intent pipeline; our own Monad RPC provider or providers plus an oracle provider as the metered upstreams. `02-platform-mapping.md > 2.2 Build approach`.
- Placement: platform side as a shared multi-tenant service; the sandbox holds only the server URL. Reasons: the agent cannot tamper with code, policy or data; identity comes from a credential the sandbox never sees; all upstream credentials stay on the platform; egress allows exactly one host plus the model API; metering is recorded where the paid call happens; one shared price and quote cache; one network hop per call (tens of milliseconds in the same region, Inferred); blast radius mitigated with tenant isolation, tests and rate limits; deploy once with the tool schema version pinned per agent config epoch. `02-platform-mapping.md > 2.3 Where the server runs`.
- Spike layout: `server/` (SDK plus viem plus zod, Streamable HTTP), `policy/` (pure functions `checkQuick()` and `checkFull()`), `fixtures/` (agent records, token keys, Executor stub address), `hermes/` (two configs), `tests/` (scripted MCP client checks). `03-spike-plan.md > (intro)`.
- Server skeleton: an Express app with `StreamableHTTPServerTransport` on `/mcp`, behind an auth middleware that verifies a JWT (HS256 acceptable for the spike) and sets `req.auth = { agentId, tier, accounts }`; one `McpServer` per session registering the tools for that tier. `03-spike-plan.md > Step 1`.
- Hermes config shape in the sandbox: one HTTP entry, URL only, no headers, and a per-server `include` list mirroring the tier; E2B injects `Authorization` at egress. Key names must be verified against the pinned Hermes version. `03-spike-plan.md > Step 1`; `notes/A-mcp-structure.md > 6. How Hermes would connect`.

### 3.2 Tool conventions

- Identity is implicit: no tool accepts an address, agent ID or account address. Account selection is `account: "personal" or "vault"`, resolved on the server from the session. `02-platform-mapping.md > 2.4 Tool design`.
- Assets are an enum: launch set `"USDC"` and `"WMON"`, each mapped server side to a fixed address and decimals; no free-text symbol field anywhere. `02-platform-mapping.md > 2.4 Tool design`.
- Amounts are decimal strings in token units (for example `"125.5"`), validated by regex and a maximum number of decimals; outputs carry both `amount` (decimal string) and `amountRaw` (base-unit integer string). JSON numbers only for small integers and basis points. `02-platform-mapping.md > 2.4 Tool design`.
- Freshness on every read: `asOf: { block, timestamp (ISO 8601) }`. `02-platform-mapping.md > 2.4 Tool design`.
- Structured output on every tool plus the same JSON as text for clients that ignore structured content. `02-platform-mapping.md > 2.4 Tool design`.
- Errors: `isError: true` with `structuredContent: { error: { code, message, retryable, details? } }`; the server never throws raw exceptions to the transport. Error codes: `UNAUTHENTICATED`, `TIER_NOT_ALLOWED`, `RATE_LIMITED`, `INVALID_INPUT`, `ASSET_NOT_ALLOWED`, `ACCOUNT_NOT_AVAILABLE`, `UPSTREAM_UNAVAILABLE`, `STALE_DATA`, `INTENT_NOT_FOUND`, `INTENT_NOT_CANCELLABLE`, `DUPLICATE_REQUEST`, `INTERNAL`. `02-platform-mapping.md > 2.4 Tool design`.
- Rejection reason codes (carried in intent status, not as tool errors): `ASSET_NOT_ALLOWED`, `VENUE_NOT_ALLOWED`, `TRADE_SIZE_EXCEEDED`, `CONCENTRATION_CAP`, `USDC_FLOOR`, `SLIPPAGE_TOO_HIGH`, `DAILY_TRADE_LIMIT`, `ORACLE_STALE`, `ORACLE_POOL_DEVIATION`, `INSUFFICIENT_BALANCE`, `CIRCUIT_BREAKER_ACTIVE`, `EPOCH_MISMATCH`, `SIMULATION_FAILED`, `DEADLINE_EXPIRED`, `EXECUTOR_REVERTED`. `02-platform-mapping.md > 2.4 Tool design`.
- No free-text chain strings: token names or symbols fetched from the chain are never returned, only registry values. `02-platform-mapping.md > 2.4 Tool design`.
- A lint rule and code review enforce that no tool schema contains `address`, `agentId`, `owner` or `wallet`. `02-platform-mapping.md > 2.6 Identity, tiers, and metering`.

### 3.4 Enforcement map and limit reads from the Executor

- Each rule is enforced in layers: tool schema (what the model sees), server validation, policy engine before signing, simulation, and the Executor onchain as the final authority. Assets are an enum in the schema and checked at every layer; the venue is not a parameter at all; per-trade size, concentration cap and USDC floor are described in the schema, pre-checked on the server, projected post-trade in policy, checked post-state in simulation, and enforced in the Executor; slippage is `maxSlippageBps` with a maximum, and policy sets `minOut`; exact approvals and reset are internal to the Executor and never exposed; the 20 per 24 hour count is shown in `get_limits`, reserved in policy and enforced onchain; the deadline is not a parameter, is set by policy and enforced onchain; oracle freshness and deviation are shown in `get_prices` and enforced in policy, simulation and the Executor; circuit breaker and epochs are shown in `get_limits` and enforced in policy and the Executor; idempotency is `clientRequestId` on the server and the nonce onchain. `02-platform-mapping.md > 2.4 Tool design`, "Enforcement map".
- The server and policy engine repeat the Executor's checks only to fail fast with a typed reason and avoid gas-wasting reverts. Their thresholds must be read from the same config epoch the Executor uses, not hard-coded. `02-platform-mapping.md > 2.4 Tool design`; `02-platform-mapping.md > 2.8 Risks, ranked` (risk 2).
- `get_limits` reads "from Executor state plus the policy engine". `02-platform-mapping.md > 2.1 Tool mapping table`.

### 3.5 Intent flow

Sequence (`02-platform-mapping.md > 2.5 Intent flow`):

1. Hermes calls `propose_swap`; the E2B firewall adds `Authorization: Bearer <agent session token>`.
2. The server verifies the token and resolves `agentId`, accounts, tier and epoch; validates the schema; applies idempotency on `clientRequestId`.
3. Quick checks in the policy engine (asset, size, caps, floor, trades left). Failure returns `{intentId, status: "rejected", rejection}` synchronously.
4. On pass: persist the intent as `pending`, reserve a trade slot, return `{intentId, status: "pending"}`.
5. Full policy asynchronously: oracle freshness, deviation, quote, `minOut`, deadline of now plus 120 seconds; result is an approved plan with the Executor call built server side; status `approved`.
6. Simulate the Executor call against the latest block; on revert or a post-state limit breach, status `failed` (`SIMULATION_FAILED`) and the slot is released.
7. Sign `Executor.swap(intentHash, params)` with a Privy session key scoped to the Executor only; broadcast; status `submitted` with `txHash` for display.
8. The Executor re-checks every limit onchain, approves the exact amount, swaps, resets the approval; on revert or a passed deadline the status is `failed` (`EXECUTOR_REVERTED` or `DEADLINE_EXPIRED`); on success `settled` with `boughtAmount`.
9. Hermes polls `get_intent_status`.

Implementation notes from the same section: the Executor call is built from the stored intent, never taken from the model or an external API unchecked, and any routing API calldata is decoded and compared with the intent; the Privy policy should allow only `to = Executor` and only the intent entrypoints (Inferred capability, verify); a trade slot is reserved at `pending` so concurrent intents cannot overshoot the daily count and is released on reject, fail, expire or cancel; nonce management lives in the signer service, per session key, serialized.

### 3.6 Identity token binding

From `02-platform-mapping.md > 2.6 Identity, tiers, and metering`:

- When the platform starts a sandbox it mints a short-lived agent session token: a platform-signed JWT with claims `sub` (agentId), `tokenId`, `tba`, `personal`, `vault`, `tier`, `configEpoch`, `ownershipEpoch`, `sandboxId`, `exp`; the research proposes a one-hour lifetime with platform refresh.
- The token is registered with the E2B firewall as an injected header for the chain tools host only and never enters the sandbox.
- Middleware verifies signature, expiry and audience; checks a second factor proving the request came through E2B egress for that `sandboxId` (options: egress IP allowlist, mTLS from the firewall, or a second injected header holding an HMAC over the sandbox ID); loads the agent record; checks that `ownershipEpoch` and `configEpoch` still match chain and database; attaches `authInfo`.
- The MCP session is bound to the `agentId` at creation; a session ID carrying a different principal is rejected; `Mcp-Session-Id` is never authentication.
- Handlers read identity only from `extra.authInfo`. Every data access goes through a repository layer keyed by `agentId` (for example `intents.get(agentId, intentId)` with no unscoped variant), backed by Postgres row-level security on `agent_id`.
- When the NFT changes hands the ownership epoch increases, live tokens are revoked, and the Executor rejects older intents with `EPOCH_MISMATCH`.
- E2B egress: deny by default, allow only the chain tools host and the model provider. `02-platform-mapping.md > 2.3 Where the server runs`.

### 3.7 Tiers

- One `McpServer` instance per authenticated session registering only `tierTools[tier]`, so `tools/list` hides gated tools and `tools/call` on an unregistered tool fails at the protocol level; the tier is re-checked inside each gated handler; a mid-session tier change triggers `notifications/tools/list_changed` or the session is closed and the agent reconnects; the Hermes include list mirrors the tier as a convenience, not a control. `02-platform-mapping.md > 2.6 Identity, tiers, and metering`; `notes/A-mcp-structure.md > 5. Enabling or disabling tools per client`.

### 3.8 Metering hook

From `02-platform-mapping.md > 2.6 Identity, tiers, and metering`:

- All paid upstreams (RPC provider, oracle or price API, quote API, simulation) are wrapped in a `meteredClient(provider)` that requires a `MeterContext { agentId, tool, requestId }`; upstream calls without a context fail in tests.
- Each paid call appends an append-only ledger row `{ ts, agentId, tool, requestId, provider, method, units, unitCostMicros, cacheHit }`, reconciled daily against provider invoices.
- Billing basis recommended: charge per tool call from a price table; keep the raw upstream ledger for cost analysis; record `cacheHit` so the table can be tuned. The alternative (pass-through of upstream cost) is left as an open question. `03-spike-plan.md > Open questions` item 16.
- Budgets: check the per-agent credit balance before paid tools run; when exhausted return `RATE_LIMITED` with `retryable: false`; per-agent token-bucket rate limits on all tools, tighter on `propose_*`.
- The operating wallet pays gas for Executor calls; gas used per intent is recorded in the same ledger keyed by `intentId`.

## 6. Gaps and weak spots

- No Monad chain facts beyond two Inferred chain IDs and an Inferred "gas charged on the limit" remark. The research gives no RPC endpoints, block time, finality model, fee market or priority fee behaviour, and no simulation tool known to work on Monad. The register's faster execution rails, priority fee budgets and 2-minute deadlines cannot be sized from this material. `03-spike-plan.md > (intro)`; `03-spike-plan.md > Step 2`; `notes/B-tools-transactions.md > 5. Gas, nonces, deadlines`.
- No oracle facts at all. The register drops any asset without a reliable feed; with a launch set of USDC and WMON, a missing MON feed leaves nothing to trade. `03-spike-plan.md > Open questions` item 11; `02-platform-mapping.md > 2.1 Tool mapping table` (`get_prices`).
- No venue facts: no depth, no addresses, no v4 hook or Kuru orderbook mechanics. The research itself rates thin liquidity plus the 2% deviation and 0.5% slippage rules as a High-likelihood cause of constant rejections, which would make the agent look broken. `02-platform-mapping.md > 2.8 Risks, ranked` (risk 3); `03-spike-plan.md > Open questions` item 12.
- Internal contradiction on limits: the tool specs and Step 5 hard-code thresholds while the enforcement map says to read them from the Executor's config epoch. `02-platform-mapping.md > 2.4 Tool design`; `03-spike-plan.md > Step 5`.
- Internal contradiction on the deadline anchor (policy step versus signing time). `02-platform-mapping.md > 2.5 Intent flow`; `02-platform-mapping.md > 2.8 Risks, ranked` (risk 10).
- A "Verified" claim that viem works with Monad, in a study where nothing was run. `02-platform-mapping.md > 2.2 Build approach`; `01-codebase-report.md > 1. Versions, license, maintenance, summary`.
- The entire identity model rests on E2B per-host header injection and a second factor, both unverified, and on token rotation without a sandbox restart, which is only an open question. `02-platform-mapping.md > 2.3 Where the server runs`; `03-spike-plan.md > Open questions` item 9.
- Hermes behaviour is unknown on four points that shape the tool contract: config keys, `structuredContent`, `list_changed`, and tool call timeout. The research's fallback (text JSON body, reconnect) is stated but untested. `03-spike-plan.md > Open questions` item 8; `02-platform-mapping.md > 2.8 Risks, ranked` (risk 9).
- One `McpServer` per session is recommended but its scaling with one Hermes instance per agent is an open question the research does not resolve. `notes/A-mcp-structure.md > Open questions` item 7; `02-platform-mapping.md > 2.6 Identity, tiers, and metering`.
- The two-stage circuit breaker, the recipient rule, rebalance leg semantics, vault counters, and USDC-versus-USD denomination are all absent or undecided in the research (see section 4).
- No spike touches the real signer, the real Executor, or mainnet. The spike pipeline stops at a stub Executor on a fork with a local test key. `03-spike-plan.md > Step 3`.
- The `expiresAt` intent TTL, the `quoteValidSeconds` value, and the token lifetime are named but not tied to any measured latency; Step 7 measures inclusion latency but nothing measures quote decay. `02-platform-mapping.md > 2.4 Tool design`; `03-spike-plan.md > Step 7`.

- The MCP SDK version is never pinned in the research and `extra.authInfo` field names are explicitly unverified. `notes/A-mcp-structure.md > 2. Tool registration, schemas, descriptions`.
- Design soundness note (Inference): `get_prices.poolPriceUsd` and `get_quote.feeBps` assume an AMM pool; if Kuru's orderbook is chosen those fields need redefinition (mid-price and taker fee), which the research acknowledges only in passing. `03-spike-plan.md > Open questions` item 12.

## 7. Open questions needing a human decision

1. Which venue, Uniswap v4 or Kuru? Recommended: run K-05 first and pick the venue that absorbs a 10%-of-typical-account trade inside 0.5% slippage; if neither does, the launch limits are infeasible on Monad depth and must be revisited before build. Reason: the research rates thin liquidity as the top likelihood risk (`02-platform-mapping.md > 2.8 Risks, ranked` risk 3).
2. Which oracle feed for MON and USDC, and push or pull? Recommended: prefer a push feed so the Executor needs no update bundling; if only pull exists, extend the Executor entrypoint to accept an update payload. Reason: pull changes the Executor interface (`03-spike-plan.md > Open questions` item 11).
3. Rebalance legs above the per-trade cap: split or reject? Recommended: split into sequential legs each under the cap, each consuming a daily slot; reject only when legs exceed remaining slots. Reason: keeps the Executor single-swap and the register's per-trade rule intact (`03-spike-plan.md > Open questions` item 13).
4. Does a vault account ship at launch, and do vault and personal share the daily trade counter? Recommended: if the vault ships, separate counters and caps per account. Reason: caps are defined per account value (`03-spike-plan.md > Open questions` item 14).
5. Are `get_pool_depth` and `simulate_rebalance` baseline or premium? Recommended: baseline, metered. Reason: the register defines tiers by data and rails, not chain tool access (`02-platform-mapping.md > 2.1 Tool mapping table`).
6. Billing basis: price table per tool call or pass-through of upstream cost? Recommended: price table with `cacheHit` recorded. Reason: shared caches make per-agent upstream attribution arbitrary (`02-platform-mapping.md > 2.6 Identity, tiers, and metering`).
7. Which second factor proves a request came through E2B egress: IP allowlist, mTLS, or an HMAC header over the sandbox ID? Recommended: whichever E2B supports natively, with an IP allowlist as the floor. Reason: a leaked token alone must not be enough (`02-platform-mapping.md > 2.3 Where the server runs`).
8. Simulation tool if Anvil cannot fork Monad: `eth_call` with state overrides on our RPC, or an external service? Recommended: `eth_call` with state overrides behind a provider-agnostic interface. Reason: keeps simulation inside our own trust boundary (`03-spike-plan.md > Open questions` item 15).
9. Signer custody: Privy session keys as the research assumes, or a platform signer? Recommended: Privy if K-03 proves policy scoping to the Executor and its selectors; otherwise a platform signer with the research's minimum checks. Reason: signer compromise is rated Critical impact (`02-platform-mapping.md > 2.8 Risks, ranked` risk 4).
10. Unit of account for limits and portfolio values: USD or USDC? Recommended: USDC, with oracle USD prices converted through a USDC/USD feed and a depeg guard (Inference). Reason: the register names USDC as base currency and the research's schemas say USD.
11. Circuit breaker exposure: should `get_limits` and `get_quote` show the mode (reduce-only versus paused) and should rejection codes distinguish them? Recommended: yes to both. Reason: the agent must know it can still sell into USDC under reduce-only.
12. Deadline anchor: signing time or proposal time? Recommended: signing time. Reason: the research's own risk analysis says so and the flow diagram contradicts it (`02-platform-mapping.md > 2.8 Risks, ranked` risk 10).
13. Run the optional Step 0 probe of the hosted kit server? Recommended: no. Reason: nothing in the build depends on it and the domain is flagged (`03-spike-plan.md > Step 0`).
14. Add a capped-funds mainnet canary with the real signer, Executor and venue after Step 7? Recommended: yes (Inference). Reason: no spike exercises the real signing and inclusion path while the register launches with real money.
15. Per-session `McpServer` instances or a shared instance with a handler-level tier check? Recommended: per-session at launch, with memory and connection counts measured in Step 7. Reason: it is the simplest way to make `tools/list` and `tools/call` agree (`notes/A-mcp-structure.md > Open questions` item 7).
16. Copy nothing from the kit, given the missing LICENSE file? Recommended: confirm the policy of borrowing ideas only. Reason: GitHub reports no license despite the README's MIT claim (`03-spike-plan.md > Open questions` item 6).
