# Hermes research: working notes

Sources: the ten files in `Planv1/research/hermes/` (00 to 09), read in full. Citations use `file.md > Section heading`. "Inference" marks my own reasoning. The decision register quoted in the task brief is called "the register". Nothing in Planv1 was changed; this note is the only file written.

## 1. Coverage and verdict

The research examined `NousResearch/hermes-agent` at commit `085d9ee608893bb0611c2fc339c19d8848af9f2b` (commit date 2026-09-25, 2,142 commits past the latest release tag `v2026.9.24`, MIT license, clean working tree) across six areas: the agent loop and self-improvement (01), model and provider handling including the LiteLLM path (02), tools and MCP (03), skills and memory (04), runtime, cron, API server, config and Docker (05), and security, egress and leak channels (06), followed by a synthesis that resolves twelve contradictions in code (07), a component-by-component platform mapping with a lifecycle design and config layout (08), and a spike plan with ranked risks and twenty open questions (09) (`00-repo-map.md > header table`, `00-repo-map.md > Sub-agent scope adjustments`, `07-summary.md > 5. Contradictions between sub-agent findings, resolved in code`). The overall verdict is: "Wrap an unmodified, pinned Hermes build, configured per agent. Do not fork for v1", because everything needed is reachable by configuration or by our own layers, a fork would carry a heavy rebase cost given the release pace, and the two remaining conflicts (skill text reaches the model vendor, and the agent can always read its skills) are not fixable in Hermes code at all (`08-platform-mapping.md > 6.5 Fork, configure, or wrap`). The research keeps a fallback: if private-skill leakage, upstream churn, or un-disableable self-improvement prove unmanageable, build a thin custom agent loop over LiteLLM and our MCP servers, borrowing Hermes design patterns under MIT (`09-spike-plan.md > 2. Risks, ranked`). Nothing in the spike plan has been run; all findings are from code reading (`09-spike-plan.md > header table`).

## 2. Facts the final plan must carry

### 2.1 Architecture: agent loop, sessions, state

- Every surface (CLI, gateway including the API server, cron, ACP, Python library) builds one `AIAgent` and calls `run_conversation()` or `chat()`; platform differences live in the surfaces, not the agent (`01-architecture.md > 1.1 Shape`).
- Turn admission takes a durable per-session lease row in `state.db` (`LEASE_TTL_SECONDS = 300`, `LEASE_WAIT_SECONDS = 1800`) and starts a turn-liveness watchdog (default 600 s without progress, then force interrupt). Only one turn runs per session at a time, across processes (`01-architecture.md > 2.1 Admission`, `01-architecture.md > 6.4 Multiple sessions`).
- The system prompt is built once per session, cached on the agent and persisted in the session row byte-identical for prompt-cache reuse; it is rebuilt only after context compression. Skills, tools and memory changes take effect next session. This is a declared design invariant, as is "every model tool is sent on every API call" (`00-repo-map.md > Two design invariants that matter for us`, `01-architecture.md > 2.2 Turn setup`, `01-architecture.md > 3. State during a turn and between turns`).
- Prompt tiers: stable (SOUL.md identity, guidance, provider blocks, `skills.auto_load` full bodies), context (caller `system_message`, project context files, git snapshot), volatile (skills index, `MEMORY.md` and `USER.md` snapshots, plugin sections, timestamp and runtime environment) (`02-models.md > 8.1 System prompt`).
- Loop shape per iteration: begin, prepare, assemble API request (structural clones of every message, `api_content` sidecar replay, system message = cached prompt plus `ephemeral_system_prompt`), preflight compression gate, retry loop, normalize response, then either a tool round or a text finish with stop gates (`01-architecture.md > 2.3 The iteration loop`).
- Tool-call decisions are the model's; the runtime shapes them through guidance text, nudges (`intent_ack_continuation`, at most 2 per turn) and the skills index preamble telling the model to `skill_view` matching skills before replying (`01-architecture.md > 4.1 Tool-call decision`).
- Stop conditions: a text response passing every stop gate; iteration budget exhausted (then one tool-less summary call); interrupt (`/stop`, new message under `busy_input_mode = interrupt`, lease loss, liveness watchdog); tool guardrail halt; unrecoverable API error, compression exhaustion or persistence failure (`01-architecture.md > 4.2 Stop conditions`).
- Default turn cap is unlimited: `AIAgent.__init__` defaults `max_iterations=sys.maxsize`, `agent.max_turns` defaults to `None`. Docs saying 500 are stale. Subagent cap is 250 (`01-architecture.md > Doc drift warning`, `07-summary.md > 5. Contradictions between sub-agent findings, resolved in code` row 7).
- The iteration budget is recreated every turn, so `max_turns` is a per-turn cap; there is no built-in cap across turns or a session (`01-architecture.md > 3. State during a turn and between turns`, `01-architecture.md > Open questions` item 1).
- Other guards and defaults: `agent.run_budget_seconds` off (wrap-up notice at 80%); `execute_code`-only rounds are refunded; tool loop warnings on (exact_failure 2, same_tool_failure 3, idempotent_no_progress 2); hard stops off (`hard_stop_enabled: false`) and `non_interactive_hard_stop_enabled` does not cover `api_server`, which is in `_ATTENDED_PLATFORMS`; per-turn caps 50 web searches and 50 subagents; identical-call stall notice on the 3rd identical call; duplicate calls in one batch dropped; empty-response retries 3; compression at 50% of context (cap 256k tokens), protecting the last 20 and first 3 messages, max 3 attempts (`01-architecture.md > 4.3 Limits, budgets and guards`, `07-summary.md > 5. Contradictions between sub-agent findings, resolved in code` row 3).
- Errors: `classify_api_error` yields a `FailoverReason` (auth, billing, rate_limit, overloaded, server_error, timeout, context_overflow, payload_too_large, model_not_found, content_policy_blocked, format_error, and more). `agent.api_max_retries = 3` plus the OpenAI SDK's own `max_retries=2`. Main-turn backoff is jittered with base 2 s, max 60 s (the `retry_utils` default is 5 s / 120 s, but the turn path passes 2 / 60). After retries and the fallback chain, `auto_recovery_cycles = 5` parks the turn only for overloaded, server_error and timeout. Non-retryable classes end the turn with a structured `failure_reason`. HTTP 402 is `billing` and non-retryable (`01-architecture.md > 5.1 API errors`, `02-models.md > 6. Streaming, retries, rate limits, errors, fallback`, `07-summary.md > 5. Contradictions between sub-agent findings, resolved in code` row 2).
- Timeouts: per-request 1800 s (`timeout_seconds` per model, `request_timeout_seconds` per provider, `HERMES_API_TIMEOUT`); non-stream stale 90 s; stream stale 180 s; concurrent tool batch 420 s; sequential tool call the same; liveness watchdog 600 s; gateway inactivity 1800 s; clarify wait 3600 s; subagent inactivity off (`01-architecture.md > 5.2 Timeouts`).
- Tool errors: invalid names get an error result while valid calls in the same batch still run; invalid JSON arguments produce an error without running the tool (`01-architecture.md > 5.3 Tool errors`).
- Parallel tools: batches split into parallel and sequential segments; parallel-safe built-ins plus MCP tools whose server set `supports_parallel_tool_calls`; `_MAX_TOOL_WORKERS = 8`; results returned in call order (`01-architecture.md > 6.1 Parallel tool calls`).
- Subagents: `delegate_task` builds a child `AIAgent` per task (`skip_memory=True`, own 250-iteration budget, own session row linked by `parent_session_id`), children never get `delegate_task`, `clarify`, `memory`, `send_message`, `cronjob_manage`; `max_concurrent_children = 10`; `max_spawn_depth = 1`; top-level delegations always run in the background and their result arrives as a new turn, never mid-turn; child approvals auto-deny (`01-architecture.md > 6.2 Subagents`).
- One process can host many sessions (gateway agent cache 128, idle TTL 3600 s), but Hermes is not fully thread-isolated across agents in one process (process-globals such as `model_tools._last_resolved_tool_names`); the profile (`HERMES_HOME`) is the isolation boundary (`01-architecture.md > 3. State during a turn and between turns`, `01-architecture.md > 6.4 Multiple sessions`).
- Transcript durability: the user row is written at turn start, the assistant tool-call row before any tool runs, and tool results are flushed to `state.db` after every tool round; if that flush fails the turn ends with `session_persistence_failed` (`01-architecture.md > 3. State during a turn and between turns`, `05-runtime-deployment.md > 8.3 Killed mid-turn`).
- Result of `run_conversation`: a dict with `final_response`, `last_reasoning`, `messages`, `api_calls`, `completed`, `turn_exit_reason`, `failed`, `partial`, `interrupted`, `model`, `provider`, `base_url`, token and cost counters, `session_id`, and optionally `error`, `failure_reason`, `guardrail`, `pending_steer` (`05-runtime-deployment.md > 4.1 Python library`).

### 2.2 Self-improvement (must be off)

- Three mechanisms: a post-turn background review fork, foreground `memory` and `skill_manage` tools with prompt guidance to save procedures as skills (plus `/learn`), and a curator (`01-architecture.md > 7. The self-improvement loop`).
- The review fork fires when `_turns_since_memory` reaches `memory.nudge_interval` (10 user turns) or `_iters_since_skill` reaches `skills.creation_nudge_interval` (10 tool iterations, code default confirmed), only at delegate depth 0 and when there is a final response. It replays the conversation on the same model and credentials, with a prompt that says "Be ACTIVE, most sessions produce at least one skill update", can only modify curator-managed skills (`created_by: agent`) but can create brand-new skills without restriction, is budgeted at 16 iterations and an input-token cap, and its writes reach the model only next session (`01-architecture.md > 7.1 Post-turn background review`, `07-summary.md > 5. Contradictions between sub-agent findings, resolved in code` row 6).
- The fork is a hidden model call on the main credentials, tens of thousands of tokens per event (`01-architecture.md > Implications for our platform` item 3, `04-skills-memory.md > 6.2 What is remembered automatically`).
- Curator: gateway-polled, runs after `curator.interval_hours = 168` and `min_idle_hours = 2`; deterministic pass marks curator-managed skills stale after 14 days and archives after 30; LLM consolidation is off by default (`01-architecture.md > 7.3 Curator`).
- Off switches: `auxiliary.background_review.enabled: false` (or `skip_background_review=True`), `memory.nudge_interval: 0`, `skills.creation_nudge_interval: 0`, `curator.enabled: false`, `curator.consolidate: false`, `skills.write_approval: true`, `memory.write_approval: true`, `agent.disabled_toolsets` to remove `memory` or `skills` (`01-architecture.md > 7.4 Controls to disable or constrain`).
- Cron runs already set `skip_background_review=True` but load memory (`skip_memory=False`; the `cron/AGENTS.md` claim of `skip_memory=True` is stale) (`05-runtime-deployment.md > 2.5 How a job runs`, `07-summary.md > 5. Contradictions between sub-agent findings, resolved in code` row 8).

### 2.3 Models, providers and LiteLLM

- Two ways to point at an OpenAI-compatible gateway: bare `custom` on the `model:` block, or a named entry in `providers:` referenced as `model.provider: "custom:<key>"` (recommended). Recognized keys include `base_url`, `api_key`, `key_env`, `key_cmd`, `api_mode`, `models` (per-model `context_length`, `prompt_caching`), `discover_models`, `extra_body`, `extra_headers`, `request_timeout_seconds`, `stale_timeout_seconds`, `session_affinity_header`, `ssl_ca_cert`, `ssl_verify`. `key_cmd` (a command that mints a token, cached until expiry) applies to main and auxiliary calls (`02-models.md > 3.1 Two supported shapes`).
- `OPENAI_BASE_URL` never selects the endpoint; it only scopes which host may receive `OPENAI_API_KEY`. `CUSTOM_BASE_URL` does override the bare custom resolver. `config.yaml` is the source of truth (`02-models.md > 3.1 Two supported shapes`, `02-models.md > 3.3 Env vars`, `07-summary.md > 5. Contradictions between sub-agent findings, resolved in code` row 1).
- Key leak guard: `OPENAI_API_KEY`, `OPENROUTER_API_KEY`, `OLLAMA_API_KEY` are only sent to their own hosts; a `<VENDOR>_API_KEY` is derived from the hostname label (`02-models.md > 3.1 Two supported shapes`).
- Auxiliary tasks (compression, vision, approval, mcp, title_generation, review, memory_query_rewrite, session_search, web_extract, background_review, curator, goal_judge, and more) default to `provider: auto`, which routes to the main provider and model first; the vendor discovery chain runs only when no main provider is set. Exception: vision `auto` has no such gate and falls to OpenRouter, Nous, DeepInfra if those keys exist. Each slot accepts `provider, model, base_url, api_key, timeout, extra_body, reasoning_effort, fallback_chain, max_concurrency` (`02-models.md > 1. TL;DR`, `02-models.md > 3.4 What could bypass the configured endpoint`, `02-models.md > 4.2 Auxiliary slots`).
- MCP `sampling` (server-initiated LLM calls) is enabled by default and routes through the auxiliary client as task `mcp` (`03-tools-mcp.md > 3.1 Configuration format`).
- There is no Hermes-side spend cap; cost for a custom endpoint usually reads "unknown" locally. Budgets must live in LiteLLM. Hermes does not retry a 402 (`02-models.md > 1. TL;DR`, `02-models.md > 5.2 Cost tracking`).
- Default requests carry no `user` field and no session header. Ways to attach an agent id: per-agent virtual key (`key_env`, most robust, covers main, aux and fallback); `providers.<name>.extra_headers` (main and aux on the OpenAI wire; not `bedrock_converse`); `model.default_headers`; `providers.<name>.extra_body` (main turn only; the aux gap is Inferred by the research); `auxiliary.<task>.extra_body`; `llm_request` middleware (main turn only); `session_affinity_header: x-litellm-session-id` (main and aux). `api_request_hooks` are observer-only and their payloads include the full system prompt (`02-models.md > 7.1 What is sent by default to a custom endpoint`, `02-models.md > 7.2 Ways to attach an agent ID for LiteLLM metering`).
- Every main request carries the full system prompt (including the skills index and any auto-loaded skill bodies), every tool schema, and the whole post-compression transcript, including skill bodies returned by `skill_view` (`02-models.md > 1. TL;DR`, `02-models.md > 8.2 Messages and tools`).
- Usage: provider-reported usage is authoritative, normalized into `CanonicalUsage`; streaming requests set `stream_options: {include_usage: true}`; usage is persisted per session, model and task in `session_model_usage`; LiteLLM's `x-litellm-model-id` header is captured, `x-litellm-response-cost` is not (`02-models.md > 5.1 Token counting`, `02-models.md > 5.2 Cost tracking`).
- Prompt caching: Anthropic-style `cache_control` is auto-enabled for LiteLLM plus Claude when the token `litellm` appears in the provider id or hostname; otherwise set `prompt_caching: true` per model. Fallback activation and `/model` switches reset the prompt cache (`02-models.md > 3.2 Example config for one agent sandbox`, `02-models.md > 5.4 Prompt caching`, `02-models.md > 6. Streaming, retries, rate limits, errors, fallback`).
- Metadata lookups (`models.dev`, OpenRouter `/models`, endpoint `/models`) are content-free GETs that fail open; `models_dev.url` can redirect. The `custom` profile sends a top-level `reasoning_effort: medium` by default, which may cost an extra rejected request on non-reasoning routes (`02-models.md > 3.4 What could bypass the configured endpoint`, `02-models.md > 7.1 What is sent by default to a custom endpoint`, `02-models.md > Open questions` item 6).
- Per-stage model choice: Hermes has no "cheap Scan, strong Dive" notion inside one session; options are separate sessions or cron jobs with a per-job model, `delegation.model` for children, middleware rewrite (breaks caching), or LiteLLM alias routing (`02-models.md > 4.3 Mapping to our discovery loop`).
- Programmatic: `AIAgent(base_url=..., api_key=..., provider=..., api_mode=..., model=..., request_overrides=..., fallback_model=...)` (`02-models.md > 3.3 Env vars`).

### 2.4 Tools and MCP

- The registry is a process-wide singleton; built-in tools are discovered by AST scan of `tools/*.py`; `check_fn` hides tools whose prerequisites are missing; dispatch converts every exception into a JSON `{"error": ...}` (`03-tools-mcp.md > 1.1 Registration and discovery`).
- Model-visible tools come from `platform_toolsets.<platform>` (the gateway API server uses platform `api_server`; CLI uses `cli`; ACP uses `acp`), MCP server names in that list act as an allowlist (none named means every enabled server; `no_mcp` excludes all), then `agent.disabled_toolsets` is subtracted last. Calls to names outside `valid_tool_names` are rejected before dispatch (`03-tools-mcp.md > 1.2 From toolsets to the model-visible tool list`).
- There is no per-individual-tool disable key; granularity is the toolset. `custom_toolsets` is documented but no code reads it. `skill_manage` shares the `skills` toolset with `skills_list` and `skill_view` (`03-tools-mcp.md > 2. Tools that touch shell, filesystem, network, or browser, and how to restrict them`).
- `--safe-mode` also disables MCP, so it is not usable for us (`03-tools-mcp.md > 2. Tools that touch shell, filesystem, network, or browser, and how to restrict them`).
- Core toolsets on by default include `web`, `terminal`, `file`, `code_execution`, `vision`, `image_gen`, `tts`, `skills`, `memory`, `todo`, `session_search`, `clarify`, `delegation`, `cronjob`, `browser`; `x_search`, `kanban`, `homeassistant`, `spotify`, `discord`, `video` are default-off. There is deliberately no agent-callable `send_message` tool (`03-tools-mcp.md > 1.3 Built-in tool inventory`).
- MCP config lives under `mcp_servers:` with transports stdio (`command`, filtered env, OSV preflight), Streamable HTTP (default for `url`, content-type preflight), and SSE. Per-server keys: `headers` (static, e.g. `Authorization: "Bearer ${AGENT_MCP_TOKEN}"`), `identity_header`, `auth: oauth`, mTLS, `enabled`, `timeout` (300 s), `connect_timeout` (60 s), `supports_parallel_tool_calls`, `lazy`, `idle_timeout_seconds`, `max_lifetime_seconds`, `trust: full|untrusted`, `sampling` (on by default), `elicitation` (on by default), `tools.include/exclude/resources/prompts`. Global: `mcp.discovery_concurrency` 4, `mcp.auto_reload_on_config_change` true (`03-tools-mcp.md > 3.1 Configuration format`).
- Wire names are `mcp__<server>__<tool>` (non `[A-Za-z0-9_]` become `_`, over 64 chars clamped with an 8-hex hash), toolset `mcp-<server>` with the bare server name as alias; collisions with built-ins or other servers are skipped; `tools.include/exclude` match the original server tool name (`03-tools-mcp.md > 3.2 Naming and prefixing`, `03-tools-mcp.md > 3.3 Include/exclude filtering`).
- Result hygiene: every result from `mcp_*`, `browser_*`, `web_search`, `web_extract` is wrapped in `<untrusted_tool_result source="...">` with a "treat as data" preamble and an advisory threat scan; this applies to our own trusted servers. `read_file`, `terminal`, `execute_code`, document readers and `delegate_task` results are not wrapped. MCP description injection scan only logs (`03-tools-mcp.md > 3.4 Description and result hygiene`, `06-security.md > 6. Prompt-injection defenses`).
- Tool Search: `tools.tool_search.enabled: auto` activates whenever any deferrable tool exists, and every MCP tool is deferrable; the model then sees `tool_search`, `tool_describe`, `tool_call` instead of the MCP schemas. The only way to keep MCP tools eager is `tools.tool_search.enabled: off` (`03-tools-mcp.md > 3.5 Lazy start and Tool Search deferral`).
- Approvals are a dangerous-action gate (terminal commands, `execute_code`, protected file writes, untrusted MCP servers, elicitation), not a per-tool permission system. `approvals.mode: smart` (guardian LLM) by default; `cron_mode`, `single_query_mode`, `unattended_mode` (platforms `webhook`, `msgraph_webhook`, `api_server`) all default `deny`; `approvals.deny` globs are floors nothing bypasses; isolated backends skip container guards. A plain Python `AIAgent` embedding with no CLI, gateway or ask context auto-approves flagged commands. Under the gateway, `HERMES_EXEC_ASK=1` is set and `api_server` keeps `is_ask`, so a flagged action in `/v1/runs` waits for `POST /v1/runs/{id}/approval` up to `approvals.timeout` (300 s) rather than being denied instantly (Inferred by the research, not traced end to end) (`03-tools-mcp.md > 4.1 What it covers`, `03-tools-mcp.md > 4.2 Modes and keys`, `03-tools-mcp.md > 4.3 Headless behavior`, `07-summary.md > 5. Contradictions between sub-agent findings, resolved in code` row 4).
- `hermes -z` one-shot mode sets `HERMES_YOLO_MODE=1` and `HERMES_ACCEPT_HOOKS=1`; never use it for agent work (`05-runtime-deployment.md > 4.2 One-shot CLI`, `07-summary.md > 5. Contradictions between sub-agent findings, resolved in code` row 11).
- Allowlist layers: schema (`platform_toolsets` plus `agent.disabled_toolsets`), call-level name check, per-server `tools.include`, a fail-closed `pre_tool_call` shell hook (`hooks:` block, `matcher` regex, `fail_closed: true`, exit 2 or `{"action":"block"}`; headless runs need `hooks_auto_accept: true`, `HERMES_ACCEPT_HOOKS=1` or a pre-seeded allowlist file), and server-side checks, which are the only layer the runtime cannot change. Caveats: `_RECENTLY_SHIPPED_TOOLSETS` can auto-add toolsets to a saved explicit list after an upgrade; anything that runs code bypasses tool-level policy (`03-tools-mcp.md > 4.4 Can we enforce a strict per-agent allowlist? Yes, by configuration`).
- Output limits: MCP hard cap 2,000,000 chars per text payload; MCP per-result spill threshold 50,000 chars (`tool_budget.mcp_result_size_chars`); per-turn aggregate 200,000 chars or 30% of context; spilled results are replaced by a 1,500-char preview that tells the model to page with `read_file` or `execute_code`; spill files live in `$HERMES_HOME/cache/spillover/` pruned after 24 h. With `read_file` and `execute_code` removed, a spilled MCP result is reduced to its preview (`03-tools-mcp.md > 5. How tool outputs are fed back, and limits`).
- Transport retry: only tools with `readOnlyHint: true` are replayed after a session expiry; write-capable calls return `outcome_uncertain` (`03-tools-mcp.md > Open questions` item 6).
- Tier-based tool sets can be pure configuration per rendered `config.yaml` (separate premium server or per-tier `tools.include` globs), but the server must also enforce tier from the token because config inside the sandbox is not a trust boundary (`03-tools-mcp.md > 6. Tier-based tool sets by configuration only`).

### 2.5 Skills: format, loading, where files must live

- Skills are plain directories `<dir>/[category/]<name>/SKILL.md` plus optional `references/`, `templates/`, `scripts/`, `assets/`. Hermes has no encryption, signing or access control for skill content (`04-skills-memory.md > 1. Executive summary` item 1).
- Parser: file must start with `---`, YAML frontmatter via `hermes_yaml.safe_load` with a naive `key: value` fallback. Write-time validation (only for `skill_manage` writes): `name` and `description` required, description at most 1,024 chars (60 on create), name matches `^[a-z0-9][a-z0-9._-]*$` and at most 64 chars, SKILL.md at most 100,000 chars, support files at most 1 MiB (`04-skills-memory.md > 2.1 Parser`).
- Frontmatter fields with runtime effect: `name` (lookup, falls back to dir name), `description` (index line, truncated to 57 chars plus `...` if over 60), `platforms` (OS gate), `environments`, `requires_apps`, `deps` (calls `pm.ensure(dep)` on `skill_view`, an install path), `required_environment_variables` (checks `.env`, may prompt, registers env passthrough), `required_credential_files`, `metadata.hermes.requires_toolsets/requires_tools/fallback_for_*` (hide from index when requirements are absent), `metadata.hermes.session_platforms`, `metadata.hermes.config` (non-secret settings under `skills.config.<key>`), `metadata.hermes.blueprint` (marks the skill as a suggested cron job). `version`, `author`, `license` have no runtime effect; `allowed-tools` is informational only; category comes from the directory path, not frontmatter (`04-skills-memory.md > 2.2 Every frontmatter field found in code`).
- Body features: `${HERMES_SKILL_DIR}` and `${HERMES_SESSION_ID}` substitution; inline `` !`cmd` `` shell snippets only if `skills.inline_shell: true` (default false). A `DESCRIPTION.md` in a category dir labels the category (`04-skills-memory.md > 2.2 Every frontmatter field found in code`).
- Roots and precedence: project (`.hermes/skills`, `.agents/skills` under a trusted git root), local `$HERMES_HOME/skills/` (bundled skills copied here by `sync_skills`), `skills.create_dir`, `skills.external_dirs` (list, `~` and `${VAR}` expanded, relative paths anchored at `HERMES_HOME`, missing dirs skipped), plugin skills, org mirror. In the index, local wins and external duplicates are skipped; in `skill_view`, two different same-name skills across roots cause a hard "Ambiguous skill name" refusal. Symlinks are followed. `skills.disabled` removes skills; `hermes-agent` is essential and cannot be disabled (`04-skills-memory.md > 3.1 Roots and precedence`).
- Bundled seeding: `sync_skills` runs on CLI startup, on update and in the Docker stage2 hook; a `.no-bundled-skills` marker limits seeding to essential skills only. Not verified for the gateway API server path or direct `AIAgent` use (`04-skills-memory.md > 3.1 Roots and precedence`, `04-skills-memory.md > Open questions` item 1).
- When loaded: index built once per session; cached in an in-process LRU and a disk snapshot `.skills_prompt_snapshot.json` that covers only the local dir; external and project dirs are scanned fresh on every build and never snapshotted. `skill_manage` success clears caches but the running session's prompt does not change (`04-skills-memory.md > 3.2 When loaded`).
- How selected: the index is emitted only if at least one of `skills_list`, `skill_view`, `skill_manage` is present; the preamble says "If a skill matches or is even partially relevant to your task, you MUST load it with skill_view(name)"; selection is entirely model-driven, no retrieval. Other entry paths: slash commands and bundles, `hermes -s`, `skills.auto_load` (full bodies in the stable tier on every surface) (`04-skills-memory.md > 3.3 How selected`).
- Sizes: one index line per skill (about 20 to 30 tokens each, Inferred by the research); `skill_view(name)` returns the whole SKILL.md plus metadata and a `linked_files` listing, with no pagination; `skill_view(name, file_path=...)` returns one support file; repeat views of an unchanged file return an "unchanged" stub; after compression, skill bodies may be pruned to `[SKILL_PRUNED]` (`04-skills-memory.md > 4. How much skill content enters model context, and when`).
- `skill_manage`: atomic `operations` (create, patch, write_file, remove_file, delete); modifies skills in place wherever they live, including `external_dirs`; every mutation is appended to `skills/.curator_ledger.jsonl` with content-addressed blobs under `$HERMES_HOME/.curator_backups/blobs/`, updates `skills/.usage.json`, and triggers a debounced Nous sync push (inert without a Nous admin JWT) (`04-skills-memory.md > 5.1 The skill_manage tool`).
- The agent is told to edit skills it uses: the index preamble says "If a skill has issues, fix it with skill_manage(action='patch')" and "update it before finishing" (`04-skills-memory.md > 1. Executive summary` item 5, `04-skills-memory.md > 5.2 Who calls it`).
- Read-only is only possible via OS permissions or a read-only mount; Hermes has no config to make a skill root immutable to the foreground agent; pinned skills only block `delete`. `skills.write_approval: true` stages every mutation as JSON (with full proposed content) to `$HERMES_HOME/pending/skills/`; `skills.ledger: false` stops blob copies (`04-skills-memory.md > 5.3 Disable, redirect, capture`, `04-skills-memory.md > 7.3 Can skills be read-only or non-viewable?`).
- Skills cannot be hidden from the agent that uses them; `read_file`, `search_files`, `terminal` can read any file and the read denylist does not cover skill dirs. The only real protection for secret logic is to put it behind our MCP tools so the skill text only says "call tool X" (`04-skills-memory.md > 1. Executive summary` item 4, `04-skills-memory.md > 7.3 Can skills be read-only or non-viewable?`).
- Equip mid-session: the index is frozen, so a newly added skill is invisible to the model until a new session even though `skill_view` would find it on disk (`04-skills-memory.md > 7.1 Feasibility`).
- Leak locations for decrypted skill text beyond the skill folder: `state.db` (`messages` tool results, `system_prompts`, `sessions.system_prompt`), the mutation ledger and blobs, curator tarballs, `sessions/request_dump_*.json` (written automatically on non-retryable 4xx and retry exhaustion, no off switch), `pending/` staging files, agent-authored skills and memory, compression summaries, checkpoints (off by default), logs (`04-skills-memory.md > 7.2 What would break or leak`, `06-security.md > 4. Logging and local persistence`).

### 2.6 Memory and what persists

- Built-in memory is two `§`-delimited Markdown files: `memories/MEMORY.md` (`memory.memory_char_limit` 2,200 chars) and `memories/USER.md` (`memory.user_char_limit` 1,375), injected as a frozen snapshot at session start; mid-session writes reach the prompt only next session; no read action; writes are threat-scanned; over-budget adds return an error. Toggles: `memory.memory_enabled`, `memory.user_profile_enabled`, `memory.write_approval`, `memory.nudge_interval`, `memory.provider` (`04-skills-memory.md > 6.1 Built-in memory`).
- Session transcripts in `state.db` with FTS5 are the unbounded recall layer via `session_search`; external memory providers (one at a time) can inject prompt blocks, prefetch, sync and add tools; several are cloud services (`04-skills-memory.md > 6.2 What is remembered automatically`).
- `state.db` schema version 30 with tables `schema_version`, `system_prompts`, `sessions`, `messages`, `session_model_usage`, `state_meta`, `gateway_routing`, `gateway_hygiene_state`, `conversation_generations`, `gateway_heartbeats`, `compression_locks`, `session_turn_leases`, `async_delegations`, plus FTS virtual tables and WAL sidecars (`04-skills-memory.md > 8.1 Complete state inventory under HERMES_HOME`).
- Full `HERMES_HOME` inventory with export verdicts: export agent-created skills, `.usage.json`, `.curator_state`, `.archive/`, `memories/*.md`, `state.db`; never export `.env`, `config.yaml`, `auth.json`, lock files, `sessions/` dumps, `gateway.pid`, `gateway_state.json`; regenerate `config.yaml`, `.env`, `SOUL.md` from the control plane (`04-skills-memory.md > 8.1 Complete state inventory under HERMES_HOME`, `05-runtime-deployment.md > 5.2 HERMES_HOME layout`).
- Existing export commands do not fit: `hermes backup` includes `.env` and `auth.json`; `hermes backup --quick` omits `skills/` and `memories/`; `hermes profile export` force-redacts secret-shaped strings in every text file and can silently alter skill or memory content; `SessionDB.export_all` gives JSON transcripts; `sqlite3.backup()` is the safe way to copy a live `state.db` (`04-skills-memory.md > 8.2 Existing commands`, `05-runtime-deployment.md > 5.4 Templating mechanisms`).
- Thesis Board verdict: Hermes memory is tiny, unstructured, frozen per session, local and autonomously written; the board belongs in our platform MCP server (`write_thesis`, `update_thesis`, `list_theses`, `get_thesis`) with an optional digest at session start (`04-skills-memory.md > 9. Thesis Board: Hermes memory vs external MCP tool`).

### 2.7 Runtime and deployment

- Headless works: a gateway with zero messaging platforms keeps running; the API server is just another platform adapter; the Python `AIAgent` needs no gateway (`05-runtime-deployment.md > 3.2 Headless operation`).
- API server: enable with `API_SERVER_ENABLED=true` and `API_SERVER_KEY` (startup guard refuses keys under 16 chars; the doc's 8 is stale), default `127.0.0.1:8642`. Routes: `POST /v1/runs` plus `GET /v1/runs/{id}`, `/events` (SSE), `/stop`, `/steer`, `/approval`; `POST /v1/chat/completions`; `POST /v1/responses`; `POST /api/sessions/{id}/chat` and `/chat/stream`; `/api/jobs*`, `POST /api/cron/fire`; `GET /v1/skills`, `/v1/toolsets`, `/v1/capabilities`, `/health`, `/health/detailed`. Request fields read: `input`, `messages`, `instructions`, `model`, `stream`, `store`, `conversation`, `conversation_history`, `previous_response_id`, `session_id`, `truncation`. No per-request `toolsets`, `skills` or `response_format`. `instructions` are layered on top of the core system prompt, not a replacement. `Idempotency-Key` survives restarts. Concurrency cap `gateway.api_server.max_concurrent_runs` 10 (HTTP 429) (`05-runtime-deployment.md > 4.3 OpenAI-compatible API server`).
- No native structured output for the main agent on any surface (`response_format` exists only for auxiliary calls); input is plain text only. The robust pattern: our MCP tools define JSON input schemas and the agent's output is its tool calls; `final_response` is only a log line (`05-runtime-deployment.md > 1. Summary`, `05-runtime-deployment.md > 4.5 Structured input and output`).
- Python library caveats: one `AIAgent` per thread or task; no published wheel, run from a PM-prepared source checkout (`05-runtime-deployment.md > 4.1 Python library`).
- Cron: job store `$HERMES_HOME/cron/jobs.json`, outputs under `cron/output/`, `executions.db` ledger; per-job `model`, `provider`, `base_url`, `enabled_toolsets`, `skills`, `script`, `no_agent`, `monitor_script`, `context_from`, `deliver`; ticked by the gateway every 60 s, by `hermes cron tick`, or by a `cron.provider` plugin; bare `30m` is recurring (use `in 30m` for one-shots); `HERMES_CRON_TIMEOUT` is an idle timeout (600 s); chaining reads the last finished output and does not wait; no per-job token or dollar budget; `cron.allow_agent_scheduling` guards recursion; at-most-once per occurrence (`05-runtime-deployment.md > 2.1 Where things live` through `05-runtime-deployment.md > 2.8 Could cron drive our discovery loop?`, `05-runtime-deployment.md > 8.3 Killed mid-turn`).
- `HERMES_HOME` resolution: context-local override, then `HERMES_HOME`, then `~/.hermes`; Docker sets `HERMES_HOME=/opt/data` and `HERMES_WRITE_SAFE_ROOT=/opt/data`. Precedence: CLI flags, `config.yaml`, `.env`, defaults; `config.yaml` supports `${VAR}`. Managed Scope lets an admin pin config and secrets a user cannot override (not investigated further by the research) (`05-runtime-deployment.md > 5.1 Resolution`).
- Important env vars: `HERMES_HOME`, `API_SERVER_*`, `HERMES_CRON_TIMEOUT`, `HERMES_AGENT_TIMEOUT` (1800 s), `HERMES_API_TIMEOUT`, `HERMES_TIMEZONE`, `HERMES_WRITE_SAFE_ROOT`, `HERMES_REDACT_SECRETS` (true), `HERMES_EPHEMERAL_SYSTEM_PROMPT`, `HERMES_YOLO_MODE` (never), `HERMES_GATEWAY_LOCK_DIR`, `HERMES_STARTUP_WATCHDOG_TIMEOUT_S` (300 s, exit 75), `HERMES_GATEWAY_NO_SUPERVISE`, `TERMINAL_ENV` (`05-runtime-deployment.md > 5.3 Most important env vars`).
- Docker image: `debian:13.4`, Python 3.14, Node 26, full Chromium, FFmpeg, ripgrep, s6-overlay PID 1; code at `/opt/hermes` read-only, state at `/opt/data`, UID 10000; documented minimums 1 GB RAM (2 GB with browser), 1 CPU, 500 MB disk; lazy installs default on (the `pm/install.py` docstring claiming the image disables them is wrong); ports 8642, 8644, 9119 (`05-runtime-deployment.md > 6. Docker and runtime requirements`, `06-security.md > 2.2 Contacted by default`).
- One `hermes gateway run` per host per OS user (host lock in `$HERMES_GATEWAY_LOCK_DIR` or `$XDG_STATE_HOME/hermes/gateway-locks`, exit 75 on conflict); never point two processes at one `HERMES_HOME` (`05-runtime-deployment.md > 7. Multiple instances on one host`).
- Startup: bootstrap hardening, startup watchdog, respawn-storm breaker (5 starts in 120 s), exit 78 on fatal config. Shutdown: drains in-flight agents for `agent.restart_drain_timeout` (0 s default, cron floor 30 s), persists active `/v1/runs` as `interrupted`, spools pending messages to `pending_messages/`. Killed mid-turn: no replay and no rollback of half-done tool side effects; background `delegate_task` is lost on restart; Python-embedded runs have no automatic resume (`05-runtime-deployment.md > 8.1 Startup`, `05-runtime-deployment.md > 8.2 Shutdown`, `05-runtime-deployment.md > 8.3 Killed mid-turn`).
- Checkpoints (`tools/checkpoint_manager.py`) are a file-rollback shadow git store, off by default, not a process checkpoint. Scale-to-zero is Fly.io specific (`05-runtime-deployment.md > 8.4 Checkpoints`, `05-runtime-deployment.md > 8.5 Scale-to-zero`, `07-summary.md > 5. Contradictions between sub-agent findings, resolved in code` row 5).

### 2.8 Security: what escapes, injection surfaces, code paths

- Trust model: "the only security boundary against an adversarial LLM is the operating system"; approvals, redaction, Skills Guard, threat scans and env scrubbing are in-process heuristics; skills and plugins execute arbitrary Python at import time with full agent privileges (`06-security.md > 1. Trust model in one paragraph`).
- Required egress: our LiteLLM gateway (main and every auxiliary task, plus `/models` probes of the same host) and our MCP servers (`06-security.md > 2.1 Required for our deployment`).
- Contacted by default and how to stop it: `models.dev` (no off switch; redirect via `models_dev.url`, fails soft), `openrouter.ai` models catalog (only for openrouter, nous or unknown providers), `hermes-agent.nousresearch.com` model catalog (gateway watcher every 20 min; `model_catalog.enabled: false`), GitHub and `hermes-assets.nousresearch.com` update check (`updates.check: false`), tirith binary download (`security.tirith_enabled: false` or pre-install), PM lazy installs from PyPI, GitHub, nodejs.org, npm, playwright, ffmpeg mirrors (`security.allow_lazy_installs: false`), keyless web search backends (`web.keyless_fallback: false` or drop `web`), arbitrary URLs via `web_extract`, browser, vision, Microsoft Edge TTS, `api.osv.dev` for npx/uvx MCP launches (`06-security.md > 2.2 Contacted by default`).
- Off by default: Nous telemetry (two opt-ins, content-free enums), OTLP, Langfuse (captures full prompts and tool I/O), NeMo Relay, outbound webhooks (`hooks.outbound`), Hugging Face trace upload, debug share to pastebins, Skill Sync (`gateway-gateway.nousresearch.com`), Nous Portal, skills hubs, plugin catalog, OpenRouter aux fallback (only if the key exists), messaging platforms (`06-security.md > 2.3 Off by default`, `06-security.md > 3. Telemetry and analytics`).
- Proposed sandbox allowlist: LiteLLM host plus MCP hosts and nothing else; bake `updates.check: false`, `model_catalog.enabled: false`, `security.allow_lazy_installs: false`, `security.tirith_enabled: false`, `security.redact_secrets: true`, `web.keyless_fallback: false`, `telemetry.shared_metrics` off, `curator.enabled: false`, `hooks.outbound: []`, ideally via Managed Scope `/etc/hermes/config.yaml` (`06-security.md > 2.4 Proposed sandbox allowlist`).
- Local persistence that holds prompt or skill content: `logs/agent.log` (80-char user-message previews, 200-char tool-failure snippets, redacting formatter), `sessions/request_dump_*.json` (full request body on non-retryable 4xx and retry exhaustion, or every request with `HERMES_DUMP_REQUESTS=1`, no off switch), `state.db` (system prompts and every message), trajectories (off), memory, agent-created skills and curator backups, checkpoints (off). Redaction targets credentials, not prose (`06-security.md > 4. Logging and local persistence`).
- Secrets: `.env` is the primary store; file tools read-block `.env`, `auth.json`, `mcp-tokens/`, `vault/` (heuristic); terminal subprocesses get a blocklist scrub so unknown custom vars pass through and the shell can still `cat ~/.hermes/.env`; `execute_code` children get an allowlist-ish scrub; in-process code reads everything. The per-agent LiteLLM virtual key and MCP tokens must be treated as model-readable; mitigations are budgets and short-lived tokens. iron-proxy placeholder swapping is Docker-backend specific (`06-security.md > 5. Secrets and API keys`).
- Injection defenses (all heuristics): untrusted wrapping of web, browser and MCP results; context-file threat scan blocks the file (SOUL.md only warns); strict-scope scans on memory writes, skill installs and cron prompts block on first hit, and could block a legitimate private skill with an API-key-shaped literal or "send ... to https://" if written via `skill_manage` (Inferred by the research); MCP description scan; MCP `trust: untrusted`; Skills Guard on installs; approval gate does not cover `pip install`, `npm install` or plain `curl`; SSRF guard; security-guidance plugin appends non-blocking warnings (`06-security.md > 6. Prompt-injection defenses`).
- Code execution paths: `terminal` (default backend `local`, inside the sandbox), `execute_code` (persistent Python subprocess with RPC to a whitelisted tool set), `browser_exec`, skill `scripts/` (run via terminal), skill `deps` (pm installs on `skill_view`), skill inline shell (off by default), MCP stdio servers via npx/uvx, plugins and skills imported into the process, cron `script` and `monitor_script`, shell `pre_tool_call` hooks (`03-tools-mcp.md > 2. Tools that touch shell, filesystem, network, or browser, and how to restrict them`, `04-skills-memory.md > 2.2 Every frontmatter field found in code`, `05-runtime-deployment.md > 2.2 Job definition fields`, `06-security.md > 7. Runtime package installs and arbitrary code execution`).
- The agent can edit Hermes config: `config.yaml` and `auth.json` are read-denied but deliberately not write-denied for file tools, and the shell can edit anything writable, so it could add `hooks.outbound`, change `model.base_url` or enable plugins for the next session. Mitigation: Managed Scope plus the egress firewall, or remove `terminal` and `file` (`06-security.md > 7. Runtime package installs and arbitrary code execution`).
- Twenty channels through which skill content could leave the sandbox, with defaults and closures; the ones that stay open by design are model provider requests (inherent), MCP tool arguments (the agent can put skill text into our tools' arguments), and error messages surfaced to callers (`06-security.md > 8. Channels through which skill contents could leave the sandbox`).

## 3. Platform mapping: what the research recommends we build

### 3.1 Fit classes per component

- Agent brain: Wrap. Keep the loop, tool calling, compression, retries and guards; drive every run through `POST /v1/runs` with an `Idempotency-Key`; the orchestrator owns scheduling, budgets and stage transitions; set `agent.max_turns` and `agent.run_budget_seconds` explicitly (`08-platform-mapping.md > 6.1 Component mapping table` row 1).
- Per-agent model routing and metering: Configure. One LiteLLM virtual key per agent in `.env` via `key_env`; `extra_headers` `x-agent-id` and `x-agent-tier`; pin every auxiliary task; no other provider keys in the sandbox (`08-platform-mapping.md > 6.1 Component mapping table` row 2).
- Baseline tools: Configure. Serve web search, X data, Dune and chain tools from our `chain` and `data` MCP servers over Streamable HTTP with a per-agent bearer token; disable Hermes `web`, `search`, `x_search`; `tools.tool_search.enabled: off` (`08-platform-mapping.md > 6.1 Component mapping table` row 3).
- Premium tier tools: Configure plus server-side check. A `data_premium` server (or wider include list) rendered only into pro configs; the server must also check tier from the token (`08-platform-mapping.md > 6.1 Component mapping table` row 4).
- Private skills injection: Wrap. Decrypt equipped skills into a tmpfs dir (`/run/agent-skills`) mounted read-only before the session starts, referenced by `skills.external_dirs` (`08-platform-mapping.md > 6.1 Component mapping table` row 5).
- Skill slot enforcement: Build ourselves. Hermes loads every skill it finds; the orchestrator decides what to decrypt; namespace skill names (for example `mnd-`) (`08-platform-mapping.md > 6.1 Component mapping table` row 6).
- Built-in playbooks: Configure. Tier identity and hard rules in `SOUL.md`; tier playbooks as `skills.auto_load` skills in a separate read-only dir; starter workflows live in our workflow runner; keep per-run `instructions` small (`08-platform-mapping.md > 6.1 Component mapping table` row 7).
- Memory and persistence: Wrap. Keep built-in memory for small environment facts; turn off `USER.md`; build our own allowlist exporter; encrypt exports (`08-platform-mapping.md > 6.1 Component mapping table` row 8).
- Thesis Board: Build ourselves as platform MCP tools backed by our DB (`08-platform-mapping.md > 6.1 Component mapping table` row 9).
- Discovery loop cadence: Wrap. Orchestrator owns the clock and stage machine; each stage is one `/v1/runs` call with a stage prompt, a budget and a model via LiteLLM alias; disable the `cronjob` toolset (`08-platform-mapping.md > 6.1 Component mapping table` row 10).
- Workflows (rebalancer, idle cash sweep): Build ourselves; Hermes contributes only when a step needs judgment, through a `/v1/runs` call whose result is an MCP tool call (`08-platform-mapping.md > 6.1 Component mapping table` row 11).
- Structured goal input: Wrap. Owners fill forms, the orchestrator stores them, Hermes reads them through `get_goals_and_limits` returning typed JSON; Hermes never receives owner free text; any free-text form field should be removed or classified into enums (`08-platform-mapping.md > 6.1 Component mapping table` row 12).
- Narrator output: Build ourselves. The narrator reads only our MCP action log (tool name, validated arguments, outcome), never `final_response`, reasoning or `state.db` (`08-platform-mapping.md > 6.1 Component mapping table` row 13).
- Strategy parameter tuning: `propose_strategy_update(template_id, params, rationale_code)` with JSON-schema bounds per approved template; our policy layer validates (`08-platform-mapping.md > 6.1 Component mapping table` row 14).
- Unsigned transaction intents: `propose_allocation` and `build_intent` on the chain server return an intent id and never sign; idempotency keys are required; do not set `supports_parallel_tool_calls` on chain or platform servers (`08-platform-mapping.md > 6.1 Component mapping table` row 15).
- Sandbox egress control: E2B allowlist of LiteLLM and MCP hosts plus the config switches listed in 2.8 (`08-platform-mapping.md > 6.1 Component mapping table` row 16).
- Pausing when credits run out: Wrap. LiteLLM enforces budget; orchestrator watches for `failure_reason` billing and LiteLLM budget webhooks, stops in-flight runs, exports state, stops the sandbox (`08-platform-mapping.md > 6.1 Component mapping table` row 17).
- Self-improvement loop: Conflict by default; turn off with `auxiliary.background_review.enabled: false`, `skills.creation_nudge_interval: 0`, `memory.nudge_interval: 0`, `curator.enabled: false` (`08-platform-mapping.md > 6.1 Component mapping table` row 18).
- Owner cannot read skills: Conflict, inherent. Close owner-facing channels; the vendor channel cannot be closed, so the vendor must have zero data retention terms (`08-platform-mapping.md > 6.1 Component mapping table` row 19).

### 3.2 Lifecycle (orchestrator boundary)

- Mint: indexer sees the mint; orchestrator creates the agent record (`agent_id`, tier, token-bound account address, owner), a LiteLLM virtual key with budget equal to current credits, and a per-agent MCP bearer token scoped to `agent_id` and tier; no sandbox until the first scheduled run (`08-platform-mapping.md > Step 1. - Generate config: the orchestrator renders a fresh `HERMES_HOME` with `config.yaml` (base template plus tier overlay plus agent overrides), `.env` (`AGENT_LLM_KEY`, `AGENT_MCP_TOKEN`, `API_SERVER_KEY` of 32+ chars, `API_SERVER_ENABLED=true`), `SOUL.md` (tier), `.no-bundled-skills`, and restored `memories/`, `state.db`, agent-created `skills/`. - Equip: ownership and free slots are checked; changes apply at the next session (new `session_id`), never mid-session; the key service releases skill decryption keys only to the attested sandbox; unequip means the skill is not decrypted into the next sandbox and the exporter drops agent-created skills flagged as derived from it (policy decision) (`08-platform-mapping.md > Step 3. - First research cycle: trigger from the orchestrator scheduler or an event; start the E2B sandbox from our template, write `HERMES_HOME`, decrypt skills, start `hermes gateway run` with only the API server, wait for `GET /health`; `POST /v1/runs` with `Idempotency-Key: <agent>:<cycle>:<stage>`, a new `session_id` per stage, and a short stage prompt; goals are pulled by the agent via `get_goals_and_limits`; later stages are separate runs started when the previous stage wrote its outputs to the Thesis Board; Challenge runs on a different model alias with a skeptic playbook (`08-platform-mapping.md > Step 4. - Proposing an allocation: the agent calls `mcp__platform__propose_allocation({weights: [{asset, bps}], max_drawdown_bps, rationale_ref: thesis_ids, valid_until})`; the server validates against goals and limits, stores a proposal, returns `{proposal_id, status: "pending_policy"}`; policy, simulation and approval proceed outside Hermes; `final_response` is stored privately for debugging (`08-platform-mapping.md > Step 5. Proposing an allocation`).
- Shutdown, export, restore: stop accepting runs, wait or `/v1/runs/{id}/stop`, stop the gateway (active runs recorded `interrupted`); export `state.db` via `sqlite3.backup()`, `memories/MEMORY.md`, agent-created `skills/` plus `.usage.json` and `.archive/`, ship `logs/` to private observability; never export `.env`, `config.yaml`, `SOUL.md`, injected skill dirs, `sessions/request_dump_*`, `pending/`, `.curator_backups/`, lock and pid files; wipe tmpfs and destroy the sandbox; restore is step 2 in reverse before the gateway starts (`08-platform-mapping.md > Step 6. Sandbox shutdown, export, restore`).
- NFT sold: reset goals and limits, cancel pending proposals, rotate MCP token, LiteLLM key and `API_SERVER_KEY`, delete `USER.md`, keep `MEMORY.md` (simplest v1), keep the Thesis Board with pre-transfer items marked, keep or archive transcripts, activity feed visible from transfer onwards (`08-platform-mapping.md > Step 7. NFT sold`).
- Credits run out: LiteLLM rejects with 402, Hermes ends the turn without retry, orchestrator marks `paused_no_credits`, cancels stages, exports, stops the sandbox; deterministic workflow parts can keep running by product choice; top-up raises the key budget and resumes (`08-platform-mapping.md > Step 8. Credits run out`).

## 6. Gaps and weak spots

- Egress-side token injection is asserted by the register but never examined by the research; the research's whole MCP auth design assumes a bearer header in Hermes config from `.env` (`03-tools-mcp.md > 3.1 Configuration format`, `08-platform-mapping.md > Base config.yaml sketch`). Hermes' HTTP transport does a content-type preflight and can strip headers on cross-origin redirects (`03-tools-mcp.md > 3.1 Configuration format`); how an injected header interacts with that is unknown. Inference: this needs its own spike before the chain tools server contract is fixed.
- Skill secrecy is weaker than the product promise suggests: the agent can read and quote every skill, skill text reaches the vendor on every call, and lands in `state.db`, request dumps and compression summaries (`04-skills-memory.md > 7.3 Can skills be read-only or non-viewable?`, `06-security.md > 8. Channels through which skill contents could leave the sandbox`). The research's conclusion is that "skill privacy" must be defined as privacy from owners and other users, not from the model vendor (`09-spike-plan.md > 2. Risks, ranked` row 1). The register's `privacy` field in skill.json has no stated definition.
- Model-driven skill selection from a 60-char description is the only trigger and is untested with several skills (`04-skills-memory.md > 3.3 How selected`, `09-spike-plan.md > 3. Open questions` item 18). Nine launch skills with overlapping research themes (deep-dive, risk screen, regime read, narrative and flow, wallet intel) make distinct descriptions hard. Inference: this is the biggest quality risk that no spike step in section 1 of the plan covers.
- The skills index preamble instructs the agent to patch skills and save new ones; with skills read-only this produces failed tool calls, staged writes, or ledger noise every session unless `SOUL.md` counters it (`04-skills-memory.md > 1. Executive summary` item 5, `08-platform-mapping.md > Changes a fork would need (only if config proves insufficient)`). No spike measures how often this happens.
- Our own platform tool results are wrapped as untrusted (`03-tools-mcp.md > 3.4 Description and result hygiene`). Goals, limits and circuit-breaker state arrive to the model with a "treat as data" preamble. Whether the model still obeys them is unknown (`03-tools-mcp.md > Open questions` item 7).
- Budget enforcement has two soft spots: the LiteLLM error may not classify as `billing` (`02-models.md > Open questions` item 4), and the Hermes budget is per turn only, so cross-run caps are entirely orchestrator work (`01-architecture.md > Open questions` item 1). Hidden model calls (compression, approval guardian, MCP sampling if left on) also bill the agent (`02-models.md > 8.3 Auxiliary requests that carry sensitive content`).
- Request dumps have no off switch and hold the full prompt (`06-security.md > 4. Logging and local persistence`); the only mitigation is a tmpfs mount for `sessions/`, which is a deployment convention, not an enforced control.
- The approval bridge on `api_server` may park a flagged action for up to 300 s (`07-summary.md > 5. Contradictions between sub-agent findings, resolved in code` row 4). With shell and file tools removed this should be rare, but MCP elicitation and `trust: untrusted` also route there (`03-tools-mcp.md > 4.1 What it covers`); the orchestrator needs an auto-deny path or runs can hang.
- Managed Scope is the recommended way to pin security-relevant config, but the research explicitly did not investigate it (`05-runtime-deployment.md > 5.1 Resolution`). The fallback (removing `terminal` and `file`) still leaves `skill_manage`'s `write_file` action and any future toolset auto-add after an upgrade (`03-tools-mcp.md > 4.4 Can we enforce a strict per-agent allowlist? Yes, by configuration`).
- Deployment inside E2B is unmeasured: image is Debian 13.4 with Python 3.14 and full Chromium, s6 may not be PID 1, RSS and startup time unknown (`05-runtime-deployment.md > 6. Docker and runtime requirements`, `09-spike-plan.md > 2. Risks, ranked` rows 5 and 7). The per-stage sandbox lifecycle in the mapping may be too slow; the research itself suggests keeping the sandbox alive across a cycle.
- The register's user-chosen model has no verified delivery path into a running Hermes beyond `model.default` at session start (`02-models.md > 4.1 Main model`); the API server reads a `model` field but the research did not trace its effect (`05-runtime-deployment.md > 4.3 OpenAI-compatible API server`).
- The research's discovery loop, Thesis Board, stage prompts and tool names (`write_thesis`, `complete_stage`, `propose_allocation` with `max_drawdown_bps`) are the research's own Inferred design (`08-platform-mapping.md > 6.1 Component mapping table` header note). The register does not ratify them and its hard limits use different quantities (per-trade percent, asset caps, USDC floor, slippage, trade count).
- Nothing in the research covers x402 payments, following or auto-copy, "faster execution rails", the Executor, the StrategyVault, or Solana. Those are outside Hermes and must be designed elsewhere; the only Hermes-side implication is that intents stay unsigned and idempotent (`05-runtime-deployment.md > Implications for our platform` item 9).
- Parallel Dive runs would need separate homes (`05-runtime-deployment.md > 7. Multiple instances on one host`), yet the export design assumes one `state.db` per agent (`08-platform-mapping.md > Step 6. Sandbox shutdown, export, restore`). Inference: sequential Dives at launch.
- The spike's mock server is Python FastMCP while the register mandates the TypeScript SDK (`09-spike-plan.md > Step 2. Mock MCP server with a structured-output tool`); `readOnlyHint`, `outcome_uncertain` and pagination behavior would be validated against the wrong implementation.
- Memory remains a laundering channel even with the review fork off: the foreground `memory` tool can copy skill text into `MEMORY.md`, which is exported (`06-security.md > 8. Channels through which skill contents could leave the sandbox` row 16). The research keeps memory on and suggests diff audits at shutdown (`04-skills-memory.md > 9. Thesis Board: Hermes memory vs external MCP tool`); nothing specifies the audit.

## 7. Open questions needing a human decision

1. Where do the per-agent secrets live: MCP token and LiteLLM key injected at egress (register, for the MCP token) or in the sandbox `.env` (research)? Recommended: egress injection for both, verified by a spike; reason: any secret inside the sandbox is model-readable (`06-security.md > 5. Secrets and API keys`).
2. Does the user pick one model for every stage, or a model profile that maps to per-stage aliases (cheap Scan and Test, strong Dive, different strong Challenge)? Recommended: one user-chosen primary model at launch, with a platform-defined cheap alias for Scan and Test disclosed in pricing; reason: the register forbids tier-based model choice but not cost-tiered stages (`08-platform-mapping.md > Structuring research tasks for the discovery loop`).
3. Keep Hermes built-in `MEMORY.md` on? Recommended: on, foreground only (`nudge_interval: 0`), `USER.md` off, exported encrypted, diffed at shutdown; reason: cheap environment facts with the review fork off, and dropping it is a one-line change later (`04-skills-memory.md > 9. Thesis Board: Hermes memory vs external MCP tool`).
4. Adopt the research's five-stage discovery loop and Thesis Board as the orchestrator's definition of the discovery loop? Recommended: yes; reason: Hermes has no structured output and no usable cross-session memory, so stage state must live in our tools (`05-runtime-deployment.md > 4.5 Structured input and output`).
5. Do proposals execute automatically within the Executor's hard limits, or wait for an owner approval card? Recommended: automatic within hard limits at launch, with a view-only activity feed; reason: the register has no chat or approval surface and the hard limits are the safety boundary; the platform server contract depends on this (`08-platform-mapping.md > Step 5. Proposing an allocation`).
6. Definition of skill privacy in skill.json: private from owners and other users only, not from the model vendor? Recommended: adopt that definition and require zero-retention vendor terms plus LiteLLM logging off; reason: the vendor channel cannot be closed (`08-platform-mapping.md > 6.1 Component mapping table` row 19).
7. Use Hermes cron at all? Recommended: no, remove the `cronjob` toolset and drive every run from the orchestrator; reason: one clock, and cron chaining reads the last output instead of waiting (`05-runtime-deployment.md > 2.8 Could cron drive our discovery loop?`).
8. Sandbox lifetime: one per stage or one per cycle? Recommended: one per cycle, exported at the end, measured in H-15 and H-33; reason: startup latency risk (`09-spike-plan.md > 2. Risks, ranked` row 7).
9. Surface: gateway API server (`/v1/runs`) or embedded Python `AIAgent`? Recommended: API server; reason: idempotent runs, restart bookkeeping and `interrupted` states, and the embedded path auto-approves flagged actions (`03-tools-mcp.md > 4.3 Headless behavior`, `05-runtime-deployment.md > Implications for our platform` item 1).
10. Keep `read_file` for spill recovery? Recommended: no; keep MCP payloads under 30k chars and paginated server-side; reason: `read_file` can read any sandbox file including decrypted skills (`03-tools-mcp.md > 5. How tool outputs are fed back, and limits`, `04-skills-memory.md > 1. Executive summary` item 4).
11. May turn and run-time budgets differ by tier ("faster execution rails")? Recommended: yes, as an explicit register amendment, keeping model choice out of tiers; reason: the research's tier overlay already varies these and they are the only Hermes-side lever left (`08-platform-mapping.md > Layers`).
12. Do agent-created skills or memory derived from a private skill survive unequip or sale (`09-spike-plan.md > 3. Open questions` item 20)? Recommended: at launch there are no agent-created skills (`skill_manage` blocked), memory survives unequip, and `USER.md` is off so sale needs no memory wipe; reason: simplest policy consistent with "agents evolve through skills and parameters", revisit if memory audits show skill text.
13. Playbook delivery: `SOUL.md` plus an auto-loaded playbook skill, or per-run `instructions`? Recommended: `SOUL.md` plus `skills.auto_load`; reason: prompt-cache stability and `instructions` are layered, not a replacement (`08-platform-mapping.md > System prompt structure`).
14. Which of the research's twenty-plus open-question spikes are required before the first playtest checkpoint versus deferred? Recommended: H-01 to H-06, H-08 to H-14, H-16, H-21, H-22, H-33, H-44 before playtest; the rest deferred; reason: those gate launch components, the others gate fallbacks or later tiers.
