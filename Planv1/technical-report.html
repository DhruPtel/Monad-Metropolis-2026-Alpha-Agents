Technical architecture report

An autonomous financial management platform where each AI agent is an NFT you customize like a game character. Skill NFTs are robotic components that measurably improve the agent, and other people and agents watch, follow, and invest in the agents that perform.

1Summary

The platform is six systems working together:

  1. Identity and ownership. Agent NFTs with their own wallets, and skill NFTs that are equipped by moving them into those wallets.
  2. Agent runtime. A slow LLM brain that researches, writes, and improves trading bots, and a fast bot that executes at block speed.
  3. Capital and execution. Hyperliquid-style agent vaults, an executor contract with hard limits, and a registry of approved protocols.
  4. Marketplace and social layer. Skill marketplace, build cards, watchers, deposits, and paid signal feeds that give owners fast feedback.
  5. Onchain CFO. Goals-based portfolios, debt management, light tax lot tracking, and workflows that run it all, with built-in and marketplace workflows.
  6. Economics. Each agent pays its own hosting and inference from its wallet, so the platform runs without the team funding it.

The guiding rule across all of it: configuration and results are public, logic is private, and proofs connect the two.

3Agent NFT and wallet

What it is

Each agent is an ERC-721 token minted in a tier (base, medium, pro). The tier sets the number of skill slots, the default model budget, and the 3D base model. Every agent NFT gets an ERC-6551 token-bound account, which becomes the agent's wallet. Whoever holds the NFT controls the wallet, so selling the agent moves its skills, funds, and history in one transfer.

How it works on Monad

  • The canonical Tokenbound ERC-6551 v3 stack is already live on Monad mainnet (chain 143) and testnet (chain 10143) at the standard addresses. The registry is 0x000000006551c19487814612e58FE06813775758, and the standard @tokenbound/sdk works with only a config change.
  • Each agent is also registered in the ERC-8004 Identity Registry, which Monad supports with an official guide. The token URI points to an "agent card", which becomes the public build card. This makes agents discoverable by any ERC-8004-aware tool, not just ours.
  • The agent's signing key is never the NFT owner's key. The owner authorizes a platform-managed session key to act for the token-bound account, within limits set by the vault and executor (section 8).

How it works on Solana

Solana has a native equivalent. A Metaplex Core asset registered in the Metaplex Agent Registry gets an identity record plus a built-in PDA wallet called the Asset Signer. Execution is delegated to an offchain operator, which the owner can revoke at any time with RevokeExecutionV1. Metaplex's DAS API now indexes agent fields, including an isAgent filter, across Helius, Triton, QuickNode, and Alchemy.

Contract sketch (Monad)

contract AgentNFT is ERC721 {
  enum Tier { Base, Medium, Pro }
  mapping(uint256 => Tier) public tierOf;
  function mint(Tier tier) external payable returns (uint256 id);
  function slotsOf(uint256 id) external view returns (uint8);
  // on mint: createAccount() on the 6551 registry, register in ERC-8004
}

4Skill NFTs

What they are

Skills are ERC-1155 tokens (one token ID per skill, with a capped supply for rarity). An agent has a skill equipped when its token-bound wallet holds that token. Unequipping moves it back to the owner, which is also how skills get resold.

Skill package format

A skill is a folder in the SKILL.md format used by Bankr, Hermes, Claude Code, and other agent tools: a SKILL.md with YAML frontmatter, plus optional tools, templates, and reference code. Using the common format means builders already know how to write them.

---
name: kuru-market-maker
version: 1.2.0
type: strategy            # strategy (paid, private) or protocol (free, verified)
unlocks_adapters: [kuru_clob]
synergy_tags: [orderbook, fast-exec]
---
Instructions the agent follows when this skill is equipped...
tools/        # MCP tools or scripts the agent can call
reference/    # templates and reference bot code

SkillRegistry (onchain)

One record per skill: publisher address, code hash, current version, price, supply, creator stake, verified-publisher flag, royalty share of performance fees, and the adapters it unlocks.

Storage and privacy

  • Skill folders are encrypted at rest in object storage with a per-skill key held in a key management service.
  • Keys are only released to an agent's sandbox after the runtime confirms onchain that the agent's wallet holds the skill.
  • The owner never receives the plaintext. The LLM sees the instructions, but the owner has no chat channel to extract them (section 6).

Two skill types

Protocol skills

Published by a protocol (for example an official Hedera or Kuru skill). Any price, usually free. Signed by a known publisher key, which shows a verified badge.

Strategy skills

Published by independent developers. Paid, private, limited supply. Creator posts a stake that can be slashed. Earns a share of performance fees from agents that equip it.

Synergies

A synergy table maps skill combinations to a bonus, such as a lending skill plus a perps skill unlocking a basis-trading tool. The runtime checks the equipped set and mounts the bonus tool when a combo is present. The table lives offchain for the hackathon and can move onchain later.

5Skill security pipeline

Uploaded skill code runs next to user funds, so safety is layered. The audit step filters, and the runtime limits are the hard guarantees.

  1. Upload. Creator uploads the encrypted skill through the creator portal. The code hash is committed to the SkillRegistry.
  2. Audit agent. Static checks plus an LLM review flag key access attempts, hidden network calls, data exfiltration, obfuscated logic, and instructions that try to override platform rules.
  3. Stake. Paid skill creators lock collateral. For the hackathon, slashing is decided by an admin multisig.
  4. Listing. Skill appears in the marketplace with its audit status.

Runtime protections, always on

  • Skills never see keys. Signing happens outside the sandbox.
  • Sandbox network egress goes through an allowlist proxy, so skills can't send data out.
  • Every transaction passes wallet policy checks (Privy's policy engine supports transfer limits, contract allowlists, recipient restrictions, and time windows) and then the onchain executor's limits.
  • A transaction screen checks for malicious contracts and unusual patterns before signing, following Bankr's security-layer approach.

6Agent runtime

Two loops

An LLM cannot react inside a 400ms block, so each agent is split in two.

Slow loop: the brain

Runs every few minutes to hours. Reads equipped skills, runs discovery, writes and edits bot code, backtests, and decides whether to deploy a new version.

Fast loop: the bot

Plain compiled code (TypeScript or Rust) that watches blocks and fires trades through the executor. No LLM calls, so it is fast and nearly free to run.

Components

  • Brain framework: Hermes Agent. Nous Research's open-source, MIT-licensed agent. It has persistent memory, a skills system, MCP support, scheduled tasks, and works with OpenRouter, OpenAI, Anthropic, or custom endpoints. Its built-in self-improvement loop matches the "agent gets better" story. Virtuals offers Hermes as one of its two hosted runtimes, which is a useful signal. We run one Hermes instance per agent, configured with our tools and the agent's decrypted skills.
  • Build sandbox: E2B. Firecracker microVMs built for AI agents. Used for writing and testing code. Sessions cap at 1 hour on the free tier and 24 hours on the $150/month Pro plan, so E2B is for building and testing, not for 24/7 bots.
  • Bot runner: persistent containers. Long-running bots live in small always-on containers (Fly Machines or a similar service). Each bot only gets the executor address and a session key with capped permissions.
  • Fork testing: Foundry. Foundry v1.8 and later include first-class Monad execution. anvil --fork-url https://rpc.monad.xyz forks mainnet and automatically applies Monad's gas model and hardfork. Agents test against real protocol contracts with fake capital.
  • Chain tools. Exposed to the brain as MCP tools. On Monad, monad-agent-kit prepares unsigned transactions and never exposes the private key to the agent. Our own adapters wrap each registry protocol.

User input: one-way goals

There is no chat. The owner sets goals in a structured form. A separate goal-translator model turns any free text into a strict config, so the brain never sees raw user text and can't be prompted to leak skills.

{
  "goal": "grow",
  "target_return_30d": 0.04,
  "risk": "balanced",
  "max_position_pct": 0.25,
  "daily_loss_limit_pct": 0.03,
  "allowed_assets": ["MON","USDC","WETH","aprMON"]
}

Output: activity feed and research notes

A separate narrator model reads only the agent's actions and outcomes, never its skills, and writes short plain-English entries like "Moved 40% of the vault to Morpho at 8.2%."

8Vaults and execution

AgentVault

Modeled on Hyperliquid user vaults, where the leader keeps at least 5% of the vault, earns a 10% profit share, can trade depositor funds but never withdraw them, and depositors can leave at any time.

  • One vault per agent, with ERC-4626-style share accounting.
  • The agent owner seeds it and must keep a minimum stake (default 5%).
  • Performance fee charged only above a high-water mark, split between the owner and the creators of equipped skills. Depositors keep the rest.
  • Anyone can deposit. Withdrawals always available, with an optional short lock set at vault creation.
  • Every trade and position is public. Logic is not.
interface IAgentVault {
  function deposit(uint256 assets, address receiver) external returns (uint256 shares);
  function withdraw(uint256 shares) external returns (uint256 assets);
  function execute(bytes32 adapterId, bytes calldata data) external; // executor only
  function highWaterMark() external view returns (uint256);
  function feeSplit() external view returns (uint16 owner, uint16 skillCreators);
}

Executor and ProtocolRegistry

  • The bot's session key can only call the executor. The executor pulls from the vault and calls approved adapters.
  • Hard limits per call: max size, max slippage, per-day loss limit taken from the owner's goals.
  • Atomic strategies (arbs, backruns) revert if profit is below a minimum, so failed attempts only cost gas.
  • The ProtocolRegistry lists approved adapters. An adapter is only callable by an agent if its tier or an equipped skill unlocks it.
  • An owner or admin pause switch stops an agent instantly.

Signing

Privy server wallets hold the session keys. Privy supports Monad mainnet and testnet with gas sponsorship, supports Solana, and enforces policies at the infrastructure level rather than relying on the agent to behave. Privy is also subsidizing Monad testnet usage for builders.

9Billing and self-funding

Borrowed from Virtuals Console, where hosting is charged monthly from the agent wallet, inference is pay per use, and the agent may be paused when the wallet runs dry.

  • What gets metered: LLM tokens, sandbox minutes, bot runner uptime, and paid data calls.
  • LLM gateway: our own OpenAI-compatible proxy in front of a model router. It tags every call with an agent ID, applies the price plus markup, and enforces per-agent budgets.
  • Billing contract: the agent wallet approves an allowance. The metering service settles debits in batches. At zero balance the runtime pauses the agent.
  • Auto top-up: owners can let vault profits refill the billing balance, so a profitable agent funds itself.
  • Platform revenue: markup on usage, mint fees, primary skill sales, and marketplace royalties. This covers hosting so the platform runs without the team paying for it.

10Feedback and social layer

Money is the long-term signal but it moves too slowly to keep owners engaged. The fast signal is demand: other people and other agents choosing your agent, the way views work for a creator.

The gaming risk is real: an audit of Virtuals' revenue leaderboard found agents looping purchases through shell wallets, including four of the top eight.

Following and copying

  • Follow is view-only. Free, shows the agent's trades and build card.
  • Signal feed. Every agent publishes trades after they settle. Delayed feed is free.
  • Real-time and auto-copy. Paid per call via x402. Published only after settlement so followers can't front-run.

Public profile of an agent: 3D model, tier, equipped skills, goal profile, verified stats, evolution timeline, and demand counters. Served as the ERC-8004 agent card.

Instant feedback on builds

When an owner changes a build, the runtime runs a quick backtest on a fork and shows the new build against the old one before deploying. This is the "hit publish" moment in the loop.

11Proofs and verifiability

Anyone can verify that a build card is real without seeing any code.

  1. Skill code hashes are committed at upload. Bot version hashes are committed at every deploy.
  2. The runtime signs EIP-712 attestations such as "agent 7 ran bot version H with skills A and B and produced these trades."
  3. Attestations and outcomes are posted to the ERC-8004 Reputation and Validation registries, which are designed for exactly this kind of track record and third-party validation.
  4. Later: run the runtime in a TEE so attestations are hardware-backed instead of signed by us.

12Agent economy

  • Per-call payments: x402. Monad runs an official x402 facilitator on testnet and mainnet, and Monad Foundation joined the x402 Foundation. Note the version detail: the Monad facilitator only supports x402 v2 and up, and for the "upto" scheme use @x402/evm 2.12.0, since 2.9 to 2.11 point to a proxy that isn't deployed on Monad.
  • On Solana: x402 supports Metaplex Core agents, paying from the agent's PDA wallet.
  • Escrowed jobs: for bigger services, an escrow contract following ERC-8183, the standard Virtuals' ACP implements. One comparison lists ACP's networks as Base, Ethereum, Polygon, Arbitrum, and BNB Chain, so on Monad we deploy our own compatible escrow.
  • Demo: the five agents buy signals and services from each other, which also creates visible demand on build cards.

13Onchain CFO layer

The agent is positioned as an onchain CFO. It does not stop at finding a better yield. It understands what each dollar is for, builds a portfolio around the owner's goals, watches it continuously, rebalances as things change, and manages debt as carefully as assets. Meta's Muse is a useful reference for the feel: it turns long-term goals into action plans, works in the background and checks back in when done, and gives users more guidance than a blank-canvas chatbot. We apply the same idea to onchain money.

Goals engine

The single goals form becomes a list of goals. Each goal has an amount, a horizon, a priority, and a risk profile, and each gets its own bucket inside the agent's wallet. Short-term buckets sit in low-risk stablecoin lending, while long-term buckets can take more market exposure. The zoom-out stage of discovery watches every bucket and rebalances when a bucket drifts past its threshold or when a goal changes.

{
  "goals": [
    { "name": "Emergency fund", "target": 5000, "horizon": "short",  "risk": "conservative", "priority": 1 },
    { "name": "House deposit",  "target": 40000, "horizon": "medium", "risk": "balanced", "deadline": "2029-06" },
    { "name": "Long-term growth","target": null, "horizon": "long",   "risk": "aggressive" }
  ],
  "rebalance": { "drift_threshold_pct": 5, "min_interval_hours": 24 }
}

Liability manager

Onchain debt is managed as actively as assets. The agent monitors loans on Aave, Morpho, and Curvance, tracks health factors so positions never get close to liquidation, refinances debt to a cheaper market when the rate gap beats the cost of moving, and repays early when idle cash earns less than the loan costs. This is the onchain version of mortgage prepayment and refinancing logic, and it is fully executable.

Offchain liabilities such as mortgages and credit cards live in banks. Reading them requires a bank data aggregator, and acting on them requires applications and identity checks an agent cannot do on its own. These stay out of the hackathon build and can come later as read-only recommendations.

Tax lots (kept light)

The agent keeps a simple cost-basis ledger of every lot it buys in the owner's own wallet. The dashboard shows unrealized gains and losses per position, the agent can flag harvesting opportunities for the owner to approve, and the owner can export a lot report. Harvesting only applies to the owner's own capital, not pooled vaults, since depositors own vault shares rather than the underlying trades. Tax rules vary by country, so the output is a report, not advice.

Owner capital and public vaults

Goals, liabilities, and tax lots apply to the owner's own capital in the agent's wallet. The public vault is a separate strategy that depositors can join. One agent can run both, with the executor keeping the two balances and their limits separate.

14Workflows

Skills versus workflows

A skill is a capability: something the agent knows how to do, like routing a loan or trading on an order book. A workflow is a playbook: when to act, in what order, under which conditions, and whether the owner needs to approve. Skills are the parts, and workflows are the routines that put them to work.

How a workflow is built

A workflow is a declarative spec with a trigger, conditions, steps, guardrails, and an approval policy. Steps call skills and tools, and can include an LLM step when judgment is needed. A workflow runner on the platform's job queue executes specs deterministically, so routine management is cheap and predictable and only uses the LLM where it adds value. A durable workflow engine such as Temporal or Inngest is an option if long-running retries become a problem.

name: debt-guardian
requires_skills: [lending-router]
trigger:
  type: condition
  check: health_factor < 1.6
  poll: every_block
steps:
  - if: idle_stable_balance > repay_needed
    do: repay(amount: repay_needed)
  - else:
    do: add_collateral(from_bucket: "long-term growth", max_pct: 10)
guardrails:
  max_action_usd: 2000
approval:
  mode: notify          # auto | notify | require_approval
  require_approval_above_usd: 2000

Approvals and check-ins

Workflows can act automatically, act and notify, or propose and wait for approval. Proposals appear as structured cards with Approve and Reject buttons, written by the narrator model from the proposed action alone. This keeps the owner in control without opening a chat channel that could leak skills.

Workflows on the marketplace

Workflows are a third marketplace item alongside agents and skills, sold as NFTs in the same way. A workflow lists the skills it requires, and the marketplace shows whether the buyer's agent can run it. Creators choose whether the workflow's steps are visible, like a public recipe, or private like a strategy skill. Owners can also build their own workflows from templates in a simple builder.

16How it fits together

Mint and equip

  1. User mints an AgentNFT. The mint creates its token-bound wallet and registers it in ERC-8004.
  2. User buys skill NFTs and drags them onto slots. Each equip is a transfer into the agent's wallet.
  3. The indexer sees the transfer. The runtime releases the skill keys to that agent's sandbox.
  4. User sets goals, funds the billing balance, seeds the vault, and presses deploy.

Deposit and fees

  1. A depositor finds an agent in the gallery and deposits into its vault.
  2. The bot trades vault funds through the executor.
  3. On withdrawal or fee settlement, profits above the high-water mark are split: depositor, owner, and skill creators.
  4. If enabled, part of the owner's share refills the agent's billing balance.

Skill upload

  1. Creator uploads an encrypted skill in the creator portal and sets price, supply, and royalty.
  2. The code hash is committed. The audit agent reviews it.
  3. Paid skill creators post a stake. The skill is listed.

Signal purchase

  1. Agent B's discovery scans the Agent Directory and finds Agent A's build card.
  2. Agent B follows Agent A (onchain event, counts as a watcher).
  3. Agent B pays per call via x402 for A's real-time post-trade feed.
  4. Agent A's build card shows a new signal buyer.

18Monad and Solana split

Two repos, one design. Build the core chain-agnostic from the start with a thin adapter per chain.

Shared core (copy between repos)

  • Agent runtime and Hermes config
  • Skill format, encryption, audit agent
  • Discovery engine and Thesis Board
  • LLM gateway and metering
  • Frontend components and 3D assets

Chain layer (rewrite per chain)

  • Agent, skill, vault, executor, billing contracts
  • Wallet and identity bindings
  • Protocol adapters
  • Indexer config
  • Payment settlement

Keep the core behind interfaces like ChainAdapter.getEquippedSkills(agentId), ChainAdapter.execute(agentId, intent), and ChainAdapter.commitVersion(agentId, hash) so each repo only swaps the implementation.

Colosseum allows pre-existing code if all prior development is disclosed. Disclose the sister build on both submissions, and confirm Monad's rules. On Solana, expect judges to compare directly against ClawPump.
