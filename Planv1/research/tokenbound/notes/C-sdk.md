## 2. Mechanisms

### Address computation (V3) (Verified, `functions/viemV3.ts:161-210`)
- Implementation passed into the ERC-1167 creation code is `implementationAddress ?? ERC_6551_DEFAULT.ACCOUNT_PROXY.ADDRESS`, so for default V3 the TBA is a minimal proxy pointing at **AccountProxy `0x55266d75...`**, not at `AccountV3Upgradable 0x41C8f394...` (line 175-176; constant comment `tokenboundAddresses.ts:32`: "Proxy for the upgradeable implementation, initialization lives here").
- Creation code = `0x3d60ad80600a3d3981f3363d3d373d3d3d363d73 ‖ implementation ‖ 0x5af43d82803e903d91602b57fd5bf3 ‖ abi.encode(salt, chainId, tokenContract, tokenId)` (line 178-198); address = CREATE2 from registry with `salt` padded to 32 bytes (line 201-209). Pure, no RPC.
- Salt is typed `number` (`types/params.ts`, `Custom6551Implementation`), default 0. Inferred: salts above 2^53 or arbitrary bytes32 salts cannot be expressed through the client.
- Test confirms deployed V3 bytecode embeds AccountProxy as implementation (`src/test/TestAll.test.ts:456-459`). Verified.

### Account creation (Verified, `TokenboundClient.ts:210-297`, `305-368`)
- Registry call built by `prepareCreateTokenboundV3Account` (`viemV3.ts:34-66`): `registry.createAccount(implementation=AccountProxy, salt bytes32, chainId, tokenContract, tokenId)`.
- If implementation is not one of `{ACCOUNT_PROXY, IMPLEMENTATION}` (custom), the plain registry call is returned and **no initialization is done** (line 236-239, 263-266); `appendedCalls` then throws (line 254-261).
- Standard V3: returns a tx to `MULTICALL_AUTHENTICATED_ADDRESS` `0xcA1167915584462449EE5b4Ea51c37fE81eCDCCD` (`constants/multicall.ts:3-5`) calling `aggregate3([...])` (line 268-296) with:
  1. `{target: registry, allowFailure: false, callData: createAccount(...)}`
  2. `{target: computedAcct, allowFailure: false, callData: AccountProxy.initialize(ERC_6551_DEFAULT.IMPLEMENTATION.ADDRESS)}` i.e. `initialize(0x41C8f394...)` (line 281-289)
  3. `...appendedCalls` (line 290-292)
- Contract side (Verified, `contracts/src/AccountProxy.sol:22-30`): `initialize(implementation)` has no caller check; it requires `implementation == initialImplementation` or guardian-trusted, then reverts `AlreadyInitialized` if an implementation is already set, else `_upgradeTo(implementation)`.
- The authenticated Multicall3 appends `msg.sender` to each call's calldata (`contracts/lib/multicall-authenticated/src/Multicall3.sol:121`), and AccountV3 treats the forwarder as ERC-2771 trusted forwarder (`contracts/src/abstract/execution/TokenboundExecutor.sol:27-31`), so appended `execute` calls to the new TBA are authenticated as the original EOA. Verified.
- Registry returns existing address without reverting if already deployed (`erc6551-reference/src/ERC6551Registry.sol:25,96`). Inferred: calling SDK `createAccount` a second time for an already created and initialized V3 account reverts the whole multicall (step 2 hits `AlreadyInitialized`, `allowFailure:false`). So SDK creation is not idempotent; check `checkAccountDeployment` first.
- Inferred: an account created directly through the registry (for example by our AgentNFT mint hook) but never initialized has no implementation behind AccountProxy, and execution calls fail until someone calls `initialize(0x41C8...)`. Anyone can call it. Our mint flow must create and initialize atomically (see Open questions).
- `createAccount` with walletClient: `walletClient.sendTransaction({...prepared, chain: this.chain, account: walletClient.account.address})` (line 343-349, with `@BJ TODO: extract into viemV3?`). With signer: `signer.sendTransaction(prepared)` (line 336-341). Returns `{account: computedAcct, txHash}` without waiting for a receipt.
- `aggregate3` calls carry no value (`Multicall3.sol:121` uses `.call` with no value). Inferred: appended calls cannot fund the TBA in the same tx through this path.

### Execution (Verified, `TokenboundClient.ts:437-519`)
- Operation is hardcoded: `const operation = CALL_OPERATIONS.CALL` (line 442). `ExecuteParams.operation` exists in the type but is never read. So DELEGATECALL/CREATE/CREATE2 are not reachable via the client.
- Encodes `execute(to, value, data, 0)` against the V3 implementation ABI; tx `to` is the TBA, tx `value` is 0 (value is spent from the TBA balance) (line 449-482).
- Cross-chain branch whenever `params.chainId !== this.chainId` (line 453-470).
- Transfer helpers (`transferNFT` 651, `transferETH` 716, `transferERC20` 760) all build calldata then call `execute` (V3) or `executeCall` (V2). ERC-721 uses 3-arg `safeTransferFrom`, ERC-1155 uses 5-arg with `"0x"` data (line 677-686). ERC-721 with `amount !== 1` throws (line 664-666). Amounts are JS `number` parsed with `parseUnits` (line 723, 775). Inferred: float precision risk for large or high-decimals amounts; decimals > 18 rejected (line 772-773).
- Recipients may be `.eth` names resolved via `publicClient.getEnsAddress` (`utils/resolvePossibleENS.ts:5-21`). Inferred: on Monad, passing a `.eth` name fails (no ENS registry on the chain); plain addresses are only checksum-normalized.
- Unused/broken internal helper: `prepareTokenboundV3Execute` and `tokenboundV3Execute` (`viemV3.ts:114-155`) pass 3 args to V3 `execute`, whose ABI has 4 (`to, value, data, operation`). Inferred: they would fail to encode; they are not exported from the root and not used by the client.

### Signing and validity
- `signMessage` signs with the connected EOA via `walletClient.signMessage` or `signer.signMessage` (line 814-843). It does not produce or verify an ERC-1271 TBA signature. README says so: "Since your EOA wallet is responsible for signing..." (root `README.md:526`). Verified.
- Bug: `if (!isEthers5SignableMessage && !isEthers6SignableMessage)` (line 820) tests the function objects, not their results, so it never throws. Verified by reading; impact Inferred as minor.
- viem path rejects plain `Uint8Array`/ArrayLike messages (must be string or `{raw}`) (`utils/messageTypeguards.ts:24-28`; tests `TestAll.test.ts:1011-1040`). Verified.
- `isValidSigner` reads `isValidSigner(walletAddress, bytes32(0))` where `walletAddress = walletClient.account.address ?? signer.address` (line 526-549). Contract returns magic if signer is token owner or root owner of a nested tree (`contracts/src/AccountV3.sol:159-173`). Verified. Inferred: ethers v5 `JsonRpcSigner` has no `.address` field, so this may call with `undefined` for that signer type.

### Deployment inspection
- `checkAccountDeployment`: bytecode length > 2 (line 557-565).
- `deconstructBytecode`: splits runtime code as 10/20/15/32/32/32/32 bytes (line 590) matching ERC-1167 + ERC-6551 footer. For V3 the `implementationAddress` returned is AccountProxy, not the real logic contract behind it. Inferred: to learn the actual implementation (post-upgrade) you must read the ERC-1967 slot yourself; the SDK has no method.

- viem version: lockfile resolves only `viem@2.21.32` (`pnpm-lock.yaml:11152`). No `node_modules` in the repo. Cross-check against other local installs (read-only, outside the repo): viem 2.21.53 (`~/eliza/node_modules/viem`) has no `monad*` chain definitions; viem 2.53.1 through 2.56.8 (several other local projects) have `chains/definitions/monad.ts` (id 143, RPC `https://rpc.monad.xyz`, multicall3 `0xcA11bde0...`) and `monadTestnet.ts` (id 10143, RPC `https://testnet-rpc.monad.xyz`). Verified for those installs. Inferred: viem 2.21.32 (older than 2.21.53) has neither; `monad`/`monadTestnet` appear somewhere between 2.21.53 and 2.53.1.
- Because `package.json` declares `viem ^2.21.32` as a regular dependency and the build marks `viem` external (`vite.config.ts:19`), a consumer install today will resolve a recent viem 2.x that does export `monad`. Inferred. However, rollup's `external: ["viem"]` string match does not cover subpaths such as `viem/chains` or `viem/ens`, so those may be bundled into `dist` from the build-time viem. Inferred; check the published `dist/tokenbound-sdk.js` (open question). Either way, we pass our own `chain` object, so the SDK's bundled chain list is irrelevant.

### Using the SDK on Monad (UNTESTED sketch, Inferred)

```ts
// UNTESTED. Inferred from TokenboundClient.ts:95-175 and README.md:126-132.
import { TokenboundClient } from "@tokenbound/sdk"
import { createWalletClient, createPublicClient, http, defineChain } from "viem"
import { privateKeyToAccount } from "viem/accounts"
import { monad, monadTestnet } from "viem/chains" // needs a recent viem (not 2.21.32); else use defineChain below

// const monad = defineChain({ id: 143, name: "Monad", nativeCurrency: { name: "MON", symbol: "MON", decimals: 18 },
//   rpcUrls: { default: { http: ["https://rpc.monad.xyz"] } } })

const chain = monadTestnet // or monad
const walletClient = createWalletClient({ chain, transport: http(RPC_URL), account: privateKeyToAccount(PK) })
const publicClient = createPublicClient({ chain, transport: http(RPC_URL) })

const tb = new TokenboundClient({ chain, walletClient, publicClient }) // pass `chain`, NOT only `chainId`

const tba = tb.getAccount({ tokenContract: AGENT_NFT, tokenId: "1" }) // salt 0, AccountProxy impl
if (!(await tb.checkAccountDeployment({ accountAddress: tba }))) {

  await publicClient.waitForTransactionReceipt({ hash: txHash })
}
// Never pass chainId different from chain.id to execute/transfer* (triggers LayerZero path, no Monad entry).
await tb.transferERC20({ account: tba, recipientAddress: OWNER, amount: 1, erc20tokenAddress: USDC, erc20tokenDecimals: 6 })
```

## 6. How tests run (pattern for a Monad fork spike)
